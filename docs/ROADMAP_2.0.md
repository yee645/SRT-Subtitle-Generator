# SRT 字幕生成器 2.0 工作清單

這份清單是**夜間自動開發排程每晚開工要讀的第一份檔案**。取最上面一項
尚未完成的來做，一次一項；做完把狀態改掉、把實際做法與偏離規劃之處寫
回來，隨當晚的 PR 一起提交。

## 2.0 是什麼

使用者的原話：

> 「主要大幅改動介面和功能流暢至符合使用者設計，以人為本。」
> 「可以及時翻譯使用者選取範圍的文字（英翻中優先開發），不管是事後編輯
> 影片，還是使用者不管在拍片與否都可以使用，希望達到使用者以及影片觀眾，
> 在外文上不會用語言不通、無法帶入等問題，也增加一些學習性。」

兩條主軸：**介面重構**與**選取即翻譯**。

## 發佈政策（2026-09-13 使用者指示，最高優先，覆蓋以下所有舊約定）

使用者原話：

> 「目前版本數有點太多，也遲遲更新不到 2.0 版，在沒有實質成果前請先不要
> 發布 1.x 的版本。小型更新請也使用 y 的版本號（1.x.y）。並且在下個穩定
> 版本發布前，讓使用者不會一直被更新至最新版，沒有穩定或多大功能前，都
> 當作測試版，不讓使用者自動更新，僅手動更新。」

具體規則：

1. **不要再增次版號。** 2.0 完成前的所有工作一律用**修訂號**：
   `1.52.1` → `1.52.2` → `1.52.3` …。次版號 +1 已經停用，下一個次版以上
   的版號就是 `2.0.0`。
2. **一律不轉正。** 不要再把版本 tag 追加到 `.github/promote_releases.txt`，
   不要開轉正 PR。所有 2.0 之前的建置**維持 pre-release**。
3. **這樣就達成「不自動更新」，不必改程式。** `updater.py` 打的是
   `/releases/latest`，而 GitHub 的 latest **不含 pre-release**；維持
   pre-release 即可讓既有使用者停在 `v1.51.0`，想試新版的人自己去
   Releases 頁面手動下載。
4. **沒有實質成果就不要發版。** 純文件、純重構、純測試的變更就只合併進
   main，不要動 `updater.py` 的 `APP_VERSION`、不要觸發 Release。
   `release.yml` 只在 `updater.py` 或 `CHANGELOG.md` 變動時觸發，所以
   「不改版號」本身就是「不發版」。
5. **下一次轉正就是 `2.0.0`。** 屆時才把 `v2.0.0` 加進
   `promote_releases.txt`，使用者才會收到自動更新。
6. **`2.0.0` 必須附一份完整的新功能介紹**（使用者 2026-09-13 指示）。
   **沒有這份文件就不要掛版、不要轉正**——它是前置條件，不是收尾的
   裝飾。規格見下面「7-1」節。特別注意它的範圍是
   **`1.51.0` → `2.0.0` 之間累積的全部改動**（因為使用者的自動更新一
   直停在 1.51.0，轉正那一刻是一次跳過來的），不是只寫最後一版。

## 已定案的決策（不要重新討論）

- **分階段推進**：介面重構拆成數個版本逐步發佈，每一步都可用、可回退。
  版號續編 `1.48.0` → `1.49.0` → …，**全部項目完成的那一版才是 `2.0.0`**，
  中途不跳號。
- **模型分工**：介面與設計判斷交給 `model: "fable"` 的 Agent；實際落地
  （寫檔、跑指令、git、PR、Release）交給 `model: "sonnet"` 的 Agent。
- **「影片觀眾不會語言不通」那一半已經有了**：`subtitle/translator.py`
  的雙語字幕與 `subtitle/multilang.py` 的多語字幕包已覆蓋，**不要重做**。
  新功能補的是「創作者自己看外文素材」那一半。

## 選取即翻譯：技術現實（調研已完成，不要再重新評估）

> 例外：**「截圖 OCR」那一列已於 2026-09-18 翻案**，它的兩個前提變
> 了，正在重新評估（見表格下方的說明與工作清單第 9 項）。其餘各列
> 維持原結論，不要再重新評估。

已做過可行性調研並以 Tkinter 原型實測，結論如下：

| 方案 | 可行性 | 結論 |
|------|--------|------|
| 本程式內選取（`<<Selection>>` + `selection_get()`） | 高，已實跑驗證 | **第一階段做這個** |
| 全系統選取 | **做不到** | Windows 沒有讓外部程式讀取「其他 App 目前選了什麼」的通用 API，零依賴下更沒有 |
| 剪貼簿輪詢 | 中 | 是「複製即翻譯」不是「選取即翻譯」，體驗退一步但技術可靠；**第二階段再評估** |
| 全域熱鍵 | 低 | Tkinter 原生做不到；`ctypes` + Win32 `RegisterHotKey` 理論可行但脆弱，且 Linux 容器無法實測 |
| 截圖 OCR | 極低 | 要扛 tesseract，打包可能多上百 MB，**排除** |

> **2026-09-18 翻案（使用者指示：寫進 ROADMAP、先調研再動手）。** 上面
> 「截圖 OCR 排除」那一列的兩個前提**現在都不成立了**，所以它重新進入評
> 估，見下面第 9 項：
>
> 1. **「打包多上百 MB」**——`gui/ffmpeg_dialog.py` 的一鍵安裝早就在讓使
>    用者下載 80~100 MB 的 ffmpeg 了（只需一次，附進度）。同一套下載＋解
>    壓＋進度回報的機制現成可用，OCR 引擎不必打包進 exe。
> 2. **「要扛 tesseract」**——現在有第三條路：截圖直接送 vision 模型，
>    OCR 與翻譯一次做完，**零新依賴**（即時查譯本來就要使用者的 API 金
>    鑰）。另有第四條：Windows 內建的 `Windows.Media.Ocr`，免費且離線。
>
> **這一列原本的判斷在當時是對的，不刪除**——記錄的是「為什麼當時排除」，
> 翻案記錄的是「什麼前提變了」。

### 9. 螢幕畫面翻譯（框選任意範圍 → OCR → 翻譯 → 朗讀／複製）— 調研✅完成，待實作

**使用者 2026-09-18 指示**：「寫進 ROADMAP，先做調研再動手」。

#### 為什麼是這一題

這是「外文不再語言不通」那條線的**第三階段，不是岔題**：

| 階段 | 版本 | 做法 | 繞開的限制 |
|---|---|---|---|
| 一 | v1.48 | 本程式內選取即翻譯 | — |
| 二 | v2.1.0 | 複製即翻譯（剪貼簿） | Windows 沒有讓外部程式讀取「別人此刻選了什麼」的 API |
| **三** | **本項** | **框選螢幕任意範圍** | **同一個限制的正面解答——讀不到選取，那就讀畫面** |

前兩階段都只是繞路：第一階段要求內容先進到本程式裡，第二階段要求使用者
多按一次 Ctrl+C，而且**有一整類東西根本複製不了**——遊戲畫面、影片裡燒
死的字幕、圖片裡的文字、防複製的網頁。那正是使用者實際會踩到的地方。

#### 範圍：哪些做得到、哪些不承諾

| 能力 | 評估 | 說明 |
|---|---|---|
| 框選任意範圍翻譯 | ✅ 主目標 | 截圖（`ctypes` + GDI `BitBlt`）＋半透明全螢幕 Tk 框選層 |
| 網頁內容、影片對話框、圖片文字 | ✅ 同上 | 畫面靜止時最準，就是主目標的應用 |
| 朗讀原文與譯文 | ✅ | Windows SAPI（`SpVoice` COM），零依賴 |
| 複製原文與譯文 | ✅ | 現成 |
| 進階單字解說 | ✅ **已經有了** | 即時查譯的「附關鍵詞解說」＋生字本（v1.48） |
| **遊戲畫面「連續即時」翻譯** | ⚠️ **不承諾** | 見下 |
| 完全免費 | ⚠️ 看定義 | 見下 |

**為什麼不承諾「連續即時」**：靜態截一張圖翻譯，跟每秒重複做十次是兩回
事。全螢幕獨佔模式的遊戲 GDI 截不到（要 DXGI）；浮在遊戲上的覆蓋層在全
螢幕下容易被吃掉或閃爍；每一幀都要 OCR＋翻譯的話，走 API 的費用與延遲都
不可能「即時」。**能做的是「按一個熱鍵，翻譯現在畫面上這一塊」**——那個
很實用，而且視窗化／無邊框的遊戲都涵蓋得到。像字幕一樣連續跟著跑的版本
留待第 2 階段依調研結果再決定。

**「完全免費」的實話**：現在的翻譯後端是 OpenAI API（使用者自己的金鑰，
要錢）。真要全免費，OCR 得走 Windows 內建或 tesseract，**翻譯**也得換一
個免費後端——那是另一個題目，不混進來。

#### 調研清單（先回答完這些才動手，每一項都要有實測或明確結論）

**A. 可以在這個容器裡實測的**（沒有藉口跳過）

1. **OCR 路線比較**。三條路各自跑同一組測資：
   - (a) vision 模型 API（零新依賴，要錢，往返延遲）
   - (b) Windows 內建 `Windows.Media.Ocr`（免費離線，但零依賴下要用
     `ctypes` 硬接 WinRT，先評估實際難度）
   - (c) tesseract 外掛（沿用 ffmpeg 的一鍵安裝機制）
   測資要**拿真的難例**，不是乾淨的黑字白底：遊戲常見字型、半透明字幕
   底、深色底淺色字、細描邊、文字疊在複雜背景上。可用 ffmpeg 的
   `drawtext` 合成（本專案既有作法）。**辨識率要量出數字**，不能寫「看
   起來還行」。
2. **一次框選翻譯的實際成本與延遲**：token 數、金額、往返秒數，拿真圖量。
3. **OCR 結果的排版還原**：多行、分欄、對話框裡的換行——OCR 回來是一堆
   帶座標的片段，怎麼併回「人看得懂的一段話」是純邏輯，可離線測。

**B. 這個容器裡驗不到的**（Windows 專屬，必須誠實標記）

4. **螢幕擷取**在三種情形下能不能截到：(i) 視窗化 (ii) 無邊框全螢幕
   (iii) 獨佔全螢幕。
5. **框選覆蓋層**：Tk 的 `-alpha` / `-topmost` / `-fullscreen` 在 Windows
   上的實際行為（Linux 容器裡的 Xvfb 不算數）。
6. **全域熱鍵**：`ctypes` + `RegisterHotKey`。上面技術現實表已記「理論可
   行但脆弱，且 Linux 容器無法實測」，這條沒有變。
7. **朗讀**：SAPI 走 COM 還是 PowerShell，哪個零依賴又不會閃出黑框。

> **這一段是本題最大的風險，要寫在調研結論最前面**：這個功能幾乎整包都是
> Windows 專屬表面，核心邏輯（框選座標運算、OCR 片段合併、翻譯快取、生字
> 本）可以寫成零 GUI 依賴、離線測得到，但**真正會壞的地方全在容器摸不到
> 的那一側**。v1.50.0 就是在驗證不足的情況下轉正，把一顆被裁切的按鈕推給
> 了使用者。所以 B 組的每一項，要嘛寫成「失敗時有明確退路而不是當掉」，
> 要嘛就在收工訊息裡明講「這一項沒能實測」。

**C. 隱私（沿用既有原則，不是新發明）**

8. 螢幕內容比剪貼簿**更敏感**——畫面上可能有密碼欄、私訊、銀行頁面。
   v2.1.0 的「寧可漏翻、不可誤送」在這裡的對應是：
   - **只截使用者當下框起來的那一塊**，不自動、不背景、不連續截圖
   - 預設關閉，由使用者主動開啟
   - 送出前讓使用者看得到自己框到了什麼
   - 沿用 `subtitle/clipwatch.py` 的篩子擋掉明顯是密碼／金鑰的內容

#### 分階段（調研結論出來後才定案）

1. **第一階段**：熱鍵框選 → OCR → 翻譯 → 朗讀／複製。價值最高、最可驗
   證，網頁、影片對話框、視窗化遊戲都涵蓋到。
2. **第二階段**：連續即時翻譯——**依調研結果決定要不要做、做到什麼程
   度**，不預先承諾。

完整內容見 **[`docs/RESEARCH_SCREEN_OCR.md`](RESEARCH_SCREEN_OCR.md)**。

**建議：做，先做第一階段。** 最重要的一個結論是實測之後才看清楚的——
**OCR 應該走本地 tesseract，不要走 vision 模型 API**：12 個難例裡 8 個一
字不差、10 個字元錯誤率 ≤ 5%、單次中位數 218 ms、不用錢，而且**畫面不必
離開這台電腦**（只有辨識出來的文字才送去翻譯）。費用、延遲、隱私三件事
一起解掉。vision API 退居「本地讀不到時，使用者自己按一下再讀一次」的選
配。

三條路線裡**只有 tesseract 測得到**：vision API 因為這個容器沒有 API 金
鑰、Windows 內建 OCR 因為沒有 Windows。這兩項照實標記為未實測。

兩個實測發現值得記在這裡：

1. **沒有一種辨識模式全贏**，但「照 tesseract 自報的平均信心值挑模式」
   這個挑法有效（13 個案例裡 12 個挑中最佳或相差 2% 以內）。`psm6` 把某
   個案例從 51.8% 救到 4.4%。
2. **信心值不能只看濾掉低分之後剩下的那些。** 那張「畫面上根本沒有字」
   的雜訊圖吐出 125 個字塊、整體平均只有 21.9，但濾掉低於 45 分的之後剩
   下 18 塊的平均是 68.2——照那個數字判就會把一串亂碼送去翻譯。**這個坑
   第一版就踩了**，拿真實資料跑才發現。

**本輪已完成的實作**：`subtitle/ocrlayout.py`（把 OCR 的帶座標字塊併回可
讀段落——CJK 之間不插空白、硬換行接回句子、兩欄分得開）＋
`tests/test_ocrlayout.py`（測資是真的 tesseract TSV 輸出，五個破壞探針都

**仍然不做「連續即時翻譯」**——數字漂亮不改變這個判斷，理由見調研文件第
5 節。

**第 1 項做完時多出來的一條規則（實跑才發現的）**：調研說「三種模式全
跑」，實作時量出那樣太慢——放大那一次要花掉其餘兩次加起來的時間。改成
**貴的模式只在「可能救得起來」時才跑**：便宜的兩個模式跑完，信心值已經
≥ 90 就不必救，< 40 則救不起來。實測乾淨畫面 12.2 秒 → **0.44 秒**，那張
雜訊圖 9.2 秒 → **1.75 秒**（省下 6.8 秒），而唯二真的靠放大變好的兩個案
例（細描邊 80→93、彩色場景 69→77）都落在中間區間，照樣會跑。

**第 2 項做完時的兩件事**：

1. **這一項有一半在開發環境驗不到，所以刻意拆成兩半做。** 語言檔那一半
   （每個 2~4 MB，直接下載單一檔案）**完整實測過**：真的抓下 eng／jpn／
   chi_tra，驗過檔頭，放進定位，再用它真的辨識出那張中文測試圖。引擎本
   體那一半驗不到——出口網路擋掉 UB-Mannheim 的發行頁與 GitHub API（實
   測 403）、digi.bib.uni-mannheim.de 也連不到，所以**沒有資格硬猜安裝
   檔名**。改成執行期去問 GitHub API 要資產名稱（使用者那台機器沒有這個
   限制），挑選邏輯用真實形狀的 API 回應離線測。
2. **截圖比對抓到一個缺陷，接著又牽出一個更嚴重的。** 截圖顯示這台機器
   上 eng／jpn／chi_tra 都已安裝，對話框卻還勾著要重新下載——因為只掃了
   自己的資料夾，沒問引擎。改成也問 `tesseract --list-langs` 之後，測試
   後段卻開始看不到系統上的語言，追下去才是真正的缺陷：**`TESSDATA_PREFIX`
   只能指向一個資料夾，沒有路徑清單**，把語言檔裝到自己的資料夾再把它指
   過去，使用者原本系統上那一份就整個消失——他只是想加一個日文，結果英
   文不見了。改成**優先裝進引擎自己的語言檔資料夾**（問 `--list-langs`
   的第一行，不用猜），只有那裡不可寫才退回自己的資料夾，而且退回時會先
   把原有的語言檔帶過去。

**第 3 項做完時的兩件事**：

1. **這一項比預期可驗證得多。** 調研把「螢幕擷取」整個列為驗不到，但實作
   時發現 Linux 的 X11 擷取在 Xvfb 下是真的跑得起來的——於是「框選 → 擷
   取 → 辨識」這一整條路在開發環境就走得完：在畫面上放一張有字的圖、模
   擬拖一個框、最後真的辨識出 `Select this line`。**只有 Windows 的
   `ctypes` GDI 那一段仍然驗不到**，調研文件第 1 節那張表要照這個結果改
   寫，不要再把整項寫成驗不到。
2. **「抓到整塊同一個顏色」要當成一種可辨識的失敗。** 全螢幕獨佔模式的
   遊戲抓回來是全黑，沒有這個判斷的話使用者只會拿到一句「沒有讀到文
   字」，完全不知道真正的原因是遊戲的顯示模式——而那件事他自己改得掉。
   已實測：在畫面上放一整塊純黑再擷取，會得到「把遊戲改成視窗化或無邊框
   視窗」這句訊息。

另外修掉自己測試檔的一個弱點（破壞探針露出來的）：實際擷取那一段沒有包
try，擷取意外失敗時例外會往上竄、整個檔案在那裡中止，後面的斷言一條都不
會跑，而輸出看起來只是「少了幾行」而不是「失敗」。這和 `run_all.py` 漏登
記是同一類毛病：測試沒跑，卻沒有人發現。

順手補上 `.gitignore` 的 `tools/`：一鍵安裝會把外部執行檔寫進
`tools/`（ffmpeg 那包就有 80~100 MB），原本沒有被忽略，從 git 檢出跑過
一次安裝就會留一堆未追蹤的大檔。

同一輪也修掉自己寫的一條**空過的測試**：「空結果不能以 0 分參賽」原本用
「空結果 0 分 vs 有字的 30 分」當測資，但空結果本來就算 0 分，拿掉過濾條
件照樣通過。改成給空結果 99 分——守的是「有字才算數，信心值再高也一
樣」。另外又踩到第五次**無效探針**：破壞程式時弄壞了縮排，測試根本沒跑
起來，而我的過濾條件只看 `FAIL` 字樣，沒看見 traceback。

## 每晚的紀律（沿用 v1.x 已驗證的作法）

- 核心邏輯放 `subtitle/`（零 GUI 依賴、CLI 可重用），GUI 只做介面層
- **零第三方依賴**；有勾選/選取狀態的控件一律 `ttk.*`
- **轉正之前一定要有一次獨立審查**，而且審查要**擋在轉正前面**，不是與
  落地並行。v1.50.0 就是在審查完成前被合併、發版並轉正的，等裁切缺陷
  確認時版本已經出去、收不回來，只能再發一版 v1.50.1。派工給子代理時，
  若要它一路做到轉正，就必須自己先看過產出；否則就把終點停在「合併前
  回報」。
- **版面「夠不夠寬」要用量的，不是用看的。** v1.50.0 的自我 review 寫著
  「截圖已核對」，但被切掉的按鈕就在那張截圖裡。`tests/test_v1501.py`
  的通用掃描（走訪所有帶文字且已 map 的控件，比對 `winfo_reqwidth()` 與
  `winfo_width()`）是為了取代這個靠肉眼的判斷——**動過版面的版本都應該
  跑它**。
- **新寫的回歸測試要先證明它在壞掉的程式碼上會失敗。** 在壞碼上也會過
  的測試沒有意義。v1.50.1 的掃描測試就是這樣驗過才收的。
- **GUI 驗證一定要用 `/tmp/vtk/bin/python3`**（那個 venv 才有 `sv_ttk`）。
  系統的 `/usr/bin/python3.12` **沒有** `sv_ttk`，用它截出來的是無主題畫面，
  深淺兩色會長得一模一樣、等於主題驗證沒做。v1.49.0 就是這樣誤判過一次，
  還在 PR 裡寫下「此沙盒未安裝 sv_ttk」的錯誤結論。截圖腳本裡加一行
  `import sv_ttk; print(sv_ttk.get_theme())` 自我確認，不要憑感覺。
- **版面類斷言要在 `deiconify()` 之後量**：未顯示的視窗其子元件一律回報
  `winfo_ismapped()=0`、寬高 1px，在那之前量會誤判。v1.48.0 的捲軸缺陷
  就是因為在錯的時機量而被放行。
- 真實端到端驗證，不只靠 mock；GUI 一律實際截圖並用 Read 檢視，
  **深淺兩色主題都要看**，並以預設視窗尺寸另截一張確認版面沒被撐破
- 介面改動要**改動前後對照截圖**，確認沒有把既有內容擠掉
- 全套測試 `tests/run_all.py` 只有 `test_v150.py` 可忽略（既有環境限制）
- Whisper 模型檔與 pytorch.org 被出口網路政策擋 403，**不要嘗試繞過**，
  用假 whisper 模組做端到端測試即為足夠驗證
- 未能實測的項目一律在總結中明講，不要略過
