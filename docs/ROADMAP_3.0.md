# SRT 字幕生成器 3.0 工作清單

這份文件定義 **3.0 的目標**。2.x 的工作清單仍在
[`docs/ROADMAP_2.0.md`](ROADMAP_2.0.md)，**它還沒做完，優先權仍然在它上面**；
本文件是等那邊收尾之後才開工的題目。

## 3.0 是什麼

使用者的原話（2026-09-23）：

> 「繼續開發，可繼續搜尋和制訂更新內容，並將 3.0 的目標訂定在，期望將本
> 軟體做成如 adobe premiere 等主流剪輯軟體的水準。」

## 使用者決定：底座的堅持放掉到第 2 層（2026-09-23，最高優先）

問過「要做成 Premiere 需要放掉哪些堅持」之後，列出了三層（每一層都以前
一層為前提），使用者的回答是：

> 「可以放到2」

也就是：

| 層 | 堅持 | 3.0 的狀態 |
|---|---|---|
| 1 | **零第三方 Python 套件**（目前 exe 只打包 `openai`、`zhconv`、`sv_ttk`） | **放掉**：可以用 PySide6、numpy 等套件 |
| 2 | **Tkinter 介面** | **放掉**：3.0 的介面改用 **Qt（PySide6）** |
| 3 | 純 Python、一個人夜間增量開發的規模（不引入 C++ 剪輯引擎如 MLT） | **保留**，不放 |

**適用範圍要講清楚，否則之後每一晚都會搞混**：

* 放掉的只有 **3.0 這條線**（新的 Qt 介面與它需要的核心）。**2.x 的 Tk
  介面照舊遵守零依賴、`ttk.*` 等所有既有規則**，直到它被 Qt 版取代為止。
* **這些照舊，不因這個決定改變**：
  - `subtitle/` 核心模組**零 GUI 依賴**（這條正是換介面時最值錢的一條
    ——57 個模組一個都不用重寫）
  - 隱私規則（剪貼簿、螢幕擷取預設關閉；「寧可漏翻、不可誤送」）
  - 先調研再動手；新測試要先證明在壞掉的程式碼上會失敗
  - Whisper 模型檔與 pytorch.org 被出口網路政策擋 403，**不要嘗試繞過**
  - 發佈政策（次版轉正要使用者拍板、四個產出物）
* **新套件的門檻**：每加一個都要在 PR 寫明「為什麼標準函式庫或既有套件不
  夠」與「打包後增加多少體積」。放掉零依賴不等於什麼都可以加。

## 換成 Qt 之後的實測（2026-09-23）

這一節取代原本「Tkinter 底座的硬限制」那張表——那張表的結論在換底座之後
大半不成立了。

**環境**：PySide6 6.11.2（LGPL-3.0），開發容器、**沒有 GPU**、4 核
CPU、`QT_QPA_PLATFORM=offscreen`。Qt Multimedia 自報使用內建的
**FFmpeg 7.1.5（LGPL）**做解碼。

| 量什麼 | Tkinter＋ffmpeg 子行程（舊） | Qt Multimedia（新） |
|---|---|---|
| 720p30 連續播放 | 上限約 8~12 fps、無聲 | **30.0 fps**（滿速） |
| 1080p30 連續播放 | ——（沒量） | **30.0 fps**（滿速） |
| 1080p60 連續播放 | —— | **60.1 fps**（滿速） |
| 720p 跳到任意位置（6 個點） | 81~130 ms | **3~112 ms** |
| 1080p 跳到任意位置（6 個點） | —— | **86~195 ms** |

幾點照實說明：

1. **聲音沒驗到。** 容器裡沒有音效裝置（`QMediaDevices.audioOutputs()`
   回傳空清單、PulseAudio 連不上）。所以「影音同步」**一次都沒驗過**，
   只驗到畫面解碼。這要在使用者的 Windows 上驗。
2. **1080p 的跳轉比 720p 慢不少**，最慢接近 0.2 秒。測試片用的是 x264
   預設的關鍵影格間距（約 8 秒）；真實相機素材的間距各家不同，可能更好也
   可能更差。拖曳時間軸要順，**就需要代理檔**（見工作清單），這也是
   Premiere 自己的解法。
3. **量的是沒有 GPU 的容器**，純 CPU 解碼。使用者的電腦多半有 GPU，Qt
   在 Windows 上可能自動用硬體解碼——**這一點沒驗過，不要當成已知**。
4. 1080p60 那一組第一次量的時候，跳轉點超出了片長（20 秒的片子跳到 150
   秒會被夾到片尾），數字無效，已按片長比例重量。上表是重量後的數字。

**打包體積**：PySide6 完整安裝 650 MB（含所有附加模組）；實際需要的部分
（Core、Gui、Widgets、Multimedia、MultimediaWidgets、FFmpeg 函式庫、
平台外掛、shiboken6）在 Linux 上合計約 **139 MB（未壓縮）**。Windows 版
的實際 exe 大小**沒有量**——要等 CI 在 Windows runner 上真的打包一次才知
道（見工作清單第 0 項）。

**先前「用 mpv 外部執行檔嵌進 Tkinter」的想法不必做了**：那是為了在零依
賴下取得真播放的繞路；Qt Multimedia 本身就帶 FFmpeg，直接解決。

## 差距盤點（沒有因為換底座而改變）

**已經有了，而且是 Premiere 沒有的**：逐字稿審片（`subtitle/review.py`）、
全片停頓自動跳剪（`subtitle/jumpcut.py`）、重複拍攝偵測與剪除
（`subtitle/retakes.py`）、短影音切片（`subtitle/shorts.py`）、字幕樣式
與燒錄、多語字幕包、十幾項上架前健檢、螢幕畫面翻譯。**3.0 不能為了追像
Premiere 而把它們稀釋掉**——它們是使用者選這個工具而不是 Premiere 的理
由。

**缺的**：

1. **所有的剪都是盲剪。** `jumpcut.py` 算出剪點之後直接輸出成片，使用者
   從頭到尾看不到剪在哪裡。`subtitle/review.py` 的說明自己寫著匯出 EDL
   「匯入 Premiere / DaVinci Resolve 繼續精剪」——那行字就是差距的位置。
2. **沒有播放器、沒有時間軸。** `gui/` 至今沒用過一次 `PhotoImage`；
   `gui/preview_panel.py` 的「預覽」是用 Canvas 畫出來的假畫面。
3. **沒有轉場**（全庫 `xfade` 零命中）。
4. **不能拼多支素材**，所有流程都假設一支輸入影片。
5. **波形只是輸出物**（`audiovis.py` 算成影片），編輯時看不到。
6. **沒有多軌**（B-roll 疊在主軌上、背景音樂獨立一軌）。

## 3.0 的目標

> **一個以時間軸為中心、能即時播放的剪輯介面，而本工具原有的自動化——
> 審片、跳剪、剪重複、切短影音、字幕、翻譯、健檢——全部直接在那條時間軸
> 上發生、看得見、改得動。**

具體承諾：

* **真的能播**：影片與聲音同步播放、拖曳即時換畫面（1080p 以上靠代理檔）。
* **剪完之前看得到剪在哪裡，而且改得動**。
* **多軌**：主影片軌、疊加軌（B-roll／圖片）、字幕軌、音樂軌。
* **最基本的剪輯動作**：切割、刪除、移動、修剪邊緣、轉場、畫面調整，
  全部可預覽。

## 遷移策略：兩套介面並行，逐頁搬

換掉介面工具包沒辦法「一晚改一點」地在原地改——Tk 與 Qt 無法共存於同一
個視窗。但**可以共存於同一個程式**：

1. 新介面放在 **`gui_qt/`**，與既有的 `gui/` 並列；兩者都只呼叫
   `subtitle/` 核心，**共用同一份設定檔**。
2. 入口加一個開關（例如 `--qt` 或設定項），**Tk 版維持預設**。Qt 版以
   「3.0 預覽版」的身分跟著 2.x 一起出貨，想試的人自己打開。
3. 每一晚搬一頁或做一個新元件，**每一步都能單獨出貨、單獨回退**——既有
   規則因此不必破例。
4. `2.3.0` 之後，**Tk 版只修錯、不再加新功能**，新功能一律只做在 Qt 版，
   避免兩套一起長。
5. Qt 版追上 Tk 版的全部功能之後，才把預設切過去；那一版就是 `3.0.0`。
   Tk 版在 `3.0.0` 之後的某一版移除（屆時另外決定）。

### 第 0 項調研結果（2026-09-26）

量測工具：`research/qt_probe/`（探針＋量測腳本）與
`.github/workflows/qt-probe.yml`（windows-latest，只量測、不發佈，只在動到
這兩處的 PR 觸發）。探針載入 3.0 會用到的 QtWidgets／QtMultimedia／
QtMultimediaWidgets，建一個帶影片元件與播放器的主視窗，顯示後自報時間並
自行關閉。

**已確認（讀套件本身，不是憑記憶）**：

- **QtMultimedia／QtMultimediaWidgets 在 `PySide6-Addons`，不在
  `PySide6-Essentials`。** 只裝精簡版不夠，打包環境要裝完整的 `PySide6`。
- **授權**：`PySide6`、`PySide6-Essentials`、`PySide6-Addons`、`shiboken6`
  6.11.2 的套件中繼資料都寫 `LGPL-3.0-only OR GPL-2.0-only OR
  GPL-3.0-only`，另有商業授權。Qt 自帶的 FFmpeg 在啟動時自報「FFmpeg
  version 7.1.5 LGPL version 2.1 or later」。
- **wheel 裡沒有任何授權全文**（dist-info 只有 METADATA，沒有 LICENSE 檔），
  所以 PyInstaller 打包出來的成品**一個授權檔都沒有**（本機 onefile、onedir
  兩種都確認過）。要守 LGPL，至少得自己把授權全文與「用了哪些 LGPL 元件、
  原始碼在哪」的說明放進成品——這件事**不會自動發生**。
- LGPL 條文細節（onefile 算不算讓使用者「能替換函式庫」、要附原始碼還是附
  取得方式）**這次沒有核對原文**：gnu.org 被這個環境的出口政策擋下，沒有
  繞過。在核對原文之前，**onedir（Qt 的 DLL 是分開的檔案，可以直接替換）
  是比較不會出錯的選擇**；是否真的必要留待核對後定案。

**本機 Linux 參考數字**（不是 Windows，只看量級；Linux 上 PyInstaller 會把
Qt 函式庫複製兩份，onedir 偏大）：

| | onefile | onedir |
|---|---|---|
| 大小 | 79 MB | 321 MB（379 檔，zip 後 126 MB） |
| 啟動牆上時間（第一次／其餘中位數） | 1.47／1.37 秒（多半是解壓） | 0.22／0.22 秒 |

對照：目前 2.x 的 Tk 版 exe 是 23.7 MB（onefile）。

**Windows 實測**（PR #146 的 CI，windows-latest、Python 3.11.9、PySide6
6.11.2，各跑 5 次；run 36208465917）：

| | onefile | onedir |
|---|---|---|
| 大小 | **58.2 MB** | 146.5 MB（245 檔），**zip 後 58.4 MB** |
| 啟動牆上時間（第一次） | 2.69 秒 | 0.31 秒 |
| 啟動牆上時間（其餘中位數） | **2.65 秒** | **0.29 秒** |
| 探針自報：Python 開始到視窗顯示 | 0.11 秒 | 0.09 秒 |
| 對照：2.x Tk 版 exe | 23.7 MB（onefile） | — |

- **onefile 每次啟動都要多等 2.5 秒左右**——不是只有第一次。onefile 每次都
  把 58 MB 解壓到暫存資料夾，五次都落在 2.5～2.7 秒；onedir 五次都在 0.3 秒
  上下。探針自報的時間兩者幾乎一樣，差的全是解壓。
- **多媒體後端有被正確打包**：`ffmpegmediaplugin.dll` 與
  `windowsmediaplugin.dll` 都在，FFmpeg 的 avcodec／avformat／avutil／
  swresample／swscale 五個 DLL 都在；播放器對不存在的檔案回報
  `ResourceError`（後端正常運作時的回應）。
- **授權檔：Windows 上同樣一個都沒有。**
- **有明顯可以瘦身的地方**（onedir 最大的檔）：`opengl32sw.dll` 20.6 MB（沒有
  顯示卡驅動時的軟體 OpenGL 備援）、`Qt6Quick.dll` 6.6 MB、`Qt6Qml.dll`
  5.3 MB、`Qt6Pdf.dll` 4.6 MB——探針完全沒用到 Quick／QML／PDF，是
  PyInstaller 的多媒體掛鉤一起拉進來的。能不能排除要實測（排除後播放器還
  能不能動），這四個加起來約 37 MB。
- CI 機器沒有音效裝置（`audio_outputs` 為 0），聲音仍然沒驗到。

**這些數字帶出來的決定（第 1 項開工前要定案）**：

1. **傾向 onedir**：啟動快九倍，zip 後下載量與 onefile 相同，Qt 的 DLL 是分開
   的檔案、使用者可以直接替換（對 LGPL 也比較穩妥，見上）。
2. **代價是自動更新要改**：`updater.py` 現在下載的是單一
   `SRT-Subtitle-Generator.exe` 並就地替換自己；onedir 是一整個資料夾，要改
   成下載 zip、解到旁邊、下次啟動時切換。Qt 版以預覽身分跟 2.x 一起出貨時，
   **Tk 版的單一 exe 與自動更新維持不變**，Qt 版另外一個 zip，這個問題可以
   延後到切換預設（3.0.0）前再解。
3. 授權全文與元件說明要自己放進成品（`release.yml` 加一步），條文細節待核對
   原文。

**第 0 項剩下的**：影音同步（需要有音效裝置的機器，CI 做不到）、LGPL 原文
核對。（四個大檔能否排除：已完成，見下。）

**四個大檔能否排除（2026-09-26 第二輪，已完成）**

為什麼挑這件：它是第 0 項裡唯一 CI 就驗得到的（另外兩件要音效裝置、要讀
gnu.org），而且直接決定 Qt 版 zip 是 58 MB 還是可能再小三成多，第 1 項
改 `release.yml` 前就要知道。

作法：探針多一種模式——給一支**真的影片**（`research/qt_probe/probe_clip.mp4`，
2 秒、320x180、H.264＋AAC、28 KB，ffmpeg 測試圖樣產生），真的播放並從影片
元件的 sink 數解出幾格，外加 `player_available`（後端外掛沒載入時播放器
「不可用」而且**不發任何錯誤訊號**，只看 `player_error` 會誤判成正常）。
量測腳本把 onedir 複製幾份，分別拿掉四個檔的其中一個與全部四個，各播 3 次。

本機 Linux 先跑（只當腳本驗證與參考，Windows 的相依關係不一定一樣）：

| 拿掉 | 播放 |
|---|---|
| 完整版（對照） | OK，3 次都解出 50 格、播到結尾 |
| Qt6Pdf | **OK**（50 格） |
| Qt6Quick | **失敗**：「No QtMultimedia backends found」，播放器不可用 |
| Qt6Qml | **失敗**：同上 |
| opengl32sw | Linux 沒有這個檔，Windows 才驗得到 |

也就是說在 Linux 上 Quick／Qml **不是白搭的**：多媒體後端外掛依賴它們，
拿掉整個播放器就沒了。

**Windows 實測**（PR #147 的 CI，run 36226964829，windows-latest、PySide6
6.11.2，每種各播 3 次）：

| 拿掉 | onedir 大小 | 播放 |
|---|---|---|
| 完整版（對照） | 146.5 MB | OK，3 次都解出 50 格、播到結尾 |
| opengl32sw | 125.9 MB | OK（50 格） |
| Qt6Quick | 140.0 MB | OK（50 格） |
| Qt6Qml | 141.2 MB | OK（50 格） |
| Qt6Pdf | 141.9 MB | OK（50 格） |

- **Windows 上四個都可以拿掉**，下載量少 26%。和 Linux 結論相反——Windows
  的多媒體外掛不依賴 Quick／Qml，所以**排除清單要分平台**，不能照抄。
- `opengl32sw.dll` 是「顯示卡驅動不支援 OpenGL 時」的軟體備援。Qt 6 在
  Windows 上預設用 Direct3D 11 畫影片，CI 機器（沒有獨立顯示卡）沒有它也
  照樣解出畫面；但**舊顯示卡或遠端桌面這類環境沒驗到**。第 1 項打包時先
  拿掉，README 的疑難排解留一條「畫面全黑 → 回報顯示卡型號」，真的遇到再
  放回來。
- 驗到的是「解得出畫格」，**沒驗到**聲音（CI 沒有音效裝置）與真的上螢幕
  （CI 是沒有顯示器的工作階段）。
- 這次 onefile 的牆上時間有兩次跳到 3.4、5.0 秒（前三次 2.45 秒左右），
  CI 機器的雜訊，不影響 onedir 的結論（五次都在 0.30～0.34 秒）。

作法定案：第 1 項在 `release.yml` 打包 Qt 版時，PyInstaller 跑完後刪掉
這四個檔（或用 `--exclude-module`／spec 的 `binaries` 過濾），**打包後照樣
用 `probe_clip.mp4` 播一次**確認沒刪壞，播不出來就讓工作流程失敗。

### 第 2 項第一階段：播放器面板＋字幕疊在真的畫面上（2026-09-27 開工）

為什麼是這一題：第 1 項做完了（剩下一次發版時確認），第 2 項是清單上「使用

這一階段只做：

- `subtitle/cuetime.py`（零 GUI 依賴）：給一個時間點，找出這一刻該顯示哪一句

**不在這一階段**：字幕樣式（字型、位置、顏色照 config 的樣式）套到疊加層；

### 第 2 項第二階段：疊加層套用字幕樣式，長得跟燒錄出來的一樣（2026-09-27 開工）

為什麼是這一題：第一階段的字幕是寫死的白字黑邊；要取代 Tk 的 Canvas 預覽，
預覽就得**跟燒錄結果一致**，否則使用者在預覽調好的樣式燒出來會不一樣。

調研（讀 `subtitle/exporter.py` 的 `cues_to_ass`，燒錄走這條）：

- 燒錄一律用 PlayRes 1920×1080 的 ASS，libass 依實際畫面等比縮放：字級、邊
  框寬度、邊距都以 1080 高為基準。
- **水平一律置中，`position_x` 燒錄時完全沒用到**；Tk 的 Canvas 預覽卻照
  `position_x` 擺——兩者本來就不一致。Qt 版照燒錄。
- 垂直：`position_y` ≥ 0.66 置底（字的底邊在 `position_y` 處）、≤ 0.33 置頂
  （字的頂邊距離上緣 `1 - position_y`）、中間則垂直置中；邊距最小 10。

這一階段只做：

- `subtitle/exporter.py` 新增 `burn_layout()`（零 GUI）：給樣式與畫面尺寸，算出
  燒錄時的字級、邊框、對齊與基準線；`cues_to_ass` 的對齊與邊距改用同一個函式
  算，**兩邊不可能各說各話**。
- 疊加層照它畫：字型、字級、文字色、邊框色與寬度、置頂／置中／置底、重點字
  上色。
- 找一格真的燒錄出來的畫面比對位置（ffmpeg＋libass），把差距記下來。

**不在這一階段**：逐字動態字幕（karaoke／word）預覽；在 Qt 版裡改樣式的介面。

**結果（2026-09-27 完成）**：

- `burn_layout()` 與 `cues_to_ass` 共用 `_ass_margin_v`／`_ass_alignment`，14 組樣式
  改寫前後 ASS 輸出逐字相同；另有測試守「`BURN_PLAY_RES` 等於 `cues_to_ass` 的預設
  解析度」，兩邊不會各改各的。
- **字級差了約 20%**：ASS 的 Fontsize 是整行高（ascent＋descent），Qt 的
  `setPixelSize` 是 em 大小；直接套用 Qt 的字會比燒出來的大兩成。`ass_font()`
  先量一次行高再依 `size² / 行高` 換算。
- **邊框要先畫**：`QGraphicsSimpleTextItem.setPen` 的描邊蓋在字上，白字會被黑
  邊吃掉一圈；改成自繪 `OutlinedText`：先描 2 倍寬的邊、再填字（libass 的邊框也
  是往外長）。
- **和真的燒錄比**：同一格畫面用 ffmpeg＋libass 燒一次、再用疊加層畫一次，量字的

### 第 3 項第一階段：`subtitle/waveform.py` 波形峰值（2026-09-28）

為什麼先做這一題：第 2 項的第三階段（逐字動態字幕預覽）是錦上添花；時間軸
（第 4 項）才是 3.0 的門面，它的兩個資料來源（波形、縮圖條）不先有，時間軸
就只能畫空殼。波形比縮圖簡單、而且剪輯最常看的是它，先做。

做了什麼（零 GUI 依賴）：

- ffmpeg 解成單聲道 16-bit PCM，取樣率 = 每秒格數 × 80（預設 100 格／秒 →
  8 kHz）；**串流讀取**，長片不會一次吃進記憶體。每格記 (最小, 最大)。
- `resample(peaks, start, end, columns)`：任何縮放倍率、任何可見範圍都從同一
  張峰值表合出來。拉遠時取最小的最小值、最大的最大值（**尖峰不會被平均
  掉**）；拉近到一欄不到一格時取所在格；片頭前、片尾後是 (0, 0)。
- 快取：`waveform_cache/`（與 `transcribe_cache/` 同層、同樣不入版控），鍵
  是路徑＋大小＋**修改時間（奈秒）**＋每秒格數；二進位格式（標頭＋小端序
  int16），損毀、截斷、舊版一律重算；先寫 `.tmp` 再換名，寫一半當掉也不會留
  下壞檔；解碼失敗不寫快取；上限 40 個、刪最舊的。
- 取消（`cancel()` 回 True 就殺掉 ffmpeg）與進度回報，給時間軸背景執行用。

實測（容器，4 核）：

| 項目 | 結果 |
|---|---|
| 5 分鐘音訊解碼＋算峰值 | 1.52 秒（其中 ffmpeg 解碼本身 1.55 秒——瓶頸在解碼，Python 那段與讀取重疊） |
| 峰值表大小（5 分鐘、100 格／秒） | 120 KB |
| 從快取讀回 | 0.1 ms |
| 合成 1600 欄（整段 5 分鐘） | 7.5 ms |

測試 `tests/test_waveform.py`：純計算；**真的解碼**一段「靜音—0.5 振幅正弦—
靜音」確認峰值落在對的格子、振幅與正負對稱；管線每次只給 333 位元組、音訊長
度不是整數格時結果仍與一次解完逐格相同；沒有音軌／檔案不存在；取消與進度；快
取命中不再呼叫 ffmpeg、**大小相同只改內容**也認得出來、損毀重算、失敗不寫快
取、刪最舊的。破壞探針 11 個，第一輪有 3 個沒抓到（尖峰剛好在欄的第一格、管線
讀取其實每次都給滿、改檔時大小也跟著變），補測資後全部抓到（其中「不檢查長
度」「範圍外取第 0 格」是以例外中止被抓到）。

**下一步（第二階段）**：`subtitle/filmstrip.py`：依時間軸縮放取一排縮圖（ffmpeg
一次抽多張、縮成小圖、帶快取），同樣零 GUI 依賴。之後第 4 項時間軸把兩者畫出
來。

### 第 3 項第二階段：`subtitle/filmstrip.py` 縮圖條（2026-09-28）

先量三種作法（5 分鐘 1280×720、30fps、每 2 秒一個關鍵影格，縮成 90px 高）：

| 作法 | 時間 | 結果 |
|---|---|---|
| 全解碼、`fps=1/2` 每 2 秒取一張 | 6.2 秒 | 150 張 |
| **只解關鍵影格**（`-skip_frame nokey`） | **1.1 秒** | 150 張、共 350～600 KB |
| 逐點 seek（每張一個 ffmpeg） | 每張約 0.1 秒 | 精準但張數多就慢 |

所以主路徑用「只解關鍵影格」，時間從最後一個濾鏡 `showinfo` 的 `pts_time` 讀；
另外處理兩種極端：

- **每一幀都是關鍵影格**：`select` 只留跟上一張至少隔 `min_interval`（1 秒）的，
  20 秒的片子 20 張而不是 600 張。
- **關鍵影格很疏**（螢幕錄影常見）：隔超過 `max_gap`（10 秒）的空檔（含最後
  一張到片尾）每 10 秒 seek 補抽一張，最多 120 張。60 秒、20 秒一個關鍵影格的
  片子：0／20／40 是關鍵影格，10／30／50 是補抽，0.7 秒。

JPEG 縮圖存 `filmstrip_cache/<鍵>/`＋`index.json`；鍵是路徑＋大小＋修改時間＋高
度＋間距。抽到 `<鍵>.tmp-<pid>`、完成才換名，失敗或取消就刪暫存。索引裡的檔名不
准帶路徑（不會讀到快取資料夾外面）；少一張圖、索引壞掉都重抽。上限 20 支影片。
`Filmstrip.slots(start, end, count)` 給時間軸每格最近的一張、片頭前片尾後留空。

**踩到的坑**：`media.probe_duration` 量不到時回傳保底值 60 秒，本來拿「等於 60」
當作量不到——結果一支真的 60 秒的測試片被當成片長未知、片尾的空檔沒補。改成自
己量、量不到回 0。

測試 `tests/test_filmstrip.py`：測資讓**畫面亮度 = 時間 × k**，每張縮圖的平均亮
度換回時間，驗「標的時間跟畫面內容對得上」——補抽的那幾張也是（如果補抽誤用
「只解關鍵影格」，畫面會是前一個關鍵影格的，時間標籤卻對，只看時間的測試抓不
到）。破壞探針 13 個，第一輪 2 個沒抓到（改檔測試連大小都變了、取消測試被補抽
階段的檢查接住），補測試後全部抓到。

另外把一支帶時間碼的測試片抽出來排成一列看過：標 0／10／20／30／40／50 的六張，
畫面上的時間碼就是 0／10／20／30／40／50。

**下一步（第 4 項第一階段）**：`gui_qt/timeline.py`：`QGraphicsView` 畫縮圖列、
波形、字幕塊與播放頭，能縮放、點一下跳到那個時間；接在②頁播放器下面，資料在
背景執行緒抽（用上面兩個模組的 cancel／progress）。

## 仍然不做的事（第 3 層，使用者選擇保留）

- **引入 C++ 剪輯引擎**（MLT 等）或自己寫 C/C++ 擴充。
- **專業調色**（色輪、曲線、示波器）與**專業混音台**（效果鏈、匯流排）。
  第 9 項的畫面調整是「基本款」，不往這個方向延伸。
- **外掛系統、第三方特效生態。**
- **關鍵影格動畫、去背、遮罩追蹤。**

這些不是永遠不做，是**使用者這次選擇不放掉第 3 層**；要改變，由使用者決定。

## 開發環境驗不到的東西（每一個 3.0 PR 都要照實列）

| 表面 | 原因 |
|---|---|
| 聲音與影音同步 | 容器沒有音效裝置 |

畫面解碼、跳轉、時間軸互動、版面在 `offscreen` 平台下**驗得到**，這一
半不能以「驗不到」帶過。
