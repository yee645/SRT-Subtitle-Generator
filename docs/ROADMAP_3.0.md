# SRT 字幕生成器 3.0 工作清單

這份文件定義 **3.0 的目標**。2.x 的工作清單仍在
[`docs/ROADMAP_2.0.md`](ROADMAP_2.0.md)，**它還沒做完，優先權仍然在它上面**；
本文件是等那邊收尾之後才開工的題目。

## 3.0 是什麼

使用者的原話（2026-09-23）：

> 「繼續開發，可繼續搜尋和制訂更新內容，並將 3.0 的目標訂定在，期望將本
> 軟體做成如 adobe premiere 等主流剪輯軟體的水準。」

## 使用者決定：底座的堅持放掉到第 2 層（2026-09-23，最高優先）

問過「要做成 Premiere 需要放掉哪些堅持」之後，列出了三層（每一層都以前
一層為前提），使用者的回答是：

> 「可以放到2」

也就是：

| 層 | 堅持 | 3.0 的狀態 |
|---|---|---|
| 1 | **零第三方 Python 套件**（目前 exe 只打包 `openai`、`zhconv`、`sv_ttk`） | **放掉**：可以用 PySide6、numpy 等套件 |
| 2 | **Tkinter 介面** | **放掉**：3.0 的介面改用 **Qt（PySide6）** |
| 3 | 純 Python、一個人夜間增量開發的規模（不引入 C++ 剪輯引擎如 MLT） | **保留**，不放 |

**適用範圍要講清楚，否則之後每一晚都會搞混**：

* 放掉的只有 **3.0 這條線**（新的 Qt 介面與它需要的核心）。**2.x 的 Tk
  介面照舊遵守零依賴、`ttk.*` 等所有既有規則**，直到它被 Qt 版取代為止。
* **這些照舊，不因這個決定改變**：
  - `subtitle/` 核心模組**零 GUI 依賴**（這條正是換介面時最值錢的一條
    ——57 個模組一個都不用重寫）
  - 隱私規則（剪貼簿、螢幕擷取預設關閉；「寧可漏翻、不可誤送」）
  - 先調研再動手；新測試要先證明在壞掉的程式碼上會失敗
  - Whisper 模型檔與 pytorch.org 被出口網路政策擋 403，**不要嘗試繞過**
  - 發佈政策（次版轉正要使用者拍板、四個產出物）
* **新套件的門檻**：每加一個都要在 PR 寫明「為什麼標準函式庫或既有套件不
  夠」與「打包後增加多少體積」。放掉零依賴不等於什麼都可以加。

## 換成 Qt 之後的實測（2026-09-23）

這一節取代原本「Tkinter 底座的硬限制」那張表——那張表的結論在換底座之後
大半不成立了。

**環境**：PySide6 6.11.2（LGPL-3.0），開發容器、**沒有 GPU**、4 核
CPU、`QT_QPA_PLATFORM=offscreen`。Qt Multimedia 自報使用內建的
**FFmpeg 7.1.5（LGPL）**做解碼。

| 量什麼 | Tkinter＋ffmpeg 子行程（舊） | Qt Multimedia（新） |
|---|---|---|
| 720p30 連續播放 | 上限約 8~12 fps、無聲 | **30.0 fps**（滿速） |
| 1080p30 連續播放 | ——（沒量） | **30.0 fps**（滿速） |
| 1080p60 連續播放 | —— | **60.1 fps**（滿速） |
| 720p 跳到任意位置（6 個點） | 81~130 ms | **3~112 ms** |
| 1080p 跳到任意位置（6 個點） | —— | **86~195 ms** |

幾點照實說明：

1. **聲音沒驗到。** 容器裡沒有音效裝置（`QMediaDevices.audioOutputs()`
   回傳空清單、PulseAudio 連不上）。所以「影音同步」**一次都沒驗過**，
   只驗到畫面解碼。這要在使用者的 Windows 上驗。
2. **1080p 的跳轉比 720p 慢不少**，最慢接近 0.2 秒。測試片用的是 x264
   預設的關鍵影格間距（約 8 秒）；真實相機素材的間距各家不同，可能更好也
   可能更差。拖曳時間軸要順，**就需要代理檔**（見工作清單），這也是
   Premiere 自己的解法。
3. **量的是沒有 GPU 的容器**，純 CPU 解碼。使用者的電腦多半有 GPU，Qt
   在 Windows 上可能自動用硬體解碼——**這一點沒驗過，不要當成已知**。
4. 1080p60 那一組第一次量的時候，跳轉點超出了片長（20 秒的片子跳到 150
   秒會被夾到片尾），數字無效，已按片長比例重量。上表是重量後的數字。

**打包體積**：PySide6 完整安裝 650 MB（含所有附加模組）；實際需要的部分
（Core、Gui、Widgets、Multimedia、MultimediaWidgets、FFmpeg 函式庫、
平台外掛、shiboken6）在 Linux 上合計約 **139 MB（未壓縮）**。Windows 版
的實際 exe 大小**沒有量**——要等 CI 在 Windows runner 上真的打包一次才知
道（見工作清單第 0 項）。

**先前「用 mpv 外部執行檔嵌進 Tkinter」的想法不必做了**：那是為了在零依
賴下取得真播放的繞路；Qt Multimedia 本身就帶 FFmpeg，直接解決。

## 差距盤點（沒有因為換底座而改變）

**已經有了，而且是 Premiere 沒有的**：逐字稿審片（`subtitle/review.py`）、
全片停頓自動跳剪（`subtitle/jumpcut.py`）、重複拍攝偵測與剪除
（`subtitle/retakes.py`）、短影音切片（`subtitle/shorts.py`）、字幕樣式
與燒錄、多語字幕包、十幾項上架前健檢、螢幕畫面翻譯。**3.0 不能為了追像
Premiere 而把它們稀釋掉**——它們是使用者選這個工具而不是 Premiere 的理
由。

**缺的**：

1. **所有的剪都是盲剪。** `jumpcut.py` 算出剪點之後直接輸出成片，使用者
   從頭到尾看不到剪在哪裡。`subtitle/review.py` 的說明自己寫著匯出 EDL
   「匯入 Premiere / DaVinci Resolve 繼續精剪」——那行字就是差距的位置。
2. **沒有播放器、沒有時間軸。** `gui/` 至今沒用過一次 `PhotoImage`；
   `gui/preview_panel.py` 的「預覽」是用 Canvas 畫出來的假畫面。
3. **沒有轉場**（全庫 `xfade` 零命中）。
4. **不能拼多支素材**，所有流程都假設一支輸入影片。
5. **波形只是輸出物**（`audiovis.py` 算成影片），編輯時看不到。
6. **沒有多軌**（B-roll 疊在主軌上、背景音樂獨立一軌）。

## 3.0 的目標

> **一個以時間軸為中心、能即時播放的剪輯介面，而本工具原有的自動化——
> 審片、跳剪、剪重複、切短影音、字幕、翻譯、健檢——全部直接在那條時間軸
> 上發生、看得見、改得動。**

具體承諾：

* **真的能播**：影片與聲音同步播放、拖曳即時換畫面（1080p 以上靠代理檔）。
* **剪完之前看得到剪在哪裡，而且改得動**。
* **多軌**：主影片軌、疊加軌（B-roll／圖片）、字幕軌、音樂軌。
* **最基本的剪輯動作**：切割、刪除、移動、修剪邊緣、轉場、畫面調整，
  全部可預覽。

## 遷移策略：兩套介面並行，逐頁搬

換掉介面工具包沒辦法「一晚改一點」地在原地改——Tk 與 Qt 無法共存於同一
個視窗。但**可以共存於同一個程式**：

1. 新介面放在 **`gui_qt/`**，與既有的 `gui/` 並列；兩者都只呼叫
   `subtitle/` 核心，**共用同一份設定檔**。
2. 入口加一個開關（例如 `--qt` 或設定項），**Tk 版維持預設**。Qt 版以
   「3.0 預覽版」的身分跟著 2.x 一起出貨，想試的人自己打開。
3. 每一晚搬一頁或做一個新元件，**每一步都能單獨出貨、單獨回退**——既有
   規則因此不必破例。
4. `2.3.0` 之後，**Tk 版只修錯、不再加新功能**，新功能一律只做在 Qt 版，
   避免兩套一起長。
5. Qt 版追上 Tk 版的全部功能之後，才把預設切過去；那一版就是 `3.0.0`。
   Tk 版在 `3.0.0` 之後的某一版移除（屆時另外決定）。

### 第 0 項調研結果（2026-09-26）

量測工具：`research/qt_probe/`（探針＋量測腳本）與
`.github/workflows/qt-probe.yml`（windows-latest，只量測、不發佈，只在動到
這兩處的 PR 觸發）。探針載入 3.0 會用到的 QtWidgets／QtMultimedia／
QtMultimediaWidgets，建一個帶影片元件與播放器的主視窗，顯示後自報時間並
自行關閉。

**已確認（讀套件本身，不是憑記憶）**：

- **QtMultimedia／QtMultimediaWidgets 在 `PySide6-Addons`，不在
  `PySide6-Essentials`。** 只裝精簡版不夠，打包環境要裝完整的 `PySide6`。
- **授權**：`PySide6`、`PySide6-Essentials`、`PySide6-Addons`、`shiboken6`
  6.11.2 的套件中繼資料都寫 `LGPL-3.0-only OR GPL-2.0-only OR
  GPL-3.0-only`，另有商業授權。Qt 自帶的 FFmpeg 在啟動時自報「FFmpeg
  version 7.1.5 LGPL version 2.1 or later」。
- **wheel 裡沒有任何授權全文**（dist-info 只有 METADATA，沒有 LICENSE 檔），
  所以 PyInstaller 打包出來的成品**一個授權檔都沒有**（本機 onefile、onedir
  兩種都確認過）。要守 LGPL，至少得自己把授權全文與「用了哪些 LGPL 元件、
  原始碼在哪」的說明放進成品——這件事**不會自動發生**。
- LGPL 條文細節（onefile 算不算讓使用者「能替換函式庫」、要附原始碼還是附
  取得方式）**這次沒有核對原文**：gnu.org 被這個環境的出口政策擋下，沒有
  繞過。在核對原文之前，**onedir（Qt 的 DLL 是分開的檔案，可以直接替換）
  是比較不會出錯的選擇**；是否真的必要留待核對後定案。

**本機 Linux 參考數字**（不是 Windows，只看量級；Linux 上 PyInstaller 會把
Qt 函式庫複製兩份，onedir 偏大）：

| | onefile | onedir |
|---|---|---|
| 大小 | 79 MB | 321 MB（379 檔，zip 後 126 MB） |
| 啟動牆上時間（第一次／其餘中位數） | 1.47／1.37 秒（多半是解壓） | 0.22／0.22 秒 |

對照：目前 2.x 的 Tk 版 exe 是 23.7 MB（onefile）。

**Windows 實測**（PR #146 的 CI，windows-latest、Python 3.11.9、PySide6
6.11.2，各跑 5 次；run 36208465917）：

| | onefile | onedir |
|---|---|---|
| 大小 | **58.2 MB** | 146.5 MB（245 檔），**zip 後 58.4 MB** |
| 啟動牆上時間（第一次） | 2.69 秒 | 0.31 秒 |
| 啟動牆上時間（其餘中位數） | **2.65 秒** | **0.29 秒** |
| 探針自報：Python 開始到視窗顯示 | 0.11 秒 | 0.09 秒 |
| 對照：2.x Tk 版 exe | 23.7 MB（onefile） | — |

- **onefile 每次啟動都要多等 2.5 秒左右**——不是只有第一次。onefile 每次都
  把 58 MB 解壓到暫存資料夾，五次都落在 2.5～2.7 秒；onedir 五次都在 0.3 秒
  上下。探針自報的時間兩者幾乎一樣，差的全是解壓。
- **多媒體後端有被正確打包**：`ffmpegmediaplugin.dll` 與
  `windowsmediaplugin.dll` 都在，FFmpeg 的 avcodec／avformat／avutil／
  swresample／swscale 五個 DLL 都在；播放器對不存在的檔案回報
  `ResourceError`（後端正常運作時的回應）。
- **授權檔：Windows 上同樣一個都沒有。**
- **有明顯可以瘦身的地方**（onedir 最大的檔）：`opengl32sw.dll` 20.6 MB（沒有
  顯示卡驅動時的軟體 OpenGL 備援）、`Qt6Quick.dll` 6.6 MB、`Qt6Qml.dll`
  5.3 MB、`Qt6Pdf.dll` 4.6 MB——探針完全沒用到 Quick／QML／PDF，是
  PyInstaller 的多媒體掛鉤一起拉進來的。能不能排除要實測（排除後播放器還
  能不能動），這四個加起來約 37 MB。
- CI 機器沒有音效裝置（`audio_outputs` 為 0），聲音仍然沒驗到。

**這些數字帶出來的決定（第 1 項開工前要定案）**：

1. **傾向 onedir**：啟動快九倍，zip 後下載量與 onefile 相同，Qt 的 DLL 是分開
   的檔案、使用者可以直接替換（對 LGPL 也比較穩妥，見上）。
2. **代價是自動更新要改**：`updater.py` 現在下載的是單一
   `SRT-Subtitle-Generator.exe` 並就地替換自己；onedir 是一整個資料夾，要改
   成下載 zip、解到旁邊、下次啟動時切換。Qt 版以預覽身分跟 2.x 一起出貨時，
   **Tk 版的單一 exe 與自動更新維持不變**，Qt 版另外一個 zip，這個問題可以
   延後到切換預設（3.0.0）前再解。
3. 授權全文與元件說明要自己放進成品（`release.yml` 加一步），條文細節待核對
   原文。

**第 0 項剩下的**：影音同步（需要有音效裝置的機器，CI 做不到）、LGPL 原文
核對、上面四個大檔能否排除。

### 螢幕畫面翻譯搬到 Qt 時的參考（2026-09-23 實測）

在 Xvfb、`xcb` 平台下：Qt 的 `QScreen.grabWindow` 截一塊 560x84 的畫面
**2.1 ms**；存成 PNG 直接交給現有的 `subtitle/ocrengine.py`，**一行都沒
改**，辨識出 `Select this line to translate`（一字不差、信心值 96.4、
`verdict: ok`、0.2 秒）。也就是說 2.x 做的核心層搬過去可以原封沿用，要
重寫的只有畫面。

| 部分 | 搬到 Qt 時的作法 | 依據 |
|---|---|---|
| OCR 引擎、排版還原、tesseract 一鍵安裝、翻譯、生字本 | **原封沿用** `subtitle/` 的模組 | 上面的實測 |
| 截圖 | 可改用 `QScreen.grabWindow`，一套程式碼三平台 | Linux 實測可用；**Windows／macOS 未驗**，`subtitle/screencap.py` 保留當退路，「整塊同一個顏色」的判斷照舊要做 |
| 框選覆蓋層 | 改用 Qt 的無邊框透明視窗 | 同樣要在 Windows 上驗 |
| 朗讀 | `QtTextToSpeech` 與 `subtitle/speech.py` 二選一，**待調研** | 這台只列出 `speechd` 與 `mock`；Windows 上的引擎沒驗過 |
| 全域熱鍵 | 沿用 `subtitle/hotkey.py`；Windows 那段改在 Qt 的原生事件過濾器接 `WM_HOTKEY` | Qt 沒有全域熱鍵 API |

## 仍然不做的事（第 3 層，使用者選擇保留）

- **引入 C++ 剪輯引擎**（MLT 等）或自己寫 C/C++ 擴充。
- **專業調色**（色輪、曲線、示波器）與**專業混音台**（效果鏈、匯流排）。
  第 9 項的畫面調整是「基本款」，不往這個方向延伸。
- **外掛系統、第三方特效生態。**
- **關鍵影格動畫、去背、遮罩追蹤。**

這些不是永遠不做，是**使用者這次選擇不放掉第 3 層**；要改變，由使用者決定。

## 開發環境驗不到的東西（每一個 3.0 PR 都要照實列）

| 表面 | 原因 |
|---|---|
| 聲音與影音同步 | 容器沒有音效裝置 |
| GPU／硬體解碼 | 容器沒有 GPU |
| Windows 上的實際外觀、高 DPI、打包後體積與啟動時間 | 容器不是 Windows（體積可由 CI 量） |

畫面解碼、跳轉、時間軸互動、版面在 `offscreen` 平台下**驗得到**，這一
半不能以「驗不到」帶過。
