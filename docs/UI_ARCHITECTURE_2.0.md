## A. 組織原則：按「工作流程階段」

**定案：2.0 按工作流程階段組織——素材與剪輯 → 字幕 → 健檢 → 輸出與發
佈，四個階段做成主視窗的四個頁籤。**

### 為什麼選「流程階段」

1. **這個領域本身就有硬性順序，而且做錯順序會產出壞成品。**稽核 1.2 節
   與更早的 v1.47 調研都指出：先跳剪再上字幕（否則時間軸錯位）、先燒字
   幕再套片頭（否則字幕整體位移）、響度正規化只做最後一次（否則重複拉
   伸）——這些順序知識現在**全部由使用者的腦子扛**，介面零引導，做錯的
   產物看起來還是「完成了」。只有按階段組織的介面能把順序知識編進版面
   本身：頁籤由左到右就是正確順序，順序錯誤最常見的形態（在錯的階段做
   對的事）會直接變得「不順手」而被自然阻止。
2. **它直接解決稽核抓到的最大結構問題：檔案交接靠剪貼簿。**稽核 ④ 指
   出審片產物要人工貼到健檢、粗剪檔要人工選回主視窗。階段式組織天然定
   義了「每一階段吃上一階段的產出」——一條共用的「目前影片／字幕」狀
   態列（見 B.1）就能把 4 次人工交接全部消掉。目的式組織裡沒有「上一
   步」這個概念，交接問題無從解起。
3. **43–46 次點擊的主因是「回字形動線」**：使用者在功能選單裡進進出出
   17–19 個視窗，每個視窗重複「開窗→按開始→讀報告→關窗」。階段式把
   同一階段的所有事攤平在同一頁籤裡，動線變成單向四步。
4. **與定位吻合**：README 與稽核都把這工具描述成 YouTuber 的生產線
   （拿到素材→可上傳成品）。生產線工具用生產線組織，是最不需要學習的
   隱喻。

### 為什麼放棄「使用者當下的目的」

目的式（首頁擺「我要上字幕」「我要檢查」「我要剪片」「我要發佈」等目
的入口，點進去進各自的工作區）曾認真考慮過，放棄的理由：

1. **它就是 v1.x 的現況，只是換了皮。**現在的工具列 11 顆按鈕＋21 個對
   話框，本質上就是一套目的式入口（「我要檢查封面」→封面健檢）。稽核
   證明這個組織的病根不是入口名字不好，而是**目的之間互不相認**：每個
   目的自帶檔案選擇、自帶輸出、彼此靠剪貼簿交接。把目的入口重排得更漂
   亮，43 次點擊裡屬於交接與重複開窗的那 20 幾次一次都省不掉。
2. **同一份狀態被多個目的共用，目的式必然造成重複。**字幕清單同時是
   「上字幕」「翻譯」「健檢」「跳剪」四個目的的操作對象；影片檔同時是
   六個目的的對象。按目的切分就得在每個目的的工作區重複擺放同一份狀
   態（v1.x 的三個輸出面、兩次轉錄正是這樣長出來的）。按階段切分則是
   狀態流經階段，每份狀態只有一個家。
3. 目的式的唯一優勢是「單點任務直達」（只想檢查封面的人不必理解流
   程）。這個優勢在階段式裡用兩個手段補回：**四個頁籤隨時可直接點進
   任何一階**（不是精靈/wizard，沒有「必須先完成上一步」的鎖），且各
   階段的檢查對象欄位都可獨立瀏覽選檔、不強制沿用流程狀態。代價是單
   點任務多一次頁籤點擊，換掉的是整條流程 20+ 次點擊與 4 次剪貼簿交
   接——這個交換值得。

**一句話：選流程階段，因為這個工具的痛不在「找不到功能」而在「功能之
間不相認」；目的式只能治前者，階段式兩者都治。**

## B. 新資訊架構與主視窗版面

### B.1 主視窗骨架（原型實測通過）

```
1400x800（預設，minsize 維持 980x560）
┌──────────────────────────────────────────────────────────────┐
│ 頂列(~40px)：SRT 字幕生成器          [即時查譯] [主題]        │ 常駐
│ 工作檔案列(~34px)：目前影片: xxx_粗剪.mp4 [瀏覽...]           │ 常駐
│                    字幕: 42 句（未存檔）                      │
├─[① 素材與剪輯]─[② 字幕]─[③ 健檢中心]─[④ 輸出與發佈]──────────┤ Notebook
│                                                              │
│                （各階段內容，見 B.3–B.6）                     │ 高~645px
│                                                              │
├──────────────────────────────────────────────────────────────┤
│ 狀態列(~28px)：就緒                                           │ 常駐
└──────────────────────────────────────────────────────────────┘
```

**工作檔案列是整個 2.0 的樞紐**：一份跨階段共用的工作狀態（目前影片路
徑＋其世代鏈、字幕清單、發佈文字、封面圖），全部是 `SrtApp` 層的記憶
體狀態＋現有 config 記憶機制，**不動 `subtitle/` 任何公開介面**。規則：

- 任何會產出新影片檔的動作（粗剪、修復版、燒錄、配樂、套版、跳剪）完
  成時，預設把產物**設為目前影片**（完成訊息裡附勾選「☑ 設為目前影
  片」，預設勾），世代鏈顯示在檔名後（如「第 3 代：套版」）。
- 任何對話框開啟時預設吃目前影片與目前字幕，不再各自從零選檔（稽核
  1.1 節「帶入規則不一致」就此統一）。
- 這條機制取代了稽核 1.2 節裡 4 次「手動把上一步輸出選給下一步」。

### B.2 折疊線問題的解法與實測證據

解法：**把「1240px 高的設定長表單」轉九十度**——設定收進左側 330px 窄
欄（自帶垂直捲動），動作列與字幕清單放中欄且永遠可見，外觀（預覽＋樣
式）收右欄固定 420px。主動作不再「在表單的結尾」，而是「在清單的頂上」。

原型實測（1400x800、deiconify 後量測、深淺兩主題同值）：

| 元件 | y | 下緣 | 右緣 | 對照 v1.x |
|---|---|---|---|---|
| 開始生成字幕（Accent 主鈕） | **126** | 156 | 465 | y=826（畫面外） |
| 字幕清單 | **162** | 730（可見 19 列） | 941 | y=889（畫面外） |
| 清單編輯列 | 736 | 766 | 941 | y=910（畫面外） |
| 樣式面板 | 397 | 766 | **1381 < 1400** | 右緣溢出被裁 |
| 預覽 | 183 | 383 | 1367 | — |

「要做的動作」（開始生成，y=126）與「做出來的結果」（字幕清單，y=162
起）同屏可見；右欄無水平裁切（v1.x 的「刪除」變「刪」問題連根消失，
樣式面板以 420px 預算緊湊重排，原型逐控件驗證過放得下）。生成完成的
回饋出現在動作列旁的狀態文字＋清單本身，視野內必有變化。

### B.3 階段②「字幕」＝首頁（預設頁籤）

```
├─左欄 330px（ScrollableFrame，只捲設定）──┬─中欄 flex(~584px)────────┬─右欄 420px────────────┐
│ 來源與模式                               │ [開始生成字幕]（Accent）  │ 樣式組合: [預設▾]      │
│  ◉ 語音轉寫（模式一）                    │ [完成輸出（依輸出設定）]  │  [另存][更新][刪除]    │
│  ◯ 文字稿對齊（模式二）                  │ ▓▓▓▓ 進度＋狀態          │ ┌─即時字幕預覽───────┐ │
│  ◯ 手動輸入（模式三）                    │ ┌─字幕清單（19 列可見）─┐ │ │  392x200 畫布      │ │
│  [匯入既有字幕檔...]                     │ │ # 開始 結束 文字      │ │ │ （樣式調整立即反映）│ │
│ 轉寫設定（模式一才顯示）                 │ │ …雙擊編輯…            │ │ └────────────────────┘ │
│  模型/語言/API 金鑰/本地 Python/提示     │ │                       │ │ 字幕視覺調整           │
│ 斷句設定                                 │ └───────────────────────┘ │  位置 XY／快捷位置     │
│ 文字稿貼上框（模式二才顯示）             │ [新增][編輯][刪除][上移]  │  字型／字級／邊框      │
│                                          │ [下移][清空]│[尋找取代]  │  顏色×3／動態效果      │
│                                          │ [翻譯字幕]                │                        │
└──────────────────────────────────────────┴──────────────────────────┴────────────────────────┘
```

要點：

- **「匯入字幕」從清單編輯列移到左欄「來源與模式」**：匯入既有 SRT 是
  一種「來源」，不是一種「清單操作」；順帶讓編輯列從 10 顆縮到 8 顆，
  在 584px 中欄單列放得下（原型逐鈕驗證 mapped=1）。
- 「字幕健檢」離開編輯列（移往階段③），終結「健檢與上移下移同視覺層
  級」的問題（稽核 ③）。
- 模式 radio 文字改為「動詞短語（模式 N）」，舊編號括號保留一版（見 D）。
- 「樣式組合」列移到右欄頂端、緊貼預覽與調整面板，表達「組合＝這一整
  欄的存檔」的關係（稽核 ② 尾項）；原型實測右欄總高 766 恰好收在頁面
  內。
- 「完成輸出」＝執行階段④已設定好的輸出組合（匯出格式＋燒錄＋正規
  化），是舊「一鍵完成」的後半段，隨時可按——校對完再按它，旗艦捷徑
  與品質流程從此不互斥（詳見 C-3）。
- 左欄的「自動化輸出」區整個移走（進階段④），左欄只剩生成前設定——
  原型實測左欄內容全部可見甚至不需捲動。

### B.4 階段①「素材與剪輯」

生成字幕之前對素材做的事，三組卡片（原型 `proto_src_*.png`）：

- **審片與粗剪**：〔開啟審片助手〕——ReviewWindow 保留為獨立視窗（它
  是真正的第二工作台，1207 行不值得硬塞進頁籤），但輸出的粗剪／精彩合
  輯完成時自動設為「目前影片」，回到階段②即接續，不再手動選檔。
- **自動修剪**：〔剪停頓（依字幕）〕〔剪重複片段〕——即現在藏在「匯
  出與燒錄」深處 y=1180 的兩顆（稽核 ③）；改名消除與審片粗剪的同名混
  淆（稽核 ②）。長期合併為單一「自動修剪」窗（C-6）。
- **素材準備**：〔音訊轉影片（波形／頻譜）〕。

### B.5 階段③「健檢中心」

**直接採用稽核 2.2 節的整併方案**（該方案已把可行性、`subtitle/` 零改
動、修復動作沿用都論證過，不重複），差別只有一點：**它不是 Toplevel，
而是主視窗的頁籤**（原型 `proto_chk_*.png` 驗證同一結構放進頁籤放得
下）。結構照抄 2.2：檢查對象區（全選填、填什麼檢什麼；影片與字幕預設
沿用工作檔案列）→ 勾選要跑的檢查（門檻收進 ⚙）→ 單一分級報告
（Treeview）→ 選取發現＋〔修復此項〕。20 項檢查、8 個既有修復動作、
termcheck 的 `apply_term_fixes` 首次接上 GUI。

修復產出新檔案時同樣走「設為目前影片」機制，修完的重燒提醒由報告列自
帶（「已修音訊→記得重燒字幕」的 advice 直接附〔前往輸出〕）。

### B.6 階段④「輸出與發佈」

四組卡片（原型 `proto_out_*.png`），**三個輸出面在此收成一個**（稽核 ④）：

- **字幕檔匯出**：SRT／VTT／ASS／TXT 四顆（自「匯出與燒錄」移入）。
- **影片輸出**：〔燒錄字幕影片〕＋〔輸出設定⚙〕。輸出設定＝舊「自動化
  輸出（一鍵完成用）」整區（格式勾選、燒錄、響度正規化、輸出資料夾），
  存起來就是「完成輸出」按鈕執行的組合。
- **成品加工**：〔配樂助手〕〔品牌套版〕（保留為對話框，入口移此；預
  設吃目前影片）。卡片說明文字直接寫建議順序：「燒錄→配樂→套版，響
  度正規化留到最後一步」——順序知識首次進入介面。
- **發佈資料**：章節／標題／說明欄／標籤／封面圖的編輯欄位＋〔由審片
  結果帶入〕＋〔送健檢〕。審片助手產生的發佈包自動寫進這裡（斷鏈修
  復），〔送健檢〕把這些欄位填進階段③的對象區。

## C. 砍掉與合併清單（定案）

> 原則：**砍入口不砍能力**。以下每一條「退役」都指視窗/按鈕消失，其檢
> 查與修復邏輯（`subtitle/`）原樣保留並在新入口可達。

1. **砍七個健檢視窗，只留一個健檢中心**（audiocheck、subtitle_check、
   preflight、publishcheck、thumbcheck、chapter、series 七窗退役）。
   理由：稽核 2.1 實證「上片前健檢」5/5 被總體檢重跑、「字幕健檢」4/6
   重疊、9 項檢查照直覺走會跑兩遍（畫面類每次完整解碼）；「健檢 vs 總
   體檢」命名雙胞胎隨之消失。風險與緩解照稽核 2.2 的取捨表（單點檢查
   多一步認知→留空即略過；系列一致性彆扭→保留獨立窗退路）。
2. **砍「上片前健檢」「上片前總體檢」兩個名字**——隨 C-1 消滅，不另
   起類似名。健檢中心報告內的分組標題沿用使用者已認得的舊名（「字幕健
   檢」「發佈」「封面」…），修復指引不再出現「請到某某視窗」。
3. **砍「一鍵完成」按鈕，拆成兩半**：前半＝〔開始生成字幕〕，後半＝
   〔完成輸出（依輸出設定）〕，兩顆並排、可分開按。校對者：生成→改字
   →完成輸出；不在乎校對者：連按兩顆，效果等同舊一鍵完成。理由：稽核
   1.2 實證舊按鈕「生成後直接匯出＋燒錄、不留校對機會」，旗艦捷徑與品
   質流程互斥——這是把錯字燒進影片的設計。**多檔批次是例外**：工作檔
   案列選多檔時動作列出現〔批次一鍵完成〕，行為與舊按鈕一致（批次本
   來就不會逐支校對）。風險：老用戶找肌肉記憶的「一鍵完成」→見 D。
4. **併三個輸出面為一個**（稽核 ④）：主視窗「匯出與燒錄」＋「自動化輸
   出」→階段④單一輸出區；審片助手「輸出」區瘦身為剪輯輸出（粗剪/合
   輯/EDL/CSV/短片），發佈類產出改為自動流入階段④。「同一個輸出 SRT
   出現三處、行為各不同」終結。
5. **砍主視窗工具列**（11 顆 3 列）→4 頁籤＋頂列 2 顆。理由：稽核 ①③
   ——工具列是「按加入版本排序」的功能堆，寬度不一、欄位錯位，且它的
   存在讓每個新功能都傾向再開一個新對話框。
6. **併「剪停頓」＋「剪重複片段」為單一「自動修剪」對話框**（兩個偵測
   器分頁共用「偵測→勾選→剪除輸出」骨架與輸出設定）。理由：同對象
   （目前影片＋字幕）、同節奏、同輸出模式；jumpcut_dialog 296 行 +
   retakes_dialog 299 行高度同構。**排最後、優先度低**——這是純化簡，
   不擋任何其他步驟；若時程緊可不做，只完成入口搬遷與改名。
7. **砍清單編輯列的「字幕健檢」「匯入字幕」兩顆**：前者移階段③、後者
   移左欄來源區（匯入是來源不是清單操作）。10 顆→8 顆，編輯列在中欄
   單列放得下（原型實測）。
8. **補洞（不是砍，順勢做）**：termcheck 的 `apply_term_fixes` 接上健
   檢中心（`subtitle/` 已寫好、GUI 從未接，稽核 ③）；片尾空間/工商揭
   露/術語/檔名四項首次有可單獨勾選的入口。

**明確不砍的**：審片助手整體（它是第二工作台，砍了能力就沒了）；配樂
／品牌／音訊轉影片三個對話框（對象與參數各異，合併無收益）；三種運作
模式；即時查譯。

## D. 遷移策略

1. **名字能不動就不動**：審片助手、配樂助手、品牌套版、翻譯字幕、尋找
   取代、一鍵完成（批次版沿用原名「批次一鍵完成」）、開始生成字幕全部
   保留原名。改名的只有：三個健檢傘名→「健檢中心」、「自動跳剪停頓」
   →「剪停頓（依字幕）」、「重複片段偵測」→「剪重複片段」、「音訊轉
   影片」→補副標。模式 radio 改為「語音轉寫（模式一）」形式，**舊編號
   括號保留至 2.0.0 之後一版再摘除**。
2. **一次性導覽（只做一張，不做多步 tour）**：頁籤版（v1.53）首次啟動
   彈出「新版介面速覽」對話框：一張 4 欄對照表「你以前按的 → 現在在哪
   個階段」，涵蓋全部 11 顆舊工具列鈕與匯出區；〔知道了〕＋「☑ 不再顯
   示」（config 記憶）。之後常駐在頂列「說明」下的「功能去哪了？」隨時
   可再開。不做逐步高亮式導覽——Tkinter 做這個成本高且干擾大。
3. **過渡期軟著陸**：v1.50–1.52 每一版只動一塊（見 E），工具列按鈕是
   逐版減少而不是一夜消失；健檢中心上線的那版，被併掉的舊按鈕原位保留
   一版、點擊即開健檢中心並以狀態列訊息說明「已整併至健檢中心」，下一
   版才移除按鈕。
4. **設定零遷移**：config.json 44 個區塊一個不動——所有門檻、樣式組
   合、記憶欄位由新介面原樣讀寫（健檢中心的 ⚙ 讀的就是舊對話框寫的同
   一批 `resolve_*_settings` 區塊）。使用者調過的門檻在新版全部生效。
5. **文件**：README 加「1.x → 2.0 對照表」章節；CHANGELOG 每版寫明
   「本版移動了什麼、去哪找」。

## F. 誠實的未定案疑慮（按沒把握程度排序）

1. **審片助手的長期定位**（最沒把握）。本設計讓它保留為獨立視窗、靠
   「自動流入」修斷鏈——這治了交接，沒治「兩個工作台各自轉錄同一支影
   片」的重複（transcribe_cache 只是緩解）。徹底解法是把審片分段做成階
   段①的內嵌內容、與階段②共用轉錄結果，但那是 1207 行的大改，且審片
   的時間軸 UI 需要大面積，塞進頁籤可能兩邊都做壞。**建議 2.0.0 前不
   動，蒐集自動流入上線後的實際痛感再決定。**
2. **「完成輸出」的命名與心智**：老用戶找「一鍵完成」找不到的期間會有
   困惑；「完成輸出（依輸出設定）」是否足夠自明也未經真人驗證。退路：
   把按鈕文字改回「一鍵完成（輸出目前字幕）」。
3. **系列一致性塞進健檢中心的彆扭度**：稽核已預留退路（保留獨立窗），
   維持該退路。
4. 四頁籤對「只匯出 SRT」極簡用戶多了一次切換；靠「完成輸出」留在階段
   ②緩解，但未實測真人動線。
5. 原型未做視窗縮到 minsize 980x560 的退化行為（三欄在 980 寬要有欄寬
   讓步規則，實作時要補：右欄先折疊、左欄可收合）。
