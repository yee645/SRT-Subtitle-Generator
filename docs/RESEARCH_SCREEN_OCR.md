# 螢幕畫面翻譯：可行性調研

對應 `docs/ROADMAP_2.0.md` 第 9 項。使用者 2026-09-18 指示「先做調研再動
手」，這份是調研結論。**本輪沒有動 `APP_VERSION`、沒有發版。**

---

## 結論先講

**建議做，而且先做第一階段：熱鍵框選一塊畫面 → OCR → 翻譯 → 朗讀／複製。**

比原本設想更好的一點是實測之後才看清楚的：**OCR 應該走本地引擎
（tesseract，比照 ffmpeg 一鍵安裝），不要走 vision 模型 API。** 實測下
來本地 OCR 在 12 個難例裡有 10 個字元錯誤率 ≤ 5%、單次 0.2 秒、不用錢、
而且**畫面不必離開這台電腦**——只有辨識出來的那段文字才會送去翻譯。這
一條同時解掉三件事：費用、延遲、隱私。

**「連續即時翻譯」仍然不建議做**，理由在下面第 5 節，和調研前的判斷一
致，沒有因為數字漂亮就改口。

---

## 1. 最大的風險：這個功能有一半我驗不到

**先講這一段，因為它比下面任何數字都重要。**

這個功能幾乎整包都是 Windows 專屬表面，而開發環境是 Linux 容器。可以離
線測的只有「拿到圖之後」那一半；「怎麼拿到圖、怎麼讓使用者框、怎麼被叫
起來、怎麼唸出來」全部驗不到。v1.50.0 就是在驗證不足的情況下轉正，把一
顆被裁切的按鈕推給了使用者。

| 項目 | 狀態 | 失敗時的退路（實作時必須先寫好這個，不是寫好功能再說） |
|---|---|---|
| 螢幕擷取（`ctypes` + GDI `BitBlt`） | **未實測** | 擷取回來全黑或例外時，明確告訴使用者「這個畫面抓不到（可能是全螢幕獨佔模式的遊戲），請改成視窗化或無邊框」，而不是送一張黑圖去 OCR |
| 獨佔全螢幕的遊戲 | **未實測，且預期抓不到** | 同上。要抓得到得用 DXGI Desktop Duplication，那是另一個量級的工程，本階段不做 |
| 框選覆蓋層（Tk `-alpha`／`-topmost`／`-fullscreen`） | **未實測**（Xvfb 下的行為不算數） | 覆蓋層叫不出來時退回「輸入座標」或「整個螢幕擷取後再裁切」 |
| 全域熱鍵（`RegisterHotKey`） | **未實測** | 註冊失敗（例如熱鍵被別的程式佔走）時要明講是哪個熱鍵、讓使用者改設定，不可以靜默失敗——技術現實表早就記著「理論可行但脆弱」 |
| 朗讀（SAPI `SpVoice`） | **未實測** | COM 建不起來時停用朗讀按鈕並說明原因，不影響翻譯本身 |
| 高 DPI 縮放下的座標換算 | **未實測** | 125%／150% 縮放時框選座標與實際像素會差一個倍率，抓錯位置。實作時要處理 DPI awareness，而這一項在容器裡連錯都看不出來 |

**實作時的分工原則**：能寫進 `subtitle/` 的純邏輯一律寫進去並離線測；
Windows 那一側的每一個呼叫都要有「失敗時說人話」的分支。上面這張表要原
樣搬進實作階段的 PR 描述，哪一項仍未實測就照實寫。

## 2. 三條 OCR 路線：只有一條測得到

| 路線 | 能不能在本環境實測 | 結論 |
|---|---|---|
| (a) vision 模型 API | **不能**——這個容器沒有 API 金鑰（環境變數與 `config.json` 都沒有） | 見下 |
| (b) Windows 內建 `Windows.Media.Ocr` | **不能**——沒有 Windows | 見下 |
| (c) tesseract | **可以**，已實測（5.3.4，eng／jpn／chi_tra） | **建議選它** |

### (a) vision 模型 API — 不建議當主力

沒有金鑰所以沒有辦法量辨識率，這點照實記錄。但有三個**不需要實測就成
立**的理由讓它不適合當主力：

1. **每次框選都要錢。** 這功能的使用方式是「看不懂就框一下」，一場遊戲
   下來可能框幾十次。OCR 走本地的話這筆錢完全不存在。
2. **每次框選都要等一趟網路往返。** 本地 OCR 實測中位數 0.2 秒；一趟
   API 往返至少是它的好幾倍，而且會受網路狀況影響。
3. **整張畫面會離開這台電腦。** 這是最重要的一條，見第 4 節。

它適合當**第二把刀**：本地 OCR 判定「讀不到」時，讓使用者自己按一下
〔用 AI 再讀一次〕。那是明示的、單次的、使用者知道自己在付錢與送圖。

### (b) Windows 內建 `Windows.Media.Ocr` — 有吸引力，但成本在別的地方

免費、離線、系統內建、不必下載任何東西，語言包跟著 Windows 的語言設定
走。問題在**零第三方依賴的限制下要怎麼呼叫它**：那是 WinRT API，Python
要嘛裝 `winrt`／`pywinrt`（違反零依賴），要嘛用 `ctypes` 自己接
`RoInitialize` / `RoGetActivationFactory` 與一連串 COM 介面。後者理論上
做得到，但是**寫起來長、錯起來難查，而且我在這裡連編譯都試不了**。

**建議**：不列入第一階段。等第一階段上線、tesseract 那條路跑順之後，再
評估要不要加這條當「不必下載的預設選項」。

### (c) tesseract — 實測結果

安裝走既有的 ffmpeg 一鍵安裝機制（`gui/ffmpeg_dialog.py` 已經在讓使用者
下載 80~100 MB，附進度條，只需一次）。tesseract 本體加三個語言包遠比那
個小。

## 3. 實測數字（tesseract 5.3.4）

### 3.1 測資

12 個難例 ＋ 1 個負向控制組，全部用 ffmpeg `drawtext` 合成（本專案既有
作法），解析度 1280×200，每張兩行英文（日文／繁中案例除外）。難例是刻
意挑的，不是乾淨的黑字白底：

| 案例 | 內容 |
|---|---|
| 01 clean | 黑字白底（基準線，證明工具鏈本身沒問題） |
| 02 game_dark | 深色底淺色字（遊戲對話框） |
| 03 translucent_bar | 半透明黑底條 ＋ 白字（影片字幕） |
| 04 thin_outline | 細描邊白字、沒有底條 |
| 05 busy_bg | 逐像素雜訊背景（**極端對照組：畫面上其實沒有可讀的字**） |
| 06 small_ui | 16px 小字級 UI |
| 07 serif | 襯線字型 |
| 08 scene_gradient | 白字描邊疊在高彩度、有明暗變化的場景上 |
| 09 alpha_text | 半透明文字（alpha 0.6） |
| 10 outline_on_light | 亮背景上的白字黑描邊（字身與背景同色，只剩描邊） |
| 11 japanese | 日文（遊戲翻譯最常見的來源語言） |
| 12 chinese | 繁體中文 |
| 99 negative_control | 圖上畫的是完全不同的句子——**用來證明計分抓得到錯** |

負向控制組的字元錯誤率是 **76.7%**，證明計分方式不是照單全收。

### 3.2 結果

錯誤率是**標點正規化後**的字元錯誤率（CER）。要正規化是因為 CJK 的全形
標點與 tesseract 逐字插入的空白不是辨識錯誤，見 3.4。

模式是「跑 psm3／psm6／psm6+3 倍放大三種，取 tesseract 自報平均信心值最
高的那一個」——實作時沒有標準答案可比，只能這樣挑。

| 案例 | 選中的模式 | CER | 平均信心 | 耗時 |
|---|---|---|---|---|
| 01 clean | psm3 | **0.0%** | 95.9 | 200 ms |
| 02 game_dark | psm3 | **0.0%** | 96.1 | 214 ms |
| 03 translucent_bar | psm6+3x | **0.0%** | 96.1 | 403 ms |
| 04 thin_outline | psm6+3x | **1.1%** | 93.3 | 412 ms |
| 05 busy_bg | psm6+3x | 失敗（純亂碼） | 22.2 | 5338 ms |
| 06 small_ui | psm3 | **0.0%** | 95.9 | 179 ms |
| 07 serif | psm3 | **0.0%** | 96.1 | 209 ms |
| 08 scene_gradient | psm6+3x | 12.2% | 76.7 | 442 ms |
| 09 alpha_text | psm3 | **0.0%** | 95.9 | 218 ms |
| 10 outline_on_light | psm6 | **4.4%** | 83.0 | 158 ms |
| 11 japanese | psm3 | **0.0%** | 92.9 | 192 ms |
| 12 chinese | psm3 | **0.0%** | 90.0 | 233 ms |

**12 個案例裡 8 個一字不差、10 個 CER ≤ 5%。** 唯一真正失敗的是 05，而
那張圖上本來就沒有字（見 3.3 第二點）。單次耗時中位數 **218 ms**。

### 3.3 兩個關鍵發現

**發現一：沒有一種模式全贏，而「照信心值挑」這個挑法有效。**

- `psm6` 把 10 號案例從 **51.8% 救到 4.4%**
- `psm6` ＋ 3 倍放大把 4 號案例從 3.6% 救到 1.1%
- `psm3` 最快，在乾淨畫面上與其他模式並列第一

三種模式全跑一遍約 **0.8 秒**，換來的是「難例不會整個垮掉」。而挑選策略
可以用 tesseract 自己吐的平均信心值——**13 個案例裡 12 個挑中最佳或與最
佳相差 2% 以內**。

**發現二：信心值不能只看「濾掉低分之後剩下的那些」。**

05 號那張雜訊圖（畫面上根本沒有字）：tesseract 吐出 **125 個字塊、整體平
均信心只有 21.9**。但把低於 45 分的丟掉之後，**剩下 18 塊的平均是 68.2**
——照那個數字判就會回報「讀得很好」，然後把
`"he a gote Fito PICK. pick u open en unt until ntern you ted"` 這種東
西送去翻譯。

這個坑我第一版就踩了，是拿真實資料跑才發現的。判讀必須看**過濾前**的平
均與留存比例：留存比例 < 50% 且過濾前平均 < 60 → 判定「讀不到」，明確告
訴使用者重框，而不是送亂碼去翻譯。已寫成
`subtitle/ocrlayout.py` 的 `verdict` 並由 `tests/test_ocrlayout.py` 用那
125 個字塊的真實資料守住。

### 3.4 排版還原：已實作並測試（`subtitle/ocrlayout.py`）

OCR 吐出來的不是文章，是一堆帶座標的字塊。直接照順序串起來會壞掉，實測
踩到三種，每一種都會讓翻譯跟著爛：

| 問題 | 實測證據 | 處理 |
|---|---|---|
| **CJK 之間被插入空白** | 日文與繁中兩張圖辨識其實**一字不差**，但逐字元比對的錯誤率是 73% 與 82%——差別全是空白。送出去的若是「扉 は 三 つ の 封印」，翻譯品質當然掉 | 兩邊只要有一邊是 CJK 就不補空白 |
| **句子中間的硬換行** | 對話框那張圖被折成四行，串起來是四個殘句 | 同一段內的列接回一句；行尾連字號吃掉 |
| **兩欄被讀成同一行** | 遊戲設定頁那張圖，左欄「Resolution」和右欄「Master Volume」被 OCR 依 y 排成一行 | 偵測跨列一致的欄界後分欄 |

施工中另外踩到兩個自己的錯，都是拿真實座標跑才發現的：

1. **欄界取平均會落在該分到右欄的字塊身上。** 四列的右欄分別從
   x=700、703、703、700 開始，平均 701.5，於是 x=700 的那兩塊被留在左
   欄，兩欄內容整個交錯。**要取最小值**（最左邊那一塊的起點才是界線）。
2. **只看單列的大間距會把一段話切成假的兩欄。** 08 號那張圖有兩列各缺
   了幾個字、留下大洞，就被誤判成兩欄。**欄界必須跨列一致**（至少兩列、
   且至少四成的列支持同一個 x）。

模組是純邏輯、零 GUI 依賴，而且**不綁任何一家 OCR 引擎**——只吃
`{"text", "left", "top", "width", "height", "conf"}` 這個共同形狀，所以
三條路線換來換去都不必改它。測資是真的 tesseract TSV 輸出（含座標與信心
值）存進 `tests/data/ocr_boxes.json`，測試本身不需要裝 tesseract。五個破
壞探針都驗過會失敗。

### 3.5 成本與延遲

| | 本地 tesseract | vision 模型 API |
|---|---|---|
| 單次辨識 | **實測中位數 218 ms**（三模式全跑約 0.8 秒） | **未實測**（沒有金鑰）；至少一趟網路往返 |
| 每次費用 | **0** | 依圖片尺寸計費，框越大越貴 |
| 畫面是否離開本機 | **否** | 是 |
| 需要下載 | 一次（比照 ffmpeg 的一鍵安裝） | 否 |

**API 那一欄沒有數字，是因為量不到，不是因為忘了量。** 實作時若要把它當
選配，費用要在介面上先講清楚再送出。

一個要注意的實測細節：05 號那張雜訊圖在 3 倍放大下花了 **5.3 秒**（其餘
案例都在 0.5 秒內）。放大要按面積設上限，否則使用者框到一大塊雜訊畫面時
會以為程式當掉。

### 3.6 這些數字的適用範圍（不要過度解讀）

- 測資是 ffmpeg 算繪出來的文字，和真實螢幕一樣屬於「算繪文字」而不是
  「拍照文字」——這正是辨識率偏高的原因，**不是測太鬆**。
- 但真實截圖還有三件事沒有被涵蓋：**ClearType 次像素平滑化**、**高 DPI
  縮放**、**影片壓縮造成的色塊**。這三項要等到 Windows 上才測得到。
- tesseract 是 Linux 版 5.3.4；Windows 版是同一個引擎與同一份
  traineddata，辨識率**應該**一致——但這是推論，不是實測。

## 4. 隱私：本地 OCR 讓這件事變簡單很多

螢幕內容比剪貼簿更敏感——畫面上可能有密碼欄、私訊、銀行頁面。v2.1.0 的
原則是「**寧可漏翻、不可誤送**」，在這裡的對應是：

1. **畫面不外傳。** OCR 走本地之後，離開這台電腦的只有「辨識出來的那段
   文字」，而且是使用者自己框的那一塊。這是本次調研最大的收穫之一。
2. **只截使用者當下框的那一塊**，不自動、不背景、不連續截圖。
3. **預設關閉**，由使用者主動開啟。
4. **送出前看得到自己框到了什麼**——辨識結果要先顯示，再送翻譯。
5. **沿用 `subtitle/clipwatch.py` 的篩子**擋掉明顯是密碼／金鑰的內容。
   那個模組已經是零 GUI 依賴的純邏輯，直接餵 OCR 結果就能用。
6. vision API 當選配時，**送圖之前要明講「這張圖會傳出去」**。

## 5. 為什麼仍然不做「連續即時翻譯」

數字漂亮不改變這個判斷：

- **獨佔全螢幕的遊戲 GDI 抓不到**，要 DXGI Desktop Duplication，那是另
  一個量級的工程，而且在這裡連測都測不了。
- **覆蓋層在全螢幕下容易被吃掉或閃爍**，同樣驗不到。
- **逐幀處理的成本**：就算 OCR 只要 0.2 秒，連續模式還要疊上「畫面變了
  沒」的判斷、翻譯的往返與費用。翻譯那一半仍然是要錢的 API。

**承諾的是「按熱鍵翻譯畫面上這一塊」**，視窗化與無邊框的遊戲、網頁、影
片對話框、圖片文字都涵蓋得到。

---

## 6. 「完全免費」現在的缺口只剩一半

OCR 走本地之後，這件事的帳變清楚了：

| | 免費嗎 |
|---|---|
| 擷取、框選、排版還原、朗讀、複製 | ✅ 全免費 |
| OCR | ✅ 免費（tesseract 本地，或日後接 Windows 內建） |
| **翻譯** | ❌ 仍是使用者自己的 OpenAI API 金鑰 |

要補上最後一塊得換一個免費翻譯後端，**那是另一個題目**，不併進這一項。

## 7. 建議的第一階段工作項

1. `subtitle/ocrlayout.py` — **已完成**（本輪產出，含測試）
2. `subtitle/ocrengine.py` — 包住 tesseract 的呼叫：三模式全跑、照信心值
   挑、放大依面積設上限、引擎不在時回報清楚的錯誤。零 GUI 依賴、可離線測
3. tesseract 一鍵安裝 — 沿用 `gui/ffmpeg_dialog.py` 的下載／解壓／進度機制
4. 螢幕擷取與框選覆蓋層 — Windows 專屬，**每一個失敗路徑都要先寫好退路**
5. 全域熱鍵 — 註冊失敗要說是哪個熱鍵、可改設定
6. 介面：辨識結果先顯示再送翻譯、`verdict` 為「讀不到」時不送出、朗讀與
   複製兩顆按鈕、沿用既有的關鍵詞解說與生字本
7. 文件與四個產出物（這一項會是次版，要有新功能介紹）

**第一階段不含**：連續即時翻譯、獨佔全螢幕支援、Windows 內建 OCR、免費
翻譯後端。
