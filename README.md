# SRT 自動字幕生成與編輯工具

一套 Windows 桌面應用程式，可將影片／音訊轉錄為 SRT 字幕，或匯入現成文字稿自動對齊時間軸。內建智慧斷句、即時預覽與字幕樣式調整功能，並提供「一鍵完成」與批次處理，把生成、匯出、燒錄濃縮成一個步驟；「審片助手」則以文字審片自動標記精彩片段、冷場與重複拍攝，快速從素材挑出可用片段並輸出粗剪影片或 EDL；「配樂助手」可一鍵幫影片配上背景音樂並自動閃避人聲，免除手動調音量的麻煩；「**健檢中心**」（v1.50.0 起）一鍵檢查爆音、音量、底噪、影片畫質、字幕品質、開場、廣告友善度等 15 項，可修的發現旁邊就是修復按鈕；「封面候選」自動從精彩片段挑出清晰畫面當縮圖素材；「品牌套版」設定一次片頭片尾與浮水印，之後每支影片一鍵套用，不必再重複手動接片頭片尾、調浮水印位置。

## 快速上手：一鍵完成（v1.3.0 起）

日常上字幕只需三步，全程不再跳出任何存檔對話框：

1. **選檔**：按「瀏覽...」選擇影片（可按住 Ctrl / Shift 一次選多個檔案批次處理）。
2. **勾選輸出**：在「自動化輸出」勾選要匯出的格式（SRT／VTT／ASS／TXT），需要硬字幕影片就勾「燒錄硬字幕影片」。這些勾選會被記憶，之後不必再設定。
3. **按「一鍵完成」**：程式自動完成「生成字幕 → 匯出檔案 → 燒錄影片」整條流程。

輸出規則：

- 輸出檔自動以來源檔名命名：`影片.mp4` → `影片.srt`、`影片_subtitled.mp4`。
- 預設輸出到來源檔所在資料夾；也可在「自動化輸出」指定固定的輸出資料夾。
- 同名檔已存在時自動改名為 `影片 (1).srt`，不會覆蓋舊檔。
- 批次處理時逐檔顯示進度（`[2/5] 影片B.mp4：...`），單一檔案失敗不會中斷整批，結束後會列出成功與失敗清單。
- 完成後最後一個檔案的字幕會載入清單，可直接檢視、微調後用下方按鈕重新匯出。

**批次跑「模式二：文字稿對齊」**：把每部影片的文字稿存成旁邊同名的 `.txt`（如 `演講.mp4` 配 `演講.txt`），程式會自動帶入，不必逐一貼上。

### 最快的用法：把檔案拖到 exe 圖示上

在檔案總管把一個或多個影片**直接拖曳到 `SRT-Subtitle-Generator.exe` 圖示上**，程式會依記憶的自動化設定靜默跑完整條流程，結束後以視窗回報每個檔案的輸出結果——連程式視窗都不用開。

### 命令列批次模式（進階）

不開視窗也能跑同一條自動流程，設定沿用 `config.json`（在 GUI 調好一次即可）：

```
python main.py 影片1.mp4 影片2.mp4          # 依記憶的自動化設定批次處理
python main.py --burn 影片.mp4              # 本次強制燒錄硬字幕
python main.py --formats srt,ass 影片.mp4   # 本次改匯出 SRT 與 ASS
python main.py --mode align 演講.mp4        # 文字稿對齊（文字稿放在同名 .txt）
python main.py --output-dir D:\out 影片.mp4 # 本次輸出到指定資料夾
python main.py --audiocheck 影片.mp4        # 上片前音訊健檢（免轉錄）
python main.py --videocheck 影片.mp4        # 影片畫質健檢＋頭尾廢秒（免轉錄）
python main.py --thumbnails 影片.mp4        # 封面候選圖（免轉錄，均勻取樣）
python main.py --subs 影片.srt --burn 影片.mp4   # 既有字幕直接燒錄（免轉錄，v1.19 起）
python main.py --subcheck 影片.mp4          # 字幕健檢：CPS／行數，可與其他模式併用（v1.20 起）
python main.py --punctcheck 影片.mp4        # 中文字幕標點規範（v1.47 起）；加 --punctfix 另存規範版
python main.py --adcheck 影片.mp4           # 廣告友善度自查：黃標風險預檢（v1.29 起）
python main.py --subs 舊字幕.srt --synccheck --syncfix 影片.mp4  # 字幕同步檢查＋校正（v1.30 起）
python main.py --seriescheck EP01.mp4 EP02.mp4 EP03.mp4  # 系列一致性：比對整批彼此（v1.31 起）
python main.py --chaptercheck 章節.txt --chapterfix 影片.mp4  # YouTube 章節健檢＋一鍵修正（v1.32 起）
python main.py --hookcheck 影片.mp4         # 開場健檢：多久才進正題（v1.33 起）
python main.py --pacecheck 影片.mp4         # 剪輯節奏健檢：畫面太久沒變化（v1.34 起）
python main.py --thumbcheck 封面1.png 封面2.png  # 封面健檢＋候選排序（v1.35 起）
python main.py --publishcheck 發佈資訊.txt 影片.mp4  # 發佈資訊健檢（v1.36 起）
python main.py --legibility 影片.mp4        # 字幕可讀性健檢（v1.37 起）
python main.py --preflight 影片.mp4         # 上片前總體檢：一次跑完（v1.38 起）
python main.py --endscreen 影片.mp4         # 片尾空間健檢（v1.39 起）
python main.py --sponsorcheck 影片.mp4      # 工商揭露健檢（v1.40 起）
python main.py --termcheck 影片.mp4         # 術語一致性檢查（v1.41 起）
python main.py --shorts 長片.mp4            # 自動挑段輸出多支直式短片（v1.42 起）
python main.py --multilang 影片.mp4         # 多語字幕包（v1.43 起）
python main.py --beatcheck --music 配樂.mp3 影片.mp4  # 節拍分析＋剪點對齊（v1.44 起）
python main.py --multilang --languages en,ja,ko --subs 母帶.srt 影片.mp4
python main.py --shorts --shorts-count 5 *.mp4  # 批次：每支各出 5 支短片
python main.py --termcheck --termfix 影片.mp4  # 順便一鍵統一寫法
```

命令列旗標僅影響本次執行，不會改寫記憶的設定。適合搭配排程或一次處理整批檔案。

## 審片助手：拍完快速找可用片段（v1.3.0 起）

拍完素材後來回拉時間軸找片段最耗時。審片助手改用**文字審片**——讀逐字稿遠比看影片快，且系統會先幫你標好可剪的內容：

1. 選好素材後按工具列的「**審片助手（找片段）**」，再按「開始分析」。
2. 系統轉錄素材、分析音量能量，切成講話段落並自動標記四類內容：
   - **精彩片段**（綠色）：綜合音量能量、語速、情緒詞（哇、太扯、wow…）與驚嘆句評分，達標即標記
   - **冷場**（灰色）：長時間無人聲（門檻可調，預設 2 秒）→ 預設捨棄
   - **重複拍攝**（琥珀色）：同一句話重講多次（吃螺絲重來），自動只保留最後一次 → 前面幾次預設捨棄
   - **口頭禪多**（琥珀色）：「呃、嗯、欸」等填充詞密集的段落 → 標記供複查（仍保留）
3. **一眼總覽**：視窗上方的**彩色時間軸**把整條素材畫成色帶——綠色是精彩、琥珀色待審視、灰色冷場、藍色一般內容，捨棄段以網點淡化；點任一色塊直接跳到對應段落。清單列也依同色系上底色，並顯示保留／精彩／冷場時長統計。
4. 掃一遍清單微調：雙擊或空白鍵切換保留／捨棄；「只看精彩」「只看待審視」篩選快速聚焦；關鍵字搜尋跳到講到某主題的段落。
5. 一鍵輸出（皆自動命名、不跳對話框）：

### 偵測設定：依自己的頻道風格調整（v1.4.0 起）

審片視窗的「偵測設定」區可調整所有判定參數，自動記憶、下次分析生效：

| 參數 | 預設值 | 可調範圍 | 調高會怎樣 | 調低會怎樣 |
|------|--------|----------|------------|------------|
| **精彩敏感度** | 1.0 倍 | 0.2～3.0 | 更多段落被標成精彩（綠色變多） | 判定更嚴格，只有反應最大的段落才標精彩 |
| **自訂情緒詞** | （空） | 自由輸入 | 加入的詞出現時更容易被判定精彩 | — |
| **口頭禪字表** | 呃嗯欸蛤齁 | 自由輸入 | 更多字被算進口頭禪密度 | 少算一些字，避免正常用字被誤判 |
| **冷場門檻** | 2 秒 | 0.5～10 | 更久的安靜才算冷場（保留較多安靜片段） | 較短的安靜就標記冷場，剪得更緊湊 |
| **段落切分停頓** | 1 秒 | 0.4～5 | 段落被切得更細（停頓稍長就分段） | 段落較長，只有明顯停頓才分段 |
| **重複判定相似度** | 0.72 | 0.5～0.95 | 判定更嚴格，只有幾乎一字不差才算重複拍攝 | 較寬鬆，措辭略有出入也會歸為同一次重講 |
| **口頭禪密度門檻** | 0.08 | 0.02～0.5 | 口頭禪要非常密集才標記「口頭禪多」 | 稍微多一點口頭禪就會被標記供複查 |
| **章節最短長度** | 60 秒 | 10～600 | YouTube 章節切得更粗（章節數變少） | 章節切得更細（章節數變多） |
| **精彩訊號權重**（v1.7.0 起） | 各 1.0 | 0～3 | 該訊號對精彩判定的影響變大 | 影響變小；調到 0 完全停用該訊號 |
| **音量聚焦人聲頻帶**（v1.8.0 起） | 開 | 開／關 | —（預設即開） | 關閉後音量分析涵蓋全頻帶；素材以音樂為主體（樂器演奏、DJ）時關閉 |

**音量聚焦人聲頻帶**：精彩偵測的音量訊號預設只看 150～4000 Hz 的人聲頻帶，背景配樂的低頻鼓點或高頻效果音不會再把普通段落「頂」成精彩——這是各家剪輯工具在背景音樂下準度下降的通病。一般拍攝素材維持預設開啟即可。

**精彩訊號權重**是四個獨立的旋鈕（音量、語速、情緒詞、驚嘆句），與「精彩敏感度」的差別：敏感度是整體門檻的高低，權重則決定**由哪些訊號來判定**。例如：

- 教學型影片語調平穩、很少驚呼 → 情緒詞 0.5、驚嘆句 0.5、音量 1.5：讓「講到重點自然提高音量」成為主要依據
- 遊戲實況激動時刻靠喊出來 → 音量 2.0、語速 1.5：抓住尖叫與連珠炮反應
- 想純靠內容文字判定（如錄音環境音量不穩） → 音量 0：完全忽略音量訊號

拿不準怎麼調時，建議的操作順序：**先用預設值跑一次分析 → 看彩色時間軸的結果 → 只調一個最不滿意的參數 → 重新分析比較差異**，而不是一次改動多個參數，比較容易看出哪個設定造成了影響。

#### 情境範例：三種常見素材類型的起始設定

以下是三種常見頻道／素材類型可以直接套用的起始值（仍可再依實際結果微調）：

| 情境 | 精彩敏感度 | 冷場門檻 | 重複判定相似度 | 說明 |
|------|-----------|----------|----------------|------|
| **Vlog／生活紀錄**（講話反應平緩，很少大喊大叫） | 1.3～1.5 | 2～3 秒 | 0.72（預設） | 語調變化小，敏感度調高才抓得到「相對」精彩的段落 |
| **遊戲實況／開箱剪輯**（情緒起伏大、常有驚呼） | 0.8～1.0（預設） | 1.5 秒 | 0.65（放寬） | 反應本來就多，用預設或略降即可；玩家常常重講同句台詞，相似度放寬更容易抓到重複 |
| **教學／知識型影片**（語速平穩、內容重於情緒） | 1.0（預設） | 3～4 秒（拉長） | 0.8（收緊，避免正常重述被誤判） | 錄影中常有思考停頓，冷場門檻拉長避免正常換氣被剪掉；教學常會刻意重複重點，相似度收緊避免誤刪 |

CLI 批次審片（`--review`）沿用同一組記憶的參數。

### Shorts 直式短片輸出（v1.5.0 起）

橫式素材重剪成 Shorts／Reels／TikTok 最花時間。審片助手輸出區的「**直式短片**」列可把任意段落一鍵轉成 9:16（1080x1920）直式影片：

1. 在段落清單**選取要輸出的段落**（Ctrl／Shift 可多選）；不選取則自動輸出所有**精彩片段**。
2. 選版式：
   - **裁切**：以「焦點」滑調（0 最左、0.5 置中、1 最右）決定取景位置，適合人物固定在畫面某側
   - **模糊背景**：完整畫面置中、上下以放大模糊的原畫面填滿，畫面資訊不損失
3. 可勾「**燒錄字幕**」（沿用你的字幕視覺樣式，時間軸自動平移）與「**響度正規化**」。
4. 按「輸出直式短片」，每段各輸出一支 `素材_短片01.mp4`，逐支顯示進度。

版式、焦點等設定會自動記憶。

**「焦點」怎麼調（範例）：** 先用 0.5（置中）輸出一支試看——人物若被裁到左邊畫面外，調小到 0.2～0.3；被裁到右邊畫面外，調大到 0.7～0.8。單人固定坐在鏡頭前的講話素材通常 0.5 就夠用；若人物在畫面中會左右走動，改用「模糊背景」版式較保險，不必為了裁切焦點反覆試錯。

#### 字幕安全區：避開平台介面遮擋（v1.25.0 起）

一般字幕樣式的垂直位置是針對橫式（16:9）畫面調的，直接套用到 9:16 短片畫布上，很容易落在 TikTok／Reels／Shorts 平台介面固定佔用的區域——底部的帳號名稱、文案、配樂資訊與互動按鈕列，以及頂端可能的置頂留言或標題覆蓋層，都會把字幕擋住。

「直式短片」輸出區新增「**字幕安全區**」勾選（預設開）：

- **頂端保留 / 底部保留**：字幕垂直位置會被夾限在這個安全範圍內（預設頂端 6%、底部 22%，皆可調 0～35%），只影響直式短片燒錄的字幕位置，不影響你原本設定的一般橫式字幕樣式。
- **左右保留**：同時縮減左右邊界（預設 5%，可調 0～15%），避開右側常見的互動按鈕欄。
- 素材原本沒有燒錄字幕、或沒選字幕來源時，安全區設定不會有任何影響。

需要更寬鬆或更保守的保留範圍（例如目標平台的介面配置與預設值不同）時，直接調整這三個百分比即可，設定會自動記憶。

### 響度正規化：告別影片太小聲（v1.5.0 起）

YouTube 會把超過 -14 LUFS 的音訊自動調小，但**太小聲的不會被調大**——錄音偏小聲的影片上傳後會一直小聲。解法：

- 在「自動化輸出」勾選「**燒錄時響度正規化**」，目標值預設 **-14 LUFS**（YouTube 標準，可調 -30～-8）。
- 之後「一鍵完成」與「燒錄字幕到影片」輸出的影片都會先量測實際響度、再線性校正到目標值（兩階段處理，比單次動態調整更精準、音質更好）。
- 直式短片輸出也有獨立的「響度正規化」勾選。
- CLI：`--loudnorm`／`--no-loudnorm` 可覆寫本次設定。

**目標值怎麼選（範例）：**

| 目標值 | 適合情境 |
|--------|----------|
| **-14 LUFS**（預設） | 一般 YouTube 影片，不確定要選什麼就用這個 |
| **-11～-13 LUFS** | 音樂／節奏感強的內容，想要比平台基準略響亮一點 |
| **-16 LUFS** | Podcast、純口說訪談，避免長時間收聽顯得刺耳 |
| **-19～-23 LUFS** | 供電視或需符合廣播響度規範的交付素材 |

不確定自己影片目前多大聲也沒關係——這個功能會自動先量測，你只需要決定「想要多大聲」這個目標值即可。

| 輸出 | 用途 |
|------|------|
| **粗剪影片（自動跳剪）** | ffmpeg 把保留段落串成一支影片，直接看粗剪效果 |
| **精彩合輯** | 只串接精彩片段——短影音（Shorts）、預告、亮點回顧素材 |
| **HTML 審片報告** | 單一檔案含彩色時間軸＋統計＋段落表，瀏覽器直接開，可傳給剪輯師 |
| **EDL（CMX3600）** | 匯入 Premiere Pro / DaVinci Resolve，時間軸即為保留段落，接著精剪 |
| **審片標記字幕（SRT）** | 與素材一起載入剪輯軟體，拉時間軸即見【精彩】【冷場】標記 |
| **CSV 片段清單** | Excel 檢視、備查、與剪輯師交接 |
| **YouTube 章節** | 智慧合併成合理粒度（見下），複製即貼影片說明欄 |
| **發佈包（v1.10.0 起）** | 建議標題候選＋描述草稿＋標籤清單，上傳時直接取用（見下） |
| **封面候選圖（v1.11.0 起）** | 從精彩片段自動挑清晰畫面輸出 PNG，縮圖素材免拖時間軸截圖（見下） |

**口頭禪自動剪除（v1.10.0 起）**：輸出區勾選「**剪除口頭禪字**」後，粗剪影片、精彩合輯與 EDL 會把保留段落裡的「呃、嗯、欸」等口頭禪**字詞本身**從時間軸剪掉（Descript 式 filler-word removal）——之前只能整段標記供複查，現在直接逐字剪除。內建防抖動保護：太短的口頭禪（<0.12 秒）不剪、剪點向內縮不切到相鄰字、剪除後過短的殘片自動捨棄；字表沿用「偵測設定」的口頭禪自訂字表。**建議先輸出一次粗剪聽聽效果**——講話節奏快的素材逐字跳剪可能略有頓挫感，不滿意取消勾選即可。

**一鍵發佈包（v1.10.0 起）**：按「**匯出發佈包**」輸出 `素材_發佈包.txt`——調研顯示多數創作者花大量時間剪片，標題、描述、標籤卻隨便帶過，導致點擊率與搜尋排名不佳。發佈包內含：
- **建議標題候選**（預設 3 個，v1.15.0 起按有效標題型態各出一手）：**精華句**（精彩分數最高段落，剝掉「然後、就是」等句首贅詞、以完整子句湊到長度上限，不再攔腰截斷）、**疑問句**（素材中實際講出的疑問，好奇缺口式）、**數字句**（含具體數字的句子）、**關鍵字冠頭**（【關鍵字】＋精華子句）——挑一個直接用或自行組合
- **描述草稿**（v1.46.0 起改寫成有結構的六段式）：**主題句**（優先挑講到你自訂關鍵字的那一句，沒有就取精彩分數最高的）＋**逐點摘要**（預設 3 點）＋**章節時間戳記**＋**hashtag**＋**頻道樣板放最後**——複製後自行潤飾
- **建議標籤**（預設 15 個）：素材中實際講到的高頻詞——你的自訂情緒詞（頻道口號、產品名）優先、中文高頻詞組、英文高頻詞，上傳時自行增刪

候選數量與長度可在 `config.json` 的 `publish` 區調整（標題候選 2~6、標題長度 20~60、標籤數 5~30）；CLI 批次審片也會逐檔附上發佈包。

**描述草稿為什麼要重寫（v1.46.0）**：舊版的描述草稿是「把第一段講話截前 60 字再補刪節號」，實測產出的開頭是「那個 就是說 今天我們要來聊一個東西……」——句首贅詞沒剝（本工具別處明明就會剪掉口頭禪）、攔腰截斷、而且取的是**第一段**而不是**最精彩那段**。同一個模組替標題挑到的是「怎麼樣讓你的影片節奏變得更好看」，描述卻用了最沒資訊量的一句，前後不一致。把舊草稿丟進 v1.45.0 的**說明欄結構健檢**，自己就會被自己標記。改寫後的順序照調研走：
- **前 200 字元權重最高**，所以主題句放第一行，且優先挑**真的講到主題關鍵字**的那一句（關鍵字沿用審片設定的「自訂情緒詞」）
- **接著逐點摘要**，讓說明欄有內容而不是只有一行；點數可用 `build_description(summary_points=N)` 調整
- **章節時間戳記**（沿用既有章節合併結果）
- **hashtag 最多 5 個**
- **頻道樣板（訂閱、社群連結、合作邀約）放最下面**——調研明講不要放最上面，放上面會把權重最高的開頭佔掉

句子的挑選與清理完全重用標題那套邏輯（依精彩分數排序、剝句首贅詞、以完整子句湊長度），不另外實作一份。實測產出的草稿丟回自己的說明欄結構健檢，四項全綠。

**封面候選擷取（v1.11.0 起）**：選封面得在播放器來回拖時間軸，肉眼找一格「清晰、有內容」的畫面截圖——現在按「**擷取封面候選圖**」即自動完成：從**精彩分數最高的段落**取樣畫面，以邊緣能量評分（動態模糊、黑畫面都會得低分）挑出最清晰的格，輸出 `素材_封面01.png`…（1280 寬，YouTube 封面標準，依清晰度排序）。可調參數（自動記憶）：
- **張數**（2~12，預設 6）與**最小間隔**（預設 8 秒）：間隔避免候選全擠在同一幕
- **優先取精彩段落**：取消勾選改為所有保留段落一視同仁；完全沒分析過的素材則整片均勻取樣

拿候選圖進 Canva 等工具加大字標題就是成品縮圖。CLI：`--thumbnails` 單獨使用（免轉錄、均勻取樣）或與 `--review` 併用（優先精彩段落）。

**mid-roll 廣告插入點建議（v1.13.0 起）**：YouTube 允許 8 分鐘以上的影片放 mid-roll 廣告，且官方指出**放在自然停頓、話題轉換處**的廣告點觀眾留存較高、也較容易被實際投放（插在句子中間的常被系統跳過）——但手動找停頓得再拉一次時間軸。審片助手輸出區的「**複製廣告插入點**」直接從分析結果挑點：
- 只挑講話段落之間**夠長的自然停頓**（預設 ≥1.2 秒），停頓越久（通常是話題轉換）越優先
- **最小間隔**（預設 4 分鐘）與**數量上限**（預設 6 個）可調並記憶；自動避開影片開頭 2 分鐘與結尾 1 分鐘
- 複製結果含時間戳、停頓秒數與**前後句摘要**，不用開影片就能確認每個點在講什麼之間；發佈包也會自動附上
- 時間以目前素材時間軸為準：未剪輯直接上傳可直接用；若上傳的是粗剪版，請以粗剪檔重新分析後再取點

**YouTube 章節智慧合併（v1.6.0 起）**：章節不會一段一章——只在大停頓（剪掉的冷場處）且目前章節已達「**章節最短長度**」（偵測設定可調，預設 60 秒）時才切新章，首章固定 0:00。覺得章節太細調大、太粗調小。

**批次審片（進階）**：`python main.py --review 素材1.mp4 素材2.mp4` 可整批分析、逐檔輸出審片清單 CSV 與 HTML 報告——睡前掛整天拍的素材，隔天直接看報告挑片段。

**多檔審片彙總（v1.7.0 起）**：批次審片兩支以上素材時，自動另輸出「**審片彙總.html**」與「**審片彙總_精彩TopN.csv**」——整批素材的精彩片段**跨檔**依分數排序，並附各素材統計對照表（總長、保留、精彩段數、冷場、口頭禪）。一天拍 20 支素材，隔天打開彙總頁就知道「這批裡最值得用的前 10 段」在哪支的第幾分鐘，不必逐檔比較。Top N 段數可在 `config.json` 的 `review.batch_top_n` 調整（3～50，預設 10）。

## 配樂助手：背景音樂自動閃避（v1.9.0 起）

幫影片配上背景音樂時，音樂蓋過講話聲是最常見的困擾——手動逐段拉關鍵影格調音量非常花時間（Premiere、Filmora、DaVinci Resolve 2026 年都已內建自動閃避功能）。工具列的「**配樂助手（自動閃避）**」提供同等效果，不必離開本程式：

1. 按工具列「**配樂助手（自動閃避）**」，分別選擇**影片**與**背景音樂**檔（若已選取檔案會自動帶入為影片）。
2. 調整三個強度旋鈕（自動記憶）：

| 旋鈕 | 範圍 | 預設 | 說明 |
|------|------|------|------|
| **音樂音量** | 0.05～1.0 | 0.35 | 混音前的音樂基礎音量——沒有人聲時音樂大概多大聲 |
| **閃避強度** | 1～20 | 8 | 講話時音樂被壓低的程度，數值越高，講話時音樂壓得越小聲 |
| **自動適應人聲音量** | 開／關 | 開 | v1.15.0 起：先量測影片的人聲響度，再自動計算靈敏度——人聲偏小聲（還沒做響度正規化）的素材也能正確觸發閃避，建議保持開啟 |
| **閃避靈敏度** | 0.01～0.5 | 0.06 | 「自動適應」關閉時才使用：數值越低，越輕的講話聲就會觸發閃避；環境音較吵的素材可調高避免誤觸發 |

3. 按「**輸出混音影片**」，程式自動偵測人聲並即時調整音樂音量，輸出 `影片_配樂.mp4`（同名自動加流水號，不覆蓋舊檔）。

背景音樂比影片短時會自動循環播放，輸出長度自動裁到與影片一致；影像串流原樣複製，只有音軌重新混音，**畫質完全不受影響**。

**怎麼調整最合適：** 先用預設值（自動適應開啟）跑一次，實際聽效果——音樂閃避後仍蓋過人聲，調高「閃避強度」；閃避太明顯、忽大忽小很突兀，調低「閃避強度」；閃避完全沒觸發或觸發過頭且已關閉自動適應，才需要手動調「閃避靈敏度」；覺得平時音樂太小聲或太大聲，直接調整「音樂音量」。

## 健檢中心：三個健檢視窗併成一個（v1.50.0 起）

**「上片前健檢」「字幕健檢」「上片前總體檢」三個視窗背後其實是同一批
`subtitle/` 分析邏輯**，彼此有大量重疊（例如「上片前健檢」的五項檢查
全部又被「上片前總體檢」原樣重跑一次），使用者要在上傳前確認一支影片
沒問題，得記得開三個視窗、按好幾個按鈕，還要自己判斷哪些一定要修、修
復按鈕又在哪個視窗裡。v1.50.0 把三個視窗併成一個**健檢中心**：

1. **檢查對象**（皆選填，填什麼檢什麼）：影片檔／字幕，可沿用主視窗
   目前選取的檔案與字幕清單，也可另外瀏覽選擇。**沒有選影片也能跑**
   ——字幕相關的純文字檢查（CPS、廣告友善度、開場、標點、術語一致

   刻意保留。
2. **要跑哪些檢查**：14 項可勾選（音訊、影片畫質、曝光與色偏、音量一

   範、語音同步、片尾空間、工商揭露、術語一致性）＋檔名一律隨影片一

4. **健檢結果**：`ttk.Treeview` 依「一定要修／建議修／通過」分三組列

## 音訊健檢：上片前檢查聲音（v1.11.0 起）

「畫面差觀眾會忍，聲音差觀眾直接關掉」——爆音（clipping）、整體音量太小、底噪過高、麥克風只錄到單邊聲道，都是**上傳後才被留言提醒**的常見悲劇，而且事後幾乎救不回來。工具列的「**音訊健檢（上片前）**」一鍵掃描音軌（不改動原始檔），以檢查表回報四項檢查與具體修法：

| 檢查項目 | 檢查內容 | 常見修法 |
|----------|----------|----------|
| **整體響度** | 是否低於「太小聲門檻」（預設 -19 LUFS）或高於 YouTube 標準 | 輸出時勾「響度正規化」自動修正 |
| **爆音檢查** | 峰值是否貼頂、波形是否削平（真的爆掉） | 已爆音幾乎無法修復；重錄時增益調低、峰值留 -6 dB 餘裕 |
| **底噪檢查** | 底噪是否高於門檻（預設 -50 dB），安靜段落會聽到嘶聲 | 剪輯軟體降噪，或錄音時關風扇冷氣、麥克風靠近嘴巴 |
| **聲道平衡** | 左右聲道電平是否嚴重不均、甚至單邊無聲 | 剪輯軟體把音軌改單聲道或複製有聲聲道 |

- 四項門檻皆可在對話框調整並自動記憶（不同錄音環境可放寬或收緊）。
- 報告可一鍵複製或另存 `素材_音訊健檢.txt`。
- CLI：`python main.py --audiocheck 影片.mp4` 免開視窗批次健檢（免轉錄，速度快）；可與 `--review` 併用在審片時一起檢查。
- **建議把健檢排進上片前流程**：拍完先健檢，有紅字（✘）先處理再剪，比剪完才發現整批素材爆音省得多。

### 影片畫質健檢與一鍵去頭尾（v1.17.0 起）

同一個健檢視窗現在**連畫質一起檢查**（純音訊檔自動略過畫質段落）：

- **位元率**：對照 YouTube 官方建議上傳位元率（依解析度與更新率，如 1080p30 建議 8 Mbps、4K 35 Mbps）——位元率不足的影片上傳後會被 YouTube 重壓成一片糊，這是「上傳後才發現畫質變爛」最常見的原因；寬嚴倍率可調（預設 1.0×）
- **解析度／畫面更新率／編碼**：未達 720p、非標準更新率（常見於手機或螢幕錄影的可變更新率來源，可能造成影音不同步）、非主流編碼都會提醒
- **頭尾廢秒偵測**：掃描開頭／結尾的無聲與黑畫面（開機、清喉嚨的廢秒）——開頭空白是留存率殺手；偵測結果自動帶入「**一鍵去頭尾**」的修剪秒數，可微調後按「輸出修剪版」輸出 `素材_修剪.mp4`（重新編碼確保剪點精準、原始檔不受影響）
- **凍結畫面偵測**（v1.26.0 起）：掃描全片抓出「畫面卡住不動、聲音仍在播放」的錄製瑕疵（SD 卡寫入卡頓、相機緩衝區不足等），列出每一段的起訖時間與長度（判定秒數可調，預設 1.0 秒）；不會自動剪除（合理的持續鏡頭也可能被誤判），只提醒你檢查來源素材該時間點，需要時改用原始檔重新剪輯
- CLI：`python main.py --videocheck 影片.mp4` 輸出 `素材_影片健檢.txt`（自動涵蓋凍結畫面檢查），可與 `--audiocheck` 併用

### 畫面曝光與色偏健檢（v1.28.0 起）

曝光不足／過曝、白平衡沒調好造成的偏黃偏藍，是剪輯常見錯誤，也是不少創作者匯出後沒有從頭到尾看過一次就直接上傳，等觀眾留言才發現的問題。健檢視窗同步分析：

- 全片均勻取樣幾張畫面（免逐幀解碼，速度快），量測**平均亮度**（偏暗／過曝）與**色調**（是否明顯偏離中性灰）
- 取樣張數（預設 6 張）、過暗／過曝門檻（預設 60／200，0~255 亮度值）、色偏門檻（預設 10）皆可調並自動記憶
- **不會自動校色**：色彩校正的「正確答案」因人因場景而異，錯誤的自動校正反而可能讓畫面更難看（例如刻意的暖色調氛圍被誤「修正」成灰白）；只負責報告與建議，交由你自行判斷是否需要回到剪輯軟體調色
- CLI：`python main.py --colorcheck 影片.mp4` 輸出 `素材_色彩健檢.txt`，可與 `--audiocheck`／`--videocheck` 併用

### 音訊一鍵修復（v1.13.0 起）

健檢發現底噪偏高或太小聲，不必再把整支影片上傳到線上工具處理——健檢視窗下方的「**音訊修復**」直接輸出修復版（`素材_修復.mp4`，畫面原樣複製、只處理音軌，純音訊檔輸出 `.m4a`）：

| 修復項目 | 原理 | 適用情境 |
|----------|------|----------|
| **降噪**（強度 6~40 dB，預設 12） | FFT 頻譜降噪（afftdn） | 冷氣聲、電流聲、嘶聲等穩態底噪；強度過高人聲會發悶，建議先用預設值試聽 |
| **去低頻隆隆**（40~200 Hz，預設 80） | 高通濾波 | 桌面震動、風切、空調低頻；人聲基頻在 85 Hz 以上，預設值不傷人聲 |
| **響度正規化** | 兩階段 loudnorm | 整體太小聲；與燒錄時的響度正規化同一引擎 |

勾選項目與強度自動記憶；修完可對修復版再跑一次健檢比對。CLI：`python main.py --audiofix 影片.mp4`（依記憶的設定批次修復，免轉錄）。

### 分段音量一致性一鍵拉平（v1.24.0 起）

整體響度正常，不代表**每一段**都一樣大聲——收音距離忽遠忽近、不同場景／不同麥克風剪接在一起、外景風切偶爾蓋過人聲，都會讓觀眾一路調音量調到煩。既有的「整體響度」檢查只看全片平均，抓不出這種「忽大忽小」的段落級落差，因此健檢視窗新增「**分段音量一致性**」分析：

- 把影片切成固定長度的分段（預設 20 秒，可調 10~60 秒），逐段量測實際響度（LUFS），再與**整支影片的中位數響度**比較（不是對照 -14 LUFS 這種固定絕對值，因為每支影片的錄音環境本來就不同）——與中位數相差超過門檻（預設 3 LU，可調 1.5~8）即標記為落差過大的段落
- 「**拉平音量落差**」只調整被標記段落的音量增益，其餘段落與畫面完全不動——採音訊獨立處理（trim＋增益＋重新接回），畫面軌整段直接複製，不重新編碼畫面也不會有影音不同步風險；健檢沒找到落差過大的段落時按鈕維持停用，不會產生無意義的輸出檔
- CLI 新增 `--volumecheck`（輸出「檔名_音量一致性.txt」）與 `--volumefix`（拉平落差過大的段落並輸出「檔名_音量平衡.mp4」，沒有偵測到落差時單檔略過並提示），可與 `--audiocheck`／`--videocheck` 併用

## 說明欄結構健檢：寫了，但寫在對的地方嗎（v1.45.0 起）

調研（中英文皆搜）指出說明欄的規則已經從「塞關鍵字」變成「結構與前幾行」，而且門檻都可以機器檢查：

- **前兩三行就是全部**。「搜尋結果頁可能只顯示說明欄的第一行」；主要關鍵字要落在**前 25 個字內**才不會在行動裝置被截斷。中文官方說明還提到行動版要**點一下標題**才看得到說明欄——前幾行更關鍵。
- **關鍵字堆砌會被當成垃圾內容**：「堆關鍵字的時代已經結束，那個做法會觸發垃圾內容分類並傷害頻道權重」。
- **要有結構**：「把可用的篇幅用清楚的結構寫完，而不是寫成一大段密密麻麻的文字」。
- **章節來自說明欄的時間戳記**（YouTube 官方說明）。

本工具既有的「發佈資訊健檢」（v1.36）只檢查**硬性上限**，兩者不重疊：

| 既有的發佈資訊健檢（v1.36） | 本模組 |
|------------------------------|--------|
| 說明欄有沒有超過 5000 位元組 | 前 200 字元有沒有在講影片內容 |
| hashtag 有沒有超過 15 個 | 同一個詞是不是重複到像堆砌 |
| 標籤字元數 | 有沒有時間戳記章節、有沒有分段 |

一句話：**v1.36 看「會不會被系統拒絕」，v1.45 看「寫得對不對」。**

```
===== 說明欄結構健檢（寫了，但寫在對的地方嗎）=====
✔ 說明欄內容：說明欄有 233 字元
⚠ 開頭實質內容：前 200 字元有 79% 是連結、hashtag 或「訂閱按讚」這類交際語（建議 55% 以下）
⚠ 章節時間戳記：影片長 10 分鐘，但說明欄沒有時間戳記
✔ 分段結構：說明欄分成 7 段
```

### 為什麼用「管線佔比」而不是「剩幾個字」

第一版是「扣掉連結、hashtag 與樣板交際語之後還剩幾個字」。**實測立刻證明這行不通**：一段全是「歡迎來到我的頻道／訂閱按讚小鈴鐺／IG／FB／Discord／合作邀約」的開頭，扣完詞表後仍殘留 **50 個字**（`我的頻道記得開啟…我的ig我的facebook加入我的discord請來信`），字數看起來很多、**資訊量卻是零**，於是整項通過。

樣板詞表永遠不可能列全。改成量**連結與帳號佔了開頭多少比例**就穩健得多——連結與帳號本身就是最大宗，不需要窮舉每一句客套話。實測分離得很乾淨：管線型開頭 **0.79**、內容型開頭 **0.22**，門檻取 0.55。

- 時間戳記解析重用 `chaptercheck.parse_chapters`、hashtag 擷取重用 `publishcheck.find_hashtags`，本模組不重新實作。
- 章節那一項**只在長片提醒**（預設 5 分鐘以上），短片本來就不需要章節；沒給影片長度時整項略過。
- 堆砌判定同時要求「重複夠多次」與「佔比夠高」，避免很短的說明欄誤判。
- **只報告不自動改**：說明欄要怎麼寫是創作決定。
- CLI：`python main.py --publishcheck 發佈資訊.txt 影片.mp4`——結構健檢直接接在既有的上限檢查之後，同一份報告出完；GUI 的「發佈資訊健檢」視窗同樣會一併顯示。

## 音樂節拍分析：把剪點對到拍子上（v1.44.0 起）

調研（中英文皆搜）在「2026 年 AI 已經接手哪些、還有哪些仍靠手工」這個題目上反覆點名同一件事：**把畫面的轉場對齊到音樂的重拍與停頓，至今仍是編輯要手動做的**（"editors still need to manually align visual transitions to match audio peaks and pauses"）。工具端能做到的頂多是「分析節奏、建議符合 BPM 的曲子」——**知道 BPM 只是第一步，真正花時間的是把剪點一個一個挪到拍子上**。

本工具既有的功能都沒有碰到這一段：

| 既有功能 | 看的是什麼 |
|----------|-----------|
| 配樂助手（v1.9） | 只做**音量閃避**，完全沒有分析音樂的節奏 |
| 剪輯節奏健檢（v1.34） | 量的是**畫面多久沒變化**，與音樂無關 |
| 自動跳剪（v1.21） | 依**語音停頓**剪，也與音樂無關 |

```
$ python main.py --beatcheck --music 配樂.mp3 影片.mp4

===== 音樂節拍分析（把剪點對到拍子上）=====
  速度：140.0 BPM（每拍 0.429 秒）
  第一拍：0:00.0；全曲共 71 拍

剪點對齊建議：
  剪點 1：0:04.0 → 0:03.9（挪 -0.143 秒）
  剪點 2：0:08.0 → 0:08.1（挪 +0.143 秒）

  4/4 個剪點可對齊（實際需要挪動 4 個）。
```

- **配樂助手也有**：選好背景音樂後按「**分析節拍（對齊剪點）**」即可。
- **畫面剪點重用既有的偵測**（v1.34 的 `detect_scene_changes`），不重新實作。
- **離拍子太遠的不硬挪**：超過 `max_shift`（預設 0.25 秒）就維持原位並說明原因——硬挪會讓畫面與內容對不上，那不是對齊而是破壞。
- **免轉錄**：節拍分析只需要 ffmpeg，不會白跑一次語音辨識。
- **零第三方依賴**：純標準函式庫實作，不需要 numpy／librosa。

### 演算法與開發時實測踩到的坑

流程是「ffmpeg 解成單聲道 PCM → 能量包絡 → 半波整流的一階差分當起音強度 → 相位感知的梳狀濾波掃描候選 BPM」。用**已知 BPM 的節拍軌**驗證時抓到三個問題，全都修掉了：

1. **固定整數 lag 的自相關會系統性偏袒慢速。** lag 取整後在長訊號上累積漂移，短 lag（快速）受害更重——實測 120 BPM 的素材被判成 **60**。改成每一拍都由 `k × 週期` 重新計算位置。
2. **只看單一幀會錯過起音尖峰。** 一個 40ms 的敲擊只有約 1.7 幀寬，±0.5 幀的捨入就可能整個踩空。改成取拍點附近 ±1 幀的最大值。
3. **慢一倍的速度分數必然與正確速度相當**（它落在真拍點的子集上），單靠分數分不出來。因此另做**八度校正**：倍速分數仍接近就取較快的那個。

最後還加上**信心判定**——沒有節拍的素材（靜音、純長音）一樣會有一個「最高分」的 BPM，直接報出去等於自信地講一個錯的數字。以最佳分數與所有候選的平均分數相比，門檻 **2.0** 是實測校準的：節拍軌 4.7~6.5、有回音的類音樂素材 5.3、**純長音 1.24、靜音 0.0**。實測 90／120／140／100 BPM 四種素材皆正確還原，純長音與靜音皆正確回報「沒有偵測到穩定的節拍」。

- CLI：`python main.py --beatcheck --music 配樂.mp3 影片.mp4`（未給 `--music` 時分析素材本身的音訊）輸出「檔名_節拍分析.txt」；門檻可於 `config.json` 的 `beatsync` 調整。

## 多語字幕包：一份母帶翻成多國語言（v1.43.0 起）

調研的數字很直接：YouTube 官方說明指出**平均一位創作者超過三分之二的觀看時間來自居住地區以外的觀眾**，而上傳多語言內容的創作者**超過 25% 的觀看時間來自非影片主要語言的觀眾**。

英文調研則直接寫出了正確的作業流程：

> 從**一份校對好的母帶檔案**開始：先產生原文字幕、**在那裡把錯誤全部修好**、再**把那份 SRT 批次翻成每一個目標語言**、抽查、然後輸出各平台需要的格式。

以及規模化時的關鍵限制：**「影片一多，手動一支一支上傳翻譯根本行不通」**。

本工具的前半段已經很完整——轉錄、編修、自動修正詞庫、術語一致性檢查（v1.41）都是在把那份**母帶**修乾淨。缺的正是後半段：

| 既有的字幕翻譯（v1.18） | 差在哪 |
|-------------------------|--------|
| 一次只能翻**一種**語言 | 要五種語言就得重跑五次 |
| 只有 GUI 入口 | 十支影片＝十次手動操作，正是調研說的「行不通」 |
| 產出的是**雙語**字幕（原文＋譯文上下行） | 那是給**燒錄**用的；上傳到 YouTube 每個語言要的是**單語**檔 |

最後一點特別容易被忽略：**拿雙語字幕去當英文字幕上傳，英文觀眾會看到每一句都黏著看不懂的中文。** 所以本模組產出的一律是**單語**字幕，與燒錄用的雙語模式完全分開。

```
$ python main.py --multilang --languages en,ja,ko,zh-TW --subs 母帶.srt 影片.mp4

===== 多語字幕包（一份母帶翻成多國語言）=====
  ✔ 英文（en）：6 句 → 影片.en.srt
  ✔ 日文（ja）：6 句 → 影片.ja.srt
  ✔ 韓文（ko）：6 句 → 影片.ko.srt

共 3/3 個語言完成。每個檔都是「單語」字幕，可直接在 YouTube Studio 逐一上傳對應語言。
```

- **檔名帶語言代碼**（`影片.en.srt`），上傳時一眼就知道哪個檔對應哪個語言。
- **自動略過原文語言**：上例指定了 `zh-TW` 但影片原文就是 `zh-TW`，直接跳過——翻成自己沒有意義，還要多付一次 API 費用。
- **單一語言失敗不影響其他語言**：報告會如實列出哪個語言失敗、原因是什麼，可單獨重跑。
- **GUI 也有**：字幕翻譯視窗新增「多語字幕包」區塊，填語言代碼、選輸出資料夾即可。

### 省 API 費用：重複的句子只送一次

字幕裡「對」「嗯」「我們繼續」這類短句會重複很多次，逐句送 API 等於重複付費。本模組會先把重複句子收斂成唯一清單，翻完再攤回原本的位置——**譯文完全一致，但送出的句數變少**。實測一份 6 句、含兩組重複的母帶，每個語言只送了 **4 句**。重複越多的影片省得越多，可於 `config.json` 的 `multilang.dedupe` 關閉。

- 需要 OpenAI API 金鑰（沿用「轉寫設定」的金鑰）；沒填時會明確提示，不會靜靜跳過。
- CLI：`python main.py --multilang 影片.mp4`，`--languages en,ja,ko` 可只覆寫本次的語言清單。

## 短片自動選段：長片一鍵變多支 Shorts（v1.42.0 起）

調研（中英文皆搜）確認「一支長片再利用成多支短影音」已是 2026 年的主流工作流程，但同一批資料也點名了它真正的失敗模式：**做出一套慢到撐不下去的流程**（"the risky part is building a workflow that is too slow to sustain"）。另一個共識是**選段比數量重要**——「最強的再利用系統都是從『本來就有張力、有結論、有意外』的片段開始」。

本工具的缺口剛好就在這裡。v1.5.0 已經有直式短片輸出，品質也夠用，但是：

| 原本的狀況 | 問題 |
|-----------|------|
| 只有 GUI 入口 | 得在審片視窗裡自己一段一段勾選再按輸出 |
| 沒有任何地方在決定「要剪哪幾段」 | 選段完全靠人工 |
| 因此**沒辦法批次** | 十支影片就是十次手動操作——正是調研說的「慢到撐不下去」 |

所以這一版補的不是把既有函式包一層 CLI，而是中間那段**從來不存在的邏輯**：拿審片模組已經算好的精彩片段，規劃成一組**真的能發**的短片。

```
$ python main.py --shorts --shorts-count 3 長片.mp4

===== 短片選段規劃（長片自動挑成多支直式短片）=====
  短片 1：0:00～0:23（23 秒，精彩分數 4.8）
    內容：「今天要跟大家分享三個剪輯技巧」
  短片 2：2:06～2:31（25 秒，精彩分數 0.9）
    內容：「以上就是今天的內容我們下次見」

共規劃 2 支，長度介於 15～60 秒；各段沿講話段落邊界切齊，不會從句子中間開始。
```

規劃時做四件非做不可的判斷：

1. **長度要落在平台可用範圍**。精彩片段本身長度是任意的——可能 3 秒，也可能 90 秒。
2. **太短的往外擴，而且沿講話段落的邊界擴**，不會從句子中間切下去；前後輪流擴，才不會每支都從半句話開始。
3. **彼此不重疊**，否則會輸出好幾支內容幾乎一樣的短片。
4. **擴不到最短長度就放棄**，不硬湊一支沒人看得完的東西。

- **GUI 也有**：審片視窗的「**自動選段輸出**」會先把規劃結果顯示出來讓你確認，再照著輸出——不必自己一段一段勾。
- **可批次**：`python main.py --shorts *.mp4` 一次處理整個資料夾。
- 支數、最短／最長長度、前後留白與最小間隔皆可於 `config.json` 的 `clipplan` 調整；`--shorts-count` 可只覆寫本次的支數。
- 裁切、字幕燒錄、字幕安全區、響度正規化全部沿用既有的 Shorts 設定，本版**不重新實作任何一邊**。
- 沒規劃出東西時會直接說明原因（沒有精彩片段，或擴張後仍不足最短長度）並指出該調哪個設定，不會安靜地什麼都不做。

## 術語一致性檢查：同一個名字被寫成好幾種（v1.41.0 起）

調研（中英文皆搜）指向同一個很具體的問題：**語音辨識最會錯的就是專有名詞**，而且錯得很有自信。

- 英文資料說得最直接：「Proper nouns are where ASR drafts look confident but fail」，而且「**同一支影片裡同一個專有名詞被拼成不同樣子**是有完整記載的問題」；模型會「拿發音相近、自己認得的詞去替換不認得的專有名詞」。
- 中文資料同樣點名：「AI 辨識再準確還是會有錯字，特別是**專有名詞、人名、英文縮寫**」。

關鍵是**既有的解法都不夠**。本工具已經有「轉寫提示詞」可以先填人名，但 **OpenAI 自己的文件就說這個做法對專有名詞「不特別可靠」**。實務上被推薦的做法是事後在整份逐字稿裡把拼法統一，並維護一份自己的詞庫。

本工具的既有功能剛好各差一步：

| 既有功能 | 差在哪 |
|----------|--------|
| 自動修正詞庫（v1.8） | 能把錯字每集自動修掉，但**要你先知道哪裡錯了**——它負責修，不負責找 |
| 系列一致性檢查（v1.31） | 比的是整批影片的響度／解析度／色調，完全沒碰文字 |
| 尋找取代 | 要你自己想得到該找什麼 |

缺的正是中間那一段：**把「同一個詞出現了兩種以上寫法」找出來**。這不需要任何模型——證據就在逐字稿本身，同一支影片裡同時出現 `Anthropic` 和 `Anthropik`，其中一個必定是錯的。

```
===== 術語一致性檢查（同一個詞有沒有被寫成好幾種）=====
⚠ 大小寫不一致：YouTube（1 次）／Youtube（1 次）／youtube（1 次）
⚠ 疑似同一個詞的不同寫法：Anthropic（2 次）／Anthropik（1 次）

逐組明細：
  [英數拼法相近]
    Anthropic：2 次，出現在 0:20、0:26 ← 建議統一成這個
    Anthropik：1 次，出現在 0:32

建議加進「自動修正詞庫」的規則（加了之後每一集都會自動修）：
  Anthropik → Anthropic
```

- **分兩個信心層級**：`大小寫不一致`（YouTube／Youtube／youtube——字母完全相同，**不可能誤判**）與 `英數拼法相近`（Anthropic／Anthropik）。
- **次數一樣多時不替你猜**：沒有主流寫法可以參考的組會另外標示，一鍵統一也不會動它們。
- **報告直接給出可貼進「自動修正詞庫」的規則**，加進去之後每一集都自動修好——這正是調研建議的「維護自己的詞庫」，也把本工具原本斷開的一步接上了。
- `--termfix` 會另存「檔名_術語統一.srt」，**原始檔不受影響**。

### 為什麼詞形變化不會被誤改

只用相似度會出事：`youtube` 與 `youtuber` 的相似度高達 **0.93**，一鍵統一會把「這個 youtuber 很有趣」改成「這個 YouTube 很有趣」——**直接改壞句子**。語音辨識的錯法是「拿發音相近的詞去替換」，所以錯字與正字長度幾乎一樣；真正差在字尾的多半是詞形變化（`model`／`models`、`run`／`running`），那是兩個不同的字。因此判定要求**長度最多差 1，且兩者不能互為前綴**。實測 `youtuber`／`youtubers`／`model`／`models` 皆正確不被更動。

### 為什麼刻意不做中文的模糊比對

開發時實作過「中文同長度一字之差」的版本，**實測立刻證明這條路走不通**。中文沒有詞間空白，不靠斷詞詞典就只能用定長 n-gram，而 n-gram 會跨越詞的邊界。同一份逐字稿掃出：

- 「我們就／我們都」——**兩個都是正常的詞**
- 「克萊的／克萊念」——「柏克萊的時候」與「柏克萊念書」被切出來的碎片，照著統一會把「柏克萊念書」改成「柏克萊的書」

而真正的錯字「的時候／的時後」反而沒被抓到。**訊號比雜訊還少，又會破壞內容**，因此整層拿掉。中文的同音錯字仍請走既有的「自動修正詞庫」：修一次、之後每一集自動修。

- CLI：`python main.py --termcheck 影片.mp4`（加 `--termfix` 一併統一）；門檻與排除詞可於 `config.json` 的 `termcheck` 調整。

## 工商揭露健檢：業配揭露得夠不夠早（v1.40.0 起）

這一項踩到的代價不是「數據難看」，而是**法規風險**。

調研（中英文皆搜）確認規則明確而且可以機器檢查：

- YouTube 官方：創作者「有責任瞭解並完全遵守所在管轄區的法律義務，當中可能包含提供揭露訊息的**時機**、方式和對象」——**時機**是被官方明文點名的。
- **揭露義務與頻道大小、金額無關**，收到免費商品且有報導預期也算。
- 最關鍵的時機規則：**揭露必須出現在業配段落開始之前**。FTC 已明確指出「影片稍早就出現業配、卻把揭露放在片尾」不符合「清楚顯著」的標準。
- 口頭揭露的份量高於單純的畫面文字。
- 中文資料另外提醒，違反揭露義務在台灣可能面臨《公平交易法》裁罰。

還有一個反直覺但一致的發現：**坦白反而留得住觀眾**。中文討論的標題就是「想工商卻怕觀眾跑光？坦白才是最好的業配之道」——把工商段落做成一個**可以跳過的章節**，比藏起來讓觀眾自己撞上更不傷留存。所以本工具除了檢查，還會直接把那一行章節排好給你貼。

既有的檢查沒有涵蓋這一段：

| 既有檢查 | 看的是什麼 |
|----------|-----------|
| 開場健檢（v1.33） | 確實認得贊助商用語，但**只看開頭那幾秒**，問的是「會不會害觀眾離開」的留存問題 |
| 廣告友善度（v1.29） | **黃標**——YouTube 會不會不給你放廣告，與「有沒有向觀眾揭露」是相反的兩件事 |

「上片前總體檢」勾選「**工商揭露**」即可（預設開啟），報告長這樣：

```
===== 工商揭露健檢（業配有沒有揭露、揭露得夠不夠早）=====
✘ 揭露得太晚：業配從 1:40 開始，揭露卻遲至 3:10 才講
    建議：揭露必須出現在業配段落開始之前。FTC 已明確指出…
✔ 工商佔比：工商段落合計 16 秒，佔全片 8%，比例合理

建議加上的章節（讓觀眾可以跳過，坦白反而留得住人）：
  1:40 贊助商說明
```

- **看的是順序，不是有沒有工商**。有業配很正常；沒揭露、或揭露得比業配還晚才是問題。
- **揭露時間跨全片找，不是只看段落內部**。「這支影片由 X 贊助」講在開頭、業配口白在第 5 分鐘，是完全合規而且非常常見的做法——只比對段落內部會把這種**正確**的影片誤判成沒有揭露。
- **不會把一般影片誤判成業配**：一段要被認定為工商，必須含**兩個以上不同的推銷詞**，或含推銷詞且同段就有揭露語。單一句「連結在資訊欄」在一般影片太常見，不算。反過來，只講一句「這集是業配」而沒有任何推銷，那是**揭露**本身，不算一段業配、也不會產生章節。
- **三種狀態分開報**：事前揭露（通過）／事後才講（`✘` 揭露得太晚）／全片都沒講（`✘` 沒有揭露），三者的建議各不相同。
- 揭露詞、推銷詞與誤判排除詞皆可自訂並自動記憶（`config.json` 的 `sponsorcheck`）。
- **只報告不自動改**：要怎麼揭露、章節怎麼命名是創作決定。
- CLI：`python main.py --sponsorcheck 影片.mp4`（可與一般轉錄／對齊模式或 `--subs` 併用）輸出「檔名_工商揭露.txt」。

## 片尾空間健檢：最後 20 秒留得下結束畫面嗎（v1.39.0 起）

YouTube 的**結束畫面**（片尾）可以加在影片結束前的 **5 到 20 秒**，16:9 影片最多四項元素。官方最佳做法直接寫著：**編輯時請務必考慮影片最後 20 秒，為結束畫面預留足夠的空間**。

調研（中英文皆搜）指出這一段有**兩個方向相反、卻同樣常見**的失敗：

| 失敗方向 | 實際長什麼樣 |
|----------|-------------|
| **內容被蓋掉** | 「主要內容播放完畢就結束，片尾的推薦影片跑出來時，反而就擋住了最後這幾秒的畫面」；英文資料則說最常見的錯誤就是元素疊在重要內容、人臉或文字上 |
| **反過來留了一段死寂** | 「留 20 秒給元素，卻在這 20 秒什麼都不講，觀眾一認出這是片尾就直接離開」 |

所以正解**不是「把最後 20 秒空出來」**，而是讓元素疊在**仍然有意義的內容**上，但不要疊到會被擋住的東西上。這兩件事必須一起看——只檢查其中一個，給出的建議會剛好把人推向另一個失敗。

既有的檢查沒有涵蓋這一段：

| 既有檢查 | 看的是什麼 |
|----------|-----------|
| 品牌套版（v1.14） | 片尾是**接上一段片尾影片檔**，不是檢查最後 20 秒的內容 |
| 一鍵去頭尾（v1.17） | 尾端只看**結尾靜音的廢秒** |

「上片前總體檢」勾選「**片尾空間**」即可（預設開啟），報告長這樣：

```
===== 片尾空間健檢（最後 20 秒留得下結束畫面嗎）=====
⚠ 字幕位置：4:40 之後有 2 句字幕，而字幕擺在畫面 38%~52% 的高度，
   正好落進結束畫面元素會擺的範圍：4:45「如果這支影片對你有幫助」…
⚠ 片尾畫面：最後這段的畫面細節量 144（建議 12 以下）
✔ 片尾內容：最後 20 秒有 60% 的時間在講話，不是空白片尾
```

- **判斷的是字幕擺在哪，不是有沒有字幕**。最後 20 秒本來就該有字幕（沒有反而是死寂片尾），所以本工具的預設字幕位置（`position_y` 0.88）是**通過**的——畫面最下緣是播放器控制列的地盤，元素不會擺過去。把字幕往畫面中央移才會被標記，而建議會直接告訴你該調回多少。
- **講話覆蓋率**用字幕時間軸當代理指標：字幕本來就來自語音辨識，不必再解一次音訊。重疊的句子會先合併，比例不會算出超過 1 的數字。
- **畫面細節量**用 sobel 邊緣能量，門檻 12 是**實測校準**出來的：純色 0、SMPTE 彩條 4.3、testsrc2 測試圖 11.3、mandelbrot 碎形 14.5、細胞格 103、純雜訊 146。實測一支「前 10 秒乾淨、後 20 秒雜訊」的影片量到 **144**，把同一段雜訊移到片頭後量到 **0**——時間窗確實只看片尾。
- **純音訊檔也會跑**：死寂片尾與畫面無關，這是少數不需要畫面也不需要字幕的檢查。
- **只報告不自動改**：片尾要怎麼設計是創作決定。
- CLI：`python main.py --endscreen 影片.mp4`（可與一般轉錄／對齊模式或 `--subs` 併用）輸出「檔名_片尾空間.txt」；門檻可於 `config.json` 的 `endscreen` 調整。

## 上片前總體檢：一次跑完，只看該修什麼（v1.38.0 起）

> **v1.50.0 起：本節描述的判斷邏輯全數保留，入口併入「健檢中心」**
> （見上方「健檢中心」一節）；工具列「上片前總體檢」按鈕這一版還在，
> 點下去改開健檢中心。

本工具到 v1.37.0 已經累積 **16 項健檢**，散落在五個入口——上片前健檢對話框、字幕健檢對話框、三個獨立對話框，外加十幾個 CLI 旗標。要在上傳前確認一支影片沒問題，你得記得開三個視窗、按五個按鈕，還要自己判斷哪些一定要修。

調研確認這正是實務痛點：**漏掉單一一個步驟就可能讓一支影片少掉數千次觀看**。市面上的檢查清單工具因此都有兩個共同設計：**依嚴重度分級**與**一個總體準備度評分**——這正是這一版補上的東西。

工具列的「**上片前總體檢**」選好素材（字幕選填）按一下，就會得到：

```
===== 上片前總體檢：final_cut_v2.mp4 =====
準備度：F（一定要修 5、建議修 5、通過 10）

--- 一定要修（5）---
✘ [音訊健檢] 整體響度：量測 -21.9 LUFS，低於門檻 -19.0
✘ [影片畫質健檢] 位元率：0.1 Mbps，低於 YouTube 建議的 2.5 Mbps
✘ [剪輯節奏] 畫面變化：整支影片從頭到尾沒有任何畫面變化
...
```

- **每一條都標明來自哪一項檢查**，要深入處理時知道該開哪個視窗。
- **依素材自動略過**：純音訊檔跳過所有畫面檢查、沒有字幕就跳過字幕相關檢查。這不只是為了不出錯——每一項畫面檢查都要完整解碼一次影片，對純音訊檔跑四項畫面檢查是白白浪費四次解碼。

## 字幕可讀性健檢：燒錄後會糊在背景裡嗎（v1.37.0 起）

調研（中英文皆搜）指向一個很具體的問題：**白色字幕遇到偏白的畫面就會糊在一起看不見**。白色在生活與影像中都太常見，所以幾乎每支影片都會遇到——只是通常要等到燒錄完、播出去才發現。

本工具已經負責燒錄字幕，而且**手上就有判斷這件事所需要的全部資訊**：字幕的垂直位置、每一句的時間點、文字顏色與描邊寬度。但既有的檢查沒有任何一項在看這件事：

| 既有檢查 | 看的是什麼 |
|----------|-----------|
| 字幕健檢（v1.20） | 閱讀速度、行數、時間軸重疊——**純文字分析** |
| 畫面曝光與色偏（v1.28） | **整張畫面**的平均亮度 |
| Shorts 字幕安全區（v1.25） | 字幕**位置**會不會被平台介面遮住 |

都不是「字幕背後那一條帶子有多亮」。

字幕健檢對話框的「**檢查字幕可讀性**」會算出字幕實際會落在畫面上的那一條帶子，在各句時間點取樣量測該區域的亮度，再與文字顏色的亮度相比。實測一段下方帶子很亮的素材量到 222、很暗的量到 30，而純白文字亮度為 255——對比分別是 **33（看不見）** 與 **225（清楚）**。

報告會**直接講出該調哪一個設定**，因為那些設定就在本工具裡，而且順序照調研的共識排：

1. **先加黑色描邊**（白字＋黑描邊在亮暗背景上都看得清）
2. 干擾更高時**加粗描邊**，或把純白改成淺灰／淡黃
3. **半透明底框留到最後**——中文資料特別提醒「除非整支影片都是亮色，否則底框會顯得突兀」

- 另外會看**帶內的明暗落差**：字幕帶本身忽亮忽暗時，換任何單一文字顏色都救不了，只有描邊有用，這時會另外提醒。
- 判準是**文字與背景的差距**而不是「背景亮不亮」——深色文字配亮背景一樣會判定通過。
- 逐句解碼在長片上太貴，預設均勻取樣 12 句；取樣數、對比門檻與帶高比例皆可調並自動記憶。
- **只報告不自動改**：字幕要用什麼顏色、描邊多粗是視覺風格決定。
- CLI：`python main.py --legibility 影片.mp4`（可與一般轉錄／對齊模式或 `--subs` 併用）輸出「檔名_字幕可讀性.txt」。

## 發佈資訊健檢：hashtag 超量會整批失效（v1.36.0 起）

調研（中英文皆搜）確認的規則全都是可機器檢查的硬性數字，其中兩點特別容易踩：

**1. hashtag 超過 15 個，YouTube 會「忽略全部」而且不給任何提示。** 不是超出的那幾個失效，是**整批都不生效**。創作者堆了 16 個想要更多曝光，結果得到零——這與 v1.32.0 的章節不顯示是同一種靜默失敗。

**2. 說明欄的上限算的是「位元組」不是字數。** 中文一個字佔 3 個位元組，所以中文說明大約寫到 1,600 多字就會撞上限。實測 **1,690 個中文字 ＝ 5,070 位元組**，用字數檢查會判定「沒超過」，實際上早就被擋下。本工具因此一律以 UTF-8 位元組計算。

工具列的「**發佈健檢**」檢查：

| 項目 | 上限 |
|------|------|
| **標題** | 100 字元（超過 40 字元手機上會被截斷） |
| **說明欄** | 5,000 **位元組**（不是字數） |
| **hashtag** | 15 個（超過即全部失效）；建議 3~5 個，前 3 個會顯示在標題上方 |
| **標籤（tags）** | 總共 500 字元預算（分隔的逗號也算） |

本工具自 v1.10.0 起就會產生發佈包（標題候選＋描述草稿＋標籤清單），但**從未檢查過任何一項上限**。而且最常見的情境是「我自己寫的說明欄，為什麼 hashtag 沒有作用」——那份文字根本不是本工具產生的，所以這裡吃的是**你直接貼上的內容**。

- 重複的 hashtag 只算一次卻仍佔用 15 個額度，也會提醒。
- 標題裡的 hashtag 同樣佔用額度，會一併計算。
- **只報告不自動改**：標題怎麼寫、要留哪幾個 hashtag 是創作決定。
- 各項上限皆可調並自動記憶。
- CLI：`python main.py --publishcheck 發佈資訊.txt 影片.mp4`（文字檔第一行為標題、其餘為說明欄），可搭配 `--tags "攝影,相機"` 一併檢查標籤欄位。

## 封面健檢：這張縮圖在手機上看得清楚嗎（v1.35.0 起）

調研（中英文皆搜）指向同一組數字：**YouTube 七成以上的觀看來自手機**，而手機清單裡的縮圖只有大約 **200×110 像素**。業界的自我檢查法就是「把封面縮到 10% 大小再看一眼，如果看不清就是失敗」——資料指出**近四成的封面失敗原因單純就是「縮小後看不清楚」**。

本工具自 v1.11.0 起就會自動擷取封面候選圖，但**從未評估過產出的封面本身好不好用**——`thumbnails.py` 只在「挑哪一格」時算清晰度，挑完就結束了。而且最常見的情境其實是「我用 Canva／Photoshop 做好封面，這張能不能用」，那根本不是從影片幀來的。

因此工具列的「**封面健檢**」吃的是**任意圖片檔**，檢查：

| 檢查項目 | 怎麼量的 |
|----------|----------|
| **手機尺寸可讀性** | 把圖縮到 200 像素寬再放大回來，比較前後的邊緣強度。大色塊構成的封面幾乎不掉，細碎雜訊型的封面會崩到接近 0——也就是縮小後糊成一團 |
| **對比** | 手機尺寸下的明暗落差；太低就是灰濛濛、滑動時不會被看見 |
| **色彩鮮明度** | 平均飽和度，太淡會被旁邊的縮圖蓋過去 |
| **規格** | 解析度、16:9 比例、2MB 檔案大小上限（超過 YouTube 直接拒收） |

一次可加入多張候選圖，會依綜合分數排序並直接指出**建議使用哪一張**——這正好接上 v1.11.0 產生的那批候選圖。

- **只報告不自動修**：封面要怎麼改是設計決定，自動加濾鏡只會讓它更糟。
- 各項門檻皆可調並自動記憶。
- 分數只用於同一批候選圖之間的相對比較，不代表絕對品質。
- CLI：`python main.py --thumbcheck 封面1.png 封面2.png`（圖片直接當位置參數傳入）輸出「封面健檢.txt」。

## 剪輯節奏健檢：畫面太久沒變化會流失觀眾（v1.34.0 起）

調研（中英文皆搜）指向同一個問題：**長時間維持單一畫面是留存殺手**。英文資料稱之為「cognitive underload」——畫面沒有新東西可看可處理，觀眾就走了；並給出可量化的基準：talking head 的常態節奏約**每 15~25 秒一次畫面變化**。中文資料的說法是「都是維持靜態的片段會讓整個影片的可看性降低很多」「節奏忽快忽慢」。

本工具原有的畫面檢查沒有任何一項在看這件事。特別要說明的是它**和凍結畫面偵測是相反的性質**：

| | 看什麼 | 抓到的情況 |
|---|--------|-----------|
| **凍結畫面偵測（v1.26）** | 畫面**完全靜止** | 錄製瑕疵、SD 卡卡頓 |
| **剪輯節奏健檢（v1.34）** | 畫面**有在動、但久久沒換過鏡頭** | talking head 一鏡到底 |

talking head 長鏡頭裡人是會動的，所以凍結偵測完全抓不到——實測一段「前 30 秒完全沒有剪接」的素材，既有健檢對那 30 秒沒有任何提示。

「**上片前健檢**」的「開始健檢」現在會一併跑剪輯節奏健檢，檢查：

- **畫面變化次數與平均鏡頭長度**（整支一鏡到底會直接標為不合格）
- **超過上限沒有變化的段落**，逐段列出起訖時間與長度
- **節奏是否忽快忽慢**（最長鏡頭遠超中位數時提醒）
- 並直接給出**建議插入 B-roll／推鏡／圖卡的時間點**

- 畫面不變上限與剪接偵測靈敏度皆可調並自動記憶。
- **只報告不自動改**：要插 B-roll、推近鏡頭還是加圖卡是創作決定，而且工具手上也沒有你的 B-roll 素材。
- CLI：`python main.py --pacecheck 影片.mp4` 輸出「檔名_剪輯節奏.txt」。

## 開場健檢：前 15 秒決定觀眾走不走（v1.33.0 起）

調研（中英日文皆搜，日文資料最完整）一致指向同一件事：**開頭十幾秒決定觀眾要不要看下去**，而流失的主因幾乎都是同一組東西——冗長的打招呼、自我介紹、頻道宣傳、開場就先要訂閱，以及跟主題無關的閒聊。業界建議是「15 秒內要讓觀眾知道這支影片能給他什麼」，並且**把訂閱提醒移到影片後段**：對還沒被說服的新觀眾來說，一開場就要訂閱只會提前趕走他。

本工具原有的健檢沒有任何一項在看開頭「講了什麼」——「一鍵去頭尾」偵測的是**靜音／黑畫面**的廢秒，講滿話的開場廢話抓不到；「廣告友善度」只在開頭找**粗話**。字幕健檢對話框的「**開始健檢**」現在會一併跑開場健檢：

| 檢查項目 | 抓什麼 |
|----------|--------|
| **進正題時間** | 開頭講了多久才進入正題（預設超過 15 秒就標記） |
| **開場要訂閱** | 訂閱／按讚／小鈴鐺出現在正題**之前** |
| **開場寒暄過長** | 打招呼、自我介紹、頻道宣傳合計佔用過久 |
| **無關閒聊／廢話轉場／贊助商／頻道雜務** | 各自分類列出並附上該怎麼改 |
| **開頭沒聲音** | 影片開始後隔太久才有第一句話 |

**判斷依據是「扣掉開場套語後這句還剩多少實質內容」，而不是單純比對關鍵詞**——「廢話不多說，今天要教大家怎麼用三個步驟做出專業影片」含有開場套語，但它同時就是正題本身，因此會被正確算成**已進正題**。中英文分開計算：中文按字數，英文按實詞數，否則任何一句英文都會因為字母多而永遠被算成有內容。

- 報告會給出**建議的開場起點**（在此之前都是套語），可交給「上片前健檢」的修剪功能或審片助手處理。
- **只報告不自動剪**：要不要保留自我介紹、開場要怎麼改寫，是創作判斷。
- 進正題目標秒數、寒暄上限、開頭乾等上限皆可調並自動記憶；頻道固定用語被誤判時填入「排除誤判詞」即可，也可用「自訂套語」補充自己的口頭開場語。
- CLI：`python main.py --hookcheck 影片.mp4` 輸出「檔名_開場健檢.txt」，可與一般轉錄／對齊模式或 `--subs` 併用。

## YouTube 章節健檢：找出章節為什麼不顯示（v1.32.0 起）

章節貼進說明欄卻**整批都不出現**，是創作者社群反覆出現的求助情境。難處在於 **YouTube 不會給任何錯誤訊息**——它只是靜靜地不顯示，你只能一條一條試錯猜哪裡錯了。

其實規則是明確且可機器檢查的，工具列的「**章節健檢**」就是把它變成一份逐條報告：

| 規則 | 沒符合會怎樣 |
|------|--------------|
| **首章必須是 0:00** | 沒有 0:00 這一章，章節功能完全不會啟用 |
| **至少 3 章** | 少於 3 章一律不顯示 |
| **每章至少 10 秒** | 只要**任何一章**太短，整批章節都不顯示 |
| 時間戳格式 | 要用半形冒號、秒數補滿兩位、時間戳與標題之間要有空白 |

**輸入不限於本工具產生的章節**：手寫的、別的工具給的、從說明欄複製回來的都可以直接貼進去檢查——這才是最常見的求助情境，所以解析器會**指認出是哪一行、哪一種錯**（「時間戳要用半形冒號」「秒數要補滿兩位，例如 0:05 而不是 0:5」），而不是只說一句「格式錯誤」。

「**一鍵修正**」會在安全範圍內改好：修正打錯的格式、排序、移除重複時間、首章補成 0:00、把過短的章節併入前一章（保留前一章的標題）。每一項改動都會列在報告裡，修正結果也直接寫回輸入框，你可以再手動微調。

- **不會憑空捏造章節**：段落本來就不足 3 章時，程式會如實告訴你這不是格式問題、無法自動修正，而不是假裝修好了。
- **格式打錯的行不會被丟掉**：意圖明確的錯誤會被救回來，不會出現「修正後顯示全部合格，但你的章節少了兩條」這種最容易誤導人的結果。
- 影片檔為**選填**，提供後才能檢查「最後一章是否太短」。
- 每章最短秒數與最少章節數可調並自動記憶（預設就是 YouTube 目前的規則）。
- 審片助手的「**複製 YouTube 章節**」也接上了同一套檢查：草稿不符規則時會先擋下來說明原因，並詢問要不要改複製修正後的版本——以往這裡會直接把貼上去不會顯示的草稿交給你。
- CLI：`python main.py --chaptercheck 章節.txt --chapterfix 影片.mp4` 輸出「章節健檢.txt」與可直接貼回說明欄的「章節修正.txt」。

## 系列一致性：比對整批影片彼此之間（v1.31.0 起）

批次製作（一次拍 5~10 支、批次剪輯、一次排程上傳）最容易踩到的坑是：**每一支單獨看都沒問題，彼此之間卻不一致**。觀眾連看同一系列時就會遇到第三集突然要調大音量、第五集畫面明顯偏暗、某一集解析度掉下來。

工具列的「**系列一致性**」一次選取同系列的多支影片（至少 2 支），比對彼此之間的：

| 比對項目 | 抓什麼 |
|----------|--------|
| **整體響度** | 哪一集特別大聲或小聲——連看時最有感，觀眾得一直調音量 |
| **解析度／畫面更新率／視訊編碼** | 規格不一致，通常代表某一集的匯出設定跑掉了 |
| **畫面亮度／色調** | 不同天拍攝、白平衡沒統一時最常見 |

**這跟「上片前健檢」是兩件不同的事**：健檢是拿固定門檻（YouTube 建議位元率、-14 LUFS…）檢查**單一支影片合不合格**；系列一致性比的是**多支影片彼此之間一不一致**，用的是整批的中位數當基準。所以「整批都偏暗但彼此一致」不會被標記——那是風格，不是失誤；只有**偏離整批的那幾支**才會被指名。

- 報告直接列出每一支的量測值、指名偏離者與偏離幅度，並指向對應的既有修法（響度正規化、音訊修復）。
- 容許差異（響度／亮度／色調）皆可調並自動記憶。
- 只報告不自動修：統一整批要重新編碼整支影片，且「往哪個基準統一」是創作判斷，交給你決定。
- CLI：`python main.py --seriescheck EP01.mp4 EP02.mp4 EP03.mp4` 輸出「系列一致性檢查.txt」。

## 品牌套版：片頭片尾接續與浮水印（v1.14.0 起）

調研發現創作者最常抱怨的重複工作之一，就是**每支影片都要重複手動加一次片頭片尾、調一次浮水印位置**——工具列的「**品牌套版**」把這兩件事收進設定檔一次設好，之後每支影片按一下即可套用，不必再進剪輯軟體重複同一套操作。

- **片頭／片尾一鍵接續**：設定片頭、片尾影片路徑（可只設定其中一項），輸出時自動接到來源影片前後。尺寸、畫面更新率、音訊格式不一致時自動正規化，避免黑畫面或比例跑掉；沒有音軌的片頭／片尾（常見的純動畫 bumper）會自動補上靜音音軌，不會因此無法接續。
- **浮水印／Logo 自動疊加**：設定圖片後，可調位置（左上／右上／左下／右下／置中）、大小（相對畫面寬度 5~50%）、透明度（10~100%）與邊緣留白，全片皆有效果。只用浮水印（不接片頭片尾）時保留音軌直接複製，不做無謂的重新編碼。
- 兩者可各自單獨使用，也可同時套用（合併成同一次 ffmpeg 執行）；輸出檔為 `素材_套版.mp4`。
- 所有設定自動記憶在 `config.json`；CLI：`python main.py --branding 影片.mp4` 套用已設定的內容（免開視窗，未設定任何一項時單檔略過並提示）。

## 音訊轉影片：純音訊素材也能用上整條字幕管線（v1.27.0 起）

Podcast、廣播剪輯、純錄音訪談這類創作者手上常常只有音訊檔，但 YouTube 等平台的慣例是上傳「影片」——沒有畫面的音軌難以被演算法推薦，本工具原本的「燒錄字幕」等功能也都假設來源已經是影片，純音訊檔完全用不上。工具列的「**音訊轉影片**」解決這個缺口：

1. 選好音訊素材（mp3／wav／m4a／aac／flac／ogg），選擇樣式：
   - **波形**：可自訂顏色，經典的 podcast 波形視覺化
   - **頻譜**：即時頻率視覺化
2. 可選擇背景圖片（例如節目封面）——設定後視覺化縮成下緣一條色帶疊加，背景圖裁切置中填滿整個畫面；留空則輸出純黑底全畫面視覺化。
3. 按「輸出視覺化影片」，輸出 `素材_視覺化影片.mp4`。

**轉出後就是一支正常的影片**：可以直接把這支 mp4 當作來源，接上本工具既有的轉錄、字幕燒錄、翻譯、Shorts 輸出等任何流程——等於讓純音訊創作者第一次能用上完整功能，不必再另外找線上工具套封面圖產生影片。

樣式與解析度自動記憶；CLI：`python main.py --audiovis 節目.mp3`（依 config.json 的 audiovis 設定批次轉換）。

## 即時查譯：選字即翻，附學習用關鍵詞解說（v1.48.0 起）

創作者看外文素材（逐字稿、外語留言、參考影片的原文字幕）時，遇到看不懂的字詞就得切出去查字典或翻譯網站，思路一斷，剪輯節奏就跟著斷掉。工具列的「**即時查譯**」把「選取→查意思」收進本程式：開一個獨立的浮動小視窗，在逐字稿、字幕編輯框、尋找取代等任何文字框裡選取一段外文，鬆開滑鼠就自動看到中文翻譯，還會順帶挑出幾個值得學的關鍵詞附解說（同一次 API 呼叫拿到，不多花一次錢）。

1. 按工具列「**即時查譯**」開啟浮動視窗（預設 520×600、預設置頂，可勾掉；關閉視窗是隱藏不是關掉，快取與生字本都留著，再按一次原地復原）。
2. 到主視窗的逐字稿、或雙擊字幕清單開啟的編輯框裡，用滑鼠**選取一段外文並放開左鍵**，等約 350ms（可調）就會自動翻譯並顯示在「中文翻譯」區，值得學的詞會列在下方並附解釋。
3. 沒有文字選取時也可以先點字幕清單的某一列，再按「**翻譯選取內容**」——字幕清單是點列不是選字，收不到文字選取事件，這顆按鈕補上這條路徑。
4. 目標語言預設「繁體中文」，可在下拉選單改成簡體中文、英文、日文等；查過的關鍵詞預設自動收進「**生字本**」分頁，可匯出 CSV（UTF-8 BOM，兩欄「詞句」「意思」，可直接匯入 Anki 做記憶卡）。

**費用與安全機制**：每次翻譯呼叫一次 OpenAI API（沿用「轉寫設定」既有的 API 金鑰，短句約千分之一美元），同樣的字句直接用快取不重複計費；選取內容太長（預設超過 600 字）、太短、純數字符號、或已經是目標語言時會自動略過不觸發；連續 3 次翻譯失敗會自動暫停「選取後自動翻譯」，避免網路斷線時每選一次字就撞一次逾時。尚未在「轉寫設定」填入 API 金鑰時，視窗會直接顯示啟用說明，「選取後自動翻譯」勾選框也會停用，貼上金鑰後不必重開視窗即可使用。

## 一、下載與安裝

1. 前往本專案的 **Releases** 頁面，下載最新版的 `SRT-Subtitle-Generator.exe`。
2. 此為免安裝程式，下載後直接雙擊即可執行。
3. 首次執行會在程式所在資料夾自動建立 `config.json`（保存個人化設定）。

### 必要元件：ffmpeg（v1.12.0 起可一鍵自動安裝）

本程式的音訊解碼與語音轉錄皆依賴 **ffmpeg**。**最簡單的安裝方式：什麼都不用先做**——程式偵測不到 ffmpeg 時（審片助手、音訊健檢等視窗會顯示黃色提示條，錯誤視窗也會提供按鈕），按「**自動安裝 ffmpeg**」即可：

- 程式自動下載（約 80~100 MB，只需一次）並安裝到程式自己的資料夾
- **免管理員權限、不需要設定 PATH**，裝完立即可用、下次啟動自動生效

偏好手動安裝（或公司網路擋下載）時：

1. 至 [gyan.dev](https://www.gyan.dev/ffmpeg/builds/) 下載 release-essentials 壓縮檔。
2. 把其中的 `ffmpeg.exe` 與 `ffprobe.exe` 放到程式資料夾的 `tools\ffmpeg\bin\` 內（免設定 PATH）；或依傳統做法把 `bin` 資料夾加入系統環境變數 `PATH`。
3. 重新開啟本程式即可。

未安裝 ffmpeg 時，「文字稿對齊」「本地轉錄」「字幕燒錄」「粗剪／精彩合輯輸出」「音訊健檢」「封面候選」與審片助手的音量能量分析皆無法使用（審片的精彩偵測會退化為純文字訊號）。

### 自動更新

本程式（v1.1.0 起）內建自動更新：

- 每次啟動時會於背景向 GitHub 檢查是否有新版本。
- 偵測到新版時會跳出視窗詢問，同意後自動下載並替換程式檔。
- 更新完成後，關閉並重新開啟程式即可套用新版。
- 無網路或連線失敗時會自動略過，不影響程式使用。

## 二、三種運作模式

### 模式一：音訊轉錄

匯入影片／音訊檔，由系統自動產生逐字稿與時間軸。轉錄引擎有兩種選擇：

- **OpenAI API**（免安裝，最簡單）
- **本地 Whisper**（免費、可離線，但需自行安裝，見下方第三節）

### 模式二：文字稿對齊

貼上現成的逐字稿，系統會借用語音辨識取得音訊中「人聲」的時間軸（會自動忽略背景音樂），再把文字稿依語音長度與停頓分配到對應的時間點，讓字幕只落在有人聲的區段。

由於改用語音辨識偵測人聲，此模式同樣需要可用的語音辨識引擎（本地 Whisper 或 OpenAI API），設定方式與模式一相同，見下方第三節。

### 模式三：手動字幕模式

不經語音辨識，從零開始手動建立字幕：按「新增字幕」逐句輸入文字與起訖時間，適合無人聲素材、歌詞字幕或需要完全手工控制的情境。建立後同樣可使用匯出與燒錄功能。

---

## 三、語音辨識引擎設定（模式一與模式二皆會用到）

### 方式 A：使用 OpenAI API（推薦給一般使用者）

1. 切換到「模式一」。
2. 在「轉寫設定」勾選 **改用 OpenAI API**。
3. 於「API 金鑰」欄位填入你的 OpenAI API Key。
4. 選擇生成字幕即可，無須安裝任何額外程式。

### 方式 B：使用本地 Whisper（免費、可離線）

由於本程式為輕量版 exe，**並未內建 Whisper**。exe 是封閉環境，無法直接讀取你用 pip 安裝的套件，因此需採「外部 Python」方式串接：

#### 若你尚未安裝 Whisper

1. 安裝 [Python](https://www.python.org/downloads/)（3.9 以上版本），安裝時勾選 **Add Python to PATH**。
2. 開啟命令提示字元，執行：
   ```
   pip install openai-whisper
   ```
3. 確認 ffmpeg 已安裝（見第一節）。
4. 回到本程式「轉寫設定」的 **本地 Python** 欄位：
   - 留空：程式會自動偵測系統 PATH 上的 Python。
   - 或按「瀏覽...」指向該 Python 的 `python.exe`（通常位於
     `C:\Users\你的帳號\AppData\Local\Programs\Python\PythonXX\python.exe`）。
5. 之後選擇生成字幕，程式即會透過該 Python 執行 Whisper 轉錄。

#### 若你已經安裝過 Whisper

直接在「本地 Python」欄位按「瀏覽...」，指向「當初安裝 whisper 的那個 Python 的 `python.exe`」即可，程式會自動使用它。

> 查詢 python.exe 位置：開啟命令提示字元輸入 `python -c "import sys; print(sys.executable)"`，顯示的路徑即是。

#### 本地模型選擇

「本地模型」可選 `tiny` / `base` / `small` / `medium` / `large`，模型越大越準確但越慢。模型會於首次使用時自動下載。

#### 語言選擇

「語言」欄位除 `auto`、`zh`、`en` 等代碼外，另提供 **`zh-TW`**。Whisper 本身只認 `zh` 且預設常輸出簡體中文；選擇 `zh-TW` 時，程式會以 `zh` 辨識並加繁體提示詞偏導，再自動把結果轉換為台灣繁體中文。需要繁體字幕時請選 `zh-TW`。

## 四、智慧斷句設定

「斷句設定」區塊可即時調整，兩種模式皆適用：

| 設定項目 | 說明 | 調整範例 |
|----------|------|----------|
| 中文單行上限 | 中文字幕單行最大字數，超過會自動斷行 | 手機直向觀看字幕常顯太長時，調小到 14～16 字；橫向大螢幕可放寬到 20 字以上 |
| 英文單行上限 | 英文字幕單行最大字母數 | 同上邏輯，手機觀看建議 30～36 字母 |
| 最短秒數 | 每句字幕停留在畫面上的最短時間（過短會自動延長） | 觀眾反映字幕一閃即逝時調大（如 1.5 秒） |
| 最長秒數 | 每句字幕停留在畫面上的最長時間（過長會自動裁切） | 長句被硬切太短時可調大（如 6～8 秒），但避免整段影片只有幾句字幕 |
| 停頓秒數 | 音訊中靜音多久才算一次「停頓」，作為斷句與時間對齊的依據 | 講話語速快、停頓短的內容（如遊戲實況）可調小（0.3～0.5 秒）讓斷句更即時；語速慢、常有思考停頓的內容可調大避免斷句過於破碎 |

斷句演算法會優先依句末標點切句，其次依句中標點切子句，避免單一字幕文字過長霸佔畫面。不確定該調多少時，先用預設值生成一次字幕，看實際效果哪裡不順眼（太長／太短／停留太久／太快消失）再針對性調整，比一開始就大幅更動更容易抓到合適的數值。

## 五、字幕視覺調整

「字幕視覺調整」面板可即時設定：

- **位置**：水平 X、垂直 Y 滑桿，或使用「頂部／中部／底部」快捷鍵。
- **字型**：下拉選單內建常見中英文字型；旁邊的「...」按鈕可開啟字型選擇器，
  從系統字型中搜尋，或按「從字型檔匯入」載入自己的 `.ttf` / `.otf` 字型檔。
- **字型大小**、**文字顏色**、**邊框顏色**、**邊框寬度**。
- **重點字上色**（v1.6.0 起）：勾選後填入詞彙（逗號或空白分隔，如自己頻道的產品名、「免費」「限時」等），燒錄影片與匯出 ASS 時這些詞會自動換色強調（預設金黃、可選色）——CapCut 風格的重點標記，免逐句手動處理。SRT／VTT 純文字輸出不受影響。

  **範例：** 帶貨直播剪輯常見句子「這個現在**免費**送，數量**限時**搶購」，只要在重點字欄位填入 `免費, 限時`，之後每一句字幕只要出現這兩個詞就自動變色，不必逐句手動上色；詞彙用逗號或空白分開即可一次填多個，長詞（如「破盤價」）會優先於短詞比對，不會被短詞截斷。想要不同影片用不同顏色（例如促銷用紅色、重點用金黃），改變「重點字顏色」即可，設定會隨樣式一起記憶。

- **動態字幕**（v1.7.0 起）：逐字動畫字幕，於燒錄影片與 ASS 匯出時生效，兩種模式：
  - **逐字上色（卡拉OK）**：整句顯示在畫面上，講到哪個字、哪個字就換色（顏色沿用「重點字顏色」）——觀眾的視線跟著語音走
  - **單字彈出**：畫面上只顯示當前講到的字詞，並帶輕微放大彈出動畫——Shorts／Reels／TikTok 最常見的字幕版式，搭配大字級（例如 48 以上）與畫面中央位置效果最好
  - 需要逐字時間軸，因此**只在「模式一：音訊轉錄」產生的字幕上生效**；手動字幕、文字稿對齊或編輯過的句子自動退回一般整句顯示，不會出錯
  - 審片助手輸出的直式短片若勾「燒錄字幕」，同樣套用此模式——單字彈出＋直式短片就是現成的 Shorts 成品

所有調整（含重點字上色，v1.6.1 起）都會即時反映在「即時字幕預覽」畫面上，改詞彙或顏色不必先燒錄就能看到效果（動態字幕的逐字動畫屬於影片時間軸效果，預覽維持整句顯示，實際效果以燒錄輸出為準）。

## 七、生成與匯出

**建議直接使用「一鍵完成」**（見開頭「快速上手」），生成、匯出、燒錄一步到位。以下為需要逐句檢查、微調時的手動流程：

1. 選擇模式、匯入檔案（模式二另需貼上文字稿）。
2. 按「開始生成字幕」，狀態列會顯示進度。
3. 生成完成後，字幕清單會列出每一句字幕，點選任一句可在預覽畫面中檢視，雙擊可編輯。
4. **校對**：同一個錯字整集重複出現時（人名、產品名、同音字），按「**尋找取代**」（v1.7.0 起）一次修正——「找下一個」逐句檢視、「取代目前」逐句確認、「全部取代」一鍵修完並回報次數；對話框開著仍可操作清單。
   - **自動修正詞庫（v1.8.0 起）**：對話框下方按「**把目前取代存為規則**」，這個錯字之後**每次生成字幕都會自動修正**，不必每集重修。語音辨識對特定人名、產品名的錯法通常很固定，累積幾條規則後校對量會明顯下降；規則可隨時在清單中刪除，重存同一錯字則更新規則。
5. 按「匯出 SRT／VTT／ASS／TXT」選擇儲存位置輸出字幕檔，或按「燒錄字幕到影片」輸出硬字幕影片。

### 字幕翻譯：一鍵雙語字幕（v1.18.0 起）

YouTube 的自動字幕功能無法輸出雙語軌，超過三分之二的觀看時數卻來自創作者所在地區以外——生成字幕後，按字幕清單下方的「**翻譯字幕**」即可一鍵翻譯：

1. **選目標語言**：11 種語言可選（英/日/韓/繁中/簡中/西/法/德/印尼/越南/泰）。
2. **選模式**：「雙語（原文＋譯文上下行）」讓每句字幕顯示原文與譯文兩行；「僅保留譯文（取代原文）」直接用譯文取代原字幕（可重新生成復原，不影響原始素材）。
3. 按「開始翻譯」。**需要 OpenAI API 金鑰**——沿用「轉寫設定」裡已填的那一把，不必再另外申請，按用量計費。
4. 翻譯完成後自動套用到字幕清單，可再用「尋找取代」校對；雙語行匯出與燒錄時分兩行顯示。

**譯文由 AI 產生，建議翻譯後抽查幾句**，尤其是人名、專有名詞與語氣是否恰當。另外，逐字動態字幕（卡拉OK／彈出字模式）在翻譯後會自動退回整句顯示——翻譯後的文字與原本的逐字時間軸已經對不上，直接顯示整句字幕最穩妥。

### 匯入既有字幕檔（v1.19.0 起）

本工具原本只能「匯出」字幕，手上已經有的字幕檔——下載的 YouTube 自動字幕、其他工具產出的檔案、舊專案留下的字幕——完全進不了工具，只能開記事本手動改。現在字幕清單下方多了「**匯入字幕**」按鈕，選取 .srt／.vtt 檔即可直接載入，接上編修、樣式、翻譯、燒錄整條既有管線。

**典型工作流程**：下載 YouTube 自動字幕 → 匯入本工具修正錯字（尋找取代）→ 翻譯成雙語字幕 → 燒錄成硬字幕影片（TikTok／Reels 等平台不支援外掛字幕檔，這是唯一選項）。

1. 按「**匯入字幕**」選擇 .srt 或 .vtt 檔；目前清單非空時會先確認是否取代。
2. 匯入成功後狀態列顯示「已匯入 N 句字幕（略過 M 段無法解析、編碼 X）」，字幕清單與預覽同步更新。
3. 之後即可比照一般生成結果操作：尋找取代校對、翻譯字幕、調整樣式、匯出其他格式或燒錄硬字幕。

**格式容錯細節**：
- **YouTube VTT 行內標記**：自動清除逐字時間戳 `<00:00:01.500>`、顏色／語者標籤 `<c>`、`<v Speaker>`，以及 `<i>`／`<b>`／`<u>`／`<font>` 等常見標記與 `{\an8}` 等 ASS 覆寫碼。
- **編碼自動偵測**：依序嘗試 UTF-8（含 BOM）／繁體 Big5 系列（cp950）／簡體（gb18030），Windows 上常見的非 UTF-8 字幕檔不會變亂碼。
- **略過壞區塊不中斷**：索引行可省略、時間軸容忍逗號或點分隔的毫秒、CRLF／CR 換行皆可解析；單一區塊格式有誤只略過該段並計入略過數量，不會讓整份檔案匯入失敗。

**CLI**：`python main.py --subs 影片.srt --burn 影片.mp4` 可跳過語音辨識，直接用既有字幕檔匯出其他格式並燒錄硬字幕（見下方命令列批次模式）。

### 字幕健檢：閱讀速度與行數（v1.20.0 起）

> **v1.50.0 起：本節描述的判斷邏輯全數保留，入口併入「健檢中心」**
> （見前面「健檢中心」一節）；編輯列「字幕健檢」按鈕這一版還在，點
> 下去改開健檢中心。

字幕檔案審核最常見的退件原因就是「觀眾根本來不及讀完」——業界常用 CPS（每秒字元數）當量尺，Netflix 成人內容上限 20、BBC 建議 15 以下。本工具生成字幕時雖然有斷句規則限制單行字數，但翻譯（雙語內容變兩倍長，時間軸卻沒變）、匯入既有字幕檔（品質不明）、手動新增或編輯的字幕都可能產生從未檢查過的過快字幕。

字幕清單下方按「**字幕健檢**」，掃描目前清單（不論字幕從何而來）並標出五類問題：

| 檢查項目 | 內容 | 預設門檻 |
|----------|------|----------|
| **閱讀速度過快** | 每秒字元數（CPS）超過門檻 | 17 字/秒 |
| **顯示時間過短** | 單句顯示秒數太短，來不及注意到 | 0.8 秒 |
| **行數過多** | 單句超過建議行數 | 2 行 |
| **單行過長** | 單行字元數超過建議寬度 | 21 字 |
| **字幕重疊**（v1.23.0 起） | 前後兩句時間軸重疊 | 有重疊即標記 |

- 門檻皆可在對話框調整並自動記憶（例如面向兒童或需要精讀的教學內容可調得更嚴格）。
- 按「**一鍵延長過快字幕**」：把 CPS 超標或顯示過短的句子，在**不與下一句重疊**的前提下自動延長顯示秒數（只調整時間軸，不改動文字內容）；下一句銜接太緊、沒有空檔可用時保留原樣，不會強行製造新的重疊，這時建議改為精簡文字內容。
- 按「**一鍵修復重疊**」（v1.23.0 起）：截短較早一句的結束時間消除重疊；起始時間相同或反序、單靠截短無法消除時，較早一句改保留極短長度、較晚一句整段順延並保留原本時長不變。**這是匯入既有字幕檔與手動編輯特別需要的檢查**——生成字幕（模式一／模式二）內建正規化已保證不重疊，但匯入檔案品質不明、手動編輯也未曾檢查起訖時間是否與相鄰句子衝突，時間軸重疊常導致 YouTube 等平台匯入失敗或播放異常。
- CLI：`python main.py --subcheck 影片.mp4` 輸出「檔名_字幕健檢.txt」（含重疊檢查），可與一般轉錄／對齊模式或 `--subs` 併用（`--review` 等不產生字幕的模式無效果）；實際修復請於 GUI 操作。

#### 中文字幕標點規範（v1.47.0 起）

**逐字稿的標點跟字幕的標點不是同一回事。** Whisper 產出的是書面標點齊全的逐字稿，而中文字幕有一套相當一致的慣例：**句末不加句號與逗號**——斷行本身就已經表達了停頓，下一句本來就是另一張畫面；但**問號與驚嘆號要保留**，那兩個帶的是語氣。Netflix 的字幕風格指南講得最直接：句末標點只允許問號與驚嘆號。

本工具的斷句演算法又刻意**切在逗號上**，兩件事加起來的結果是：**幾乎每一句字幕都以一個沒有作用的逗號結尾**。實測四種常見影片類型的講稿共 27 句，**85% 的句子以標點結尾**。

字幕健檢對話框下方的「**中文標點規範**」提供三段強度（自動記憶）：

| 強度 | 做什麼 | 適合 |
|------|--------|------|
| **只拿掉行尾標點**（預設） | 只清掉行尾的「，。、；：」 | 絕大多數情況；改動最小、爭議最少 |
| **完整字幕慣例** | 再把**句中**的逗號、頓號改成全形空格 | 想要接近專業字幕組的排版 |
| **不套用** | 只看報告不改字 | 頻道風格就是要留標點 |

- **問號、驚嘆號、刪節號一律保留**，不受強度影響。
- **英文字幕完全不會被動到**。英文的逗號與句號是文法的一部分，`Hello, everyone.` 拿掉標點會變成錯的句子；本功能只處理中日韓字元佔一定比例以上的行（預設 0.15，實測中英夾雜的中文行最低 0.27、純英文行最高 0.06，門檻落在中間）。所以像「我用的是 Premiere Pro，」這種中英夾雜的行會正確處理，而「I use Premiere Pro, and it works fine.」原封不動。
- **整行只有標點時不會被清空**，避免吃掉一句字幕。
- 按「**一鍵套用標點規範**」就地套用到目前的字幕清單（只改文字，時間軸完全不動）。
- CLI：`python main.py --punctcheck 影片.mp4` 輸出「檔名_標點規範.txt」；加上 `--punctfix` 另存「檔名_標點規範.srt」。強度可於 `config.json` 的 `punctstyle` 調整（`mode`：`trim`／`subtitle`／`off`；`space`：句中逗頓要換成的空白；`cjk_ratio`：中文行判定門檻）。

#### 廣告友善度自查：上傳前先自己抓黃標（v1.29.0 起）

「黃標」（影片被標為不適合多數廣告主）通常是上傳後才被系統標記，申訴要等、重新審查也要等；社群流傳的自保作法是「先以不公開模式上傳、靜置 12~24 小時等系統掃描」，等於每支影片都要多花一天。本工具已經有完整逐字稿與時間軸，字幕健檢的報告因此**同時附上廣告友善度自查**，幾分鐘內就能先自己看過一遍。

- **重點是「高風險段落」而不是逐詞抓**：YouTube 的判定看的是短時間內的關鍵字叢集，不是單一詞——歷史頻道講一次「步槍」通常沒事，短時間內密集出現一整串相關詞才會被歸類。本功能因此用**時間窗加權叢集分析**（預設 30 秒窗、風險分數 3 分為門檻，皆可調）標出真正該優先處理的段落，零星單次提及不會誤報。
- **開頭數秒另外加強提醒**：依 YouTube 2025 年 7 月粗俗用語政策更新，開頭數秒的用詞對營利判定影響特別大，落在開頭區間（預設 7 秒，可調）的命中會單獨列出。
- **依頻道題材裁剪**：新聞、歷史、醫療、遊戲頻道本來就會提及部分詞彙，填入「**排除誤判詞**」之後就不再重複標記；也可用「**自訂補充詞**」加入自己頻道特有的風險詞。設定自動記憶。
- **只提醒、不改動內容**：同一個詞在教育、新聞、遊戲實況情境下的風險完全不同，自動消音反而可能破壞內容原意，因此本功能只負責報告與建議。
- **這不是官方清單**：YouTube 從未公布官方禁用詞列表，內建詞表是依「廣告客戶青睞內容規範」的主題分類整理的自查起點；實際判定另包含畫面、標題、縮圖與整體脈絡——**命中不代表一定被標記，未命中也不保證不會被標記**。
- CLI：`python main.py --adcheck 影片.mp4` 輸出「檔名_廣告友善度.txt」，可與一般轉錄／對齊模式或 `--subs` 併用。

#### 字幕與語音同步檢查／一鍵校正（v1.30.0 起）

匯入既有字幕檔（下載的字幕、其他工具產出的檔案、舊專案留下的檔案）最常見的翻車點就是**跟聲音對不上**。這分兩種成因、解法完全不同：

| 症狀 | 成因 | 解法 |
|------|------|------|
| **固定偏移**：整條字幕一致地早或晚 | 匯出設定不同、片頭被剪掉、平台處理延遲 | 整軌平移 |
| **逐漸漂移**：開頭對得上、越後面差越多 | **幀率不符**（23.976 fps 的字幕套到 25 fps 版本會漂移約 4.3%，90 分鐘影片到片尾差近 4 秒） | 依比例縮放時間軸，平移救不回來 |

字幕健檢視窗按「**檢查與語音同步**」，本工具會掃出素材的**實際語音區間**（不必你自己找錨點），計算字幕落在語音上的貼合度，並搜尋最佳的「縮放倍率 × 偏移秒數」線性校正——**一次同時涵蓋上面兩種情況**：

- 縮放倍率只試常見幀率比值（23.976／24／25／29.97／30 互換），因為漂移的成因就是幀率不符；這比盲目搜尋任意倍率更穩，也更不容易把本來就對齊的字幕改壞。
- 除了看全片平均貼合度，另外比較**頭尾三分之一的落差**——漂移會被對得很準的開頭稀釋掉平均值，只看平均會漏判。
- 按「**一鍵校正同步**」自動套用，**只調整時間軸，不改動或刪除任何文字內容**（逐字動態字幕的時間軸也會一併校正）。
- 只有在校正後明顯更好時才會建議套用；素材幾乎全程有聲（連續講話或整片配樂）時，語音區間提供不了對齊資訊，會明確告訴你「無法可靠判定」而不是硬給一個看似精確的錯誤數字。
- CLI：`python main.py --subs 舊字幕.srt --synccheck 影片.mp4` 輸出「檔名_同步檢查.txt」；加上 `--syncfix` 會直接另存校正後的「檔名_同步校正.srt」（原始字幕檔不受影響）。

### 全片停頓自動跳剪（v1.21.0 起）

創作者社群公認「剪掉停頓」是初剪最花時間、最想自動化的一步——本工具已有的「一鍵去頭尾」只處理開頭結尾廢秒，中段每一句換氣、思考停頓仍要手剪。

字幕清單下方按「**自動跳剪停頓**」：依目前字幕的時間軸找出句與句之間過長的停頓，一次剪掉整支影片的冷場——**字幕時間軸同步重新對齊**，剪完不必再手動調整字幕。

- 先按「**預覽跳剪點**」（純分析目前字幕，免呼叫 ffmpeg，瞬間看到偵測到幾處停頓、預估能省下多少秒數），確認合理後再按「**輸出跳剪版**」實際裁切
- 門檻皆可調並自動記憶：**最短停頓秒數**（達此長度才視為可跳剪的冷場，預設 1.2 秒）、**緩衝秒數**（剪點兩側各保留的秒數，避免斷得突兀，預設 0.15 秒）、**安全上限**（跳剪總長度超過影片長度的此比例時自動中止，防止門檻設太低誤剪，預設 60%）
- 輸出 `素材_跳剪.mp4`＋時間軸已對齊的字幕檔（同資料夾）
- CLI：`python main.py --jumpcut 影片.mp4`，可與一般轉錄／對齊模式或 `--subs` 併用；`--burn` 燒錄的仍是原始（未跳剪）影片，兩者暫不會自動串接

### 重複片段偵測與剪除（v1.22.0 起）

同一句話講了好幾次、要手動翻逐字稿找出前面講壞掉的版本剪掉——這是初剪另一個吃時間的步驟。

字幕清單下方按「**重複片段偵測**」：找出同一時間窗內文字高度相似的句子（同一句話的前後幾次嘗試），只保留最後一次。**這裡動的是實際講話內容，假陽性風險比純靜音的跳剪高**（例如刻意重複的口號、報數測試麥克風），因此設計為先列出候選逐項勾選確認，才真正剪：

- 「**偵測重複片段**」（純分析目前字幕，免呼叫 ffmpeg）列出候選清單，預設全選，可自行取消勾選誤判項目，再按「**剪掉勾選的重複片段**」實際裁切
- 門檻皆可調並自動記憶：**相似度門檻**（兩句文字達此相似度才視為同句重講，預設 72%）、**比對時間窗**（只比對此秒數內的句子，間隔太遠不算重錄，預設 25 秒）、**剪點外擴秒數**（連同前後的吸氣停頓一起剪掉，預設 0.2 秒）
- 剪完影片同步把字幕時間軸重新對齊、被剪掉的句子從清單移除；輸出 `素材_去重複.mp4`＋對齊後的字幕檔
- CLI：`python main.py --retakes 影片.mp4` 只輸出候選清單「檔名_重複片段.txt」（不自動剪）；搭配 `--retakes-cut` 才會實際剪掉全部候選（命令列無法逐項確認，建議先用 `--retakes` 看過候選清單再決定）

## 九、常見問題

**Q：點「開始生成字幕」後出現「找不到 ffmpeg」？**
A：請依第一節安裝 ffmpeg 並加入系統 PATH。

**Q：本地轉錄出現「找不到可用的本地 Whisper」？**
A：請依第三節方式 B 安裝 Whisper，並在「本地 Python」欄位指向正確的 python.exe，或改用 OpenAI API 模式。

**Q：視窗內容顯示不下？**
A：視窗可自由縮放，內容超出時可使用右側／底部捲軸，或用滑鼠滾輪捲動。
字幕生成完成後（含「一鍵完成」批次生成），若清單原本不在視窗可視範圍
內，會自動捲動到字幕清單處，不必自己往下找（v1.49.0 起）。

**Q：字幕斷句太長或太短？**
A：於「斷句設定」調整單行字數上限與秒數限制後重新生成。

**Q：「一鍵完成」的檔案輸出到哪裡？**
A：預設輸出到來源影片所在的資料夾，檔名沿用來源檔名（如 `影片.srt`、`影片_subtitled.mp4`）。想集中輸出到固定資料夾，可在「自動化輸出」的「輸出資料夾」指定。同名檔不會被覆蓋，會自動加上 `(1)` 流水號。

**Q：把檔案拖到 exe 圖示上沒有反應？**
A：拖曳執行採用「自動化輸出」記憶的設定，請先開啟程式在「自動化輸出」勾選至少一種匯出格式（或燒錄），關閉程式後再拖曳。處理需要時間（轉錄與燒錄），完成後才會跳出結果視窗。

**Q：審片助手的「精彩片段」是怎麼判定的？標太多／太少怎麼辦？**
A：綜合四種訊號評分——說話音量能量、語速、情緒詞（哇、太扯、wow…）與驚嘆句，達門檻即標記。標太少請到「偵測設定」把**精彩敏感度**調高（如 1.5），標太多就調低（如 0.7）；也可在**自訂情緒詞**加入自己頻道常用的口號與梗詞，讓判定更貼合內容。設定會自動記憶。

**Q：同一支影片轉錄過了，換個功能又要重新等辨識？**
A：v1.4.0 起內建轉錄快取：同一檔案且轉寫設定相同時自動重用先前結果（例如審片分析完再一鍵上字幕，第二次瞬間完成）。快取存於程式資料夾的 `transcribe_cache/`，自動限量清理；不需要時可在「轉寫設定」取消勾選「重用轉錄快取」。

**Q：輸出的直式短片人物不在畫面中間？**
A：「裁切」版式預設焦點 0.5（畫面正中）。人物偏左調小（如 0.3）、偏右調大（如 0.7）後重新輸出；或改用「模糊背景」版式保留完整畫面。

**Q：響度正規化該用什麼目標值？**
A：一般影片用預設 **-14 LUFS**（YouTube 標準）即可。想在正規化後仍略高於平台基準，可用 -13～-11；Podcast 類口說內容常用 -16。設定會記憶，不需每次調整。

**Q：轉錄結果在同一時間點出現多句重複字幕？**
A：這是 Whisper 遇到靜音或背景音樂時的已知現象（幻覺迴圈），v1.4.0 已加入三層自動去重防護。若仍遇到，可回報 issue 並附上來源音訊特徵（如長靜音、純音樂段）。

**Q：動態字幕（卡拉OK／單字彈出）選了卻沒有效果？**
A：動態字幕需要逐字時間軸，只在「模式一：音訊轉錄」產生的字幕上生效；手動字幕、文字稿對齊或編輯過文字的句子會自動退回一般整句顯示。另外效果只出現在**燒錄影片與 ASS 匯出**——「即時字幕預覽」與 SRT／VTT 輸出維持整句。若整支影片都沒有效果，請確認字幕是本次以模式一生成的（重新按「開始生成字幕」即可）。

**Q：尋找取代會改到時間軸嗎？改錯了怎麼辦？**
A：尋找取代只改文字，時間軸完全不動。「全部取代」前可先用「找下一個」逐句檢視命中的句子；若取代錯了，把「尋找」與「取代為」兩欄對調再全部取代一次即可還原。

**Q：每集都要重修同樣的錯字（人名、產品名），有辦法記住嗎？**
A：有（v1.8.0 起）。在「尋找取代」填好錯字與正確字後，按下方「**把目前取代存為規則**」——之後每次生成字幕（含一鍵完成與 CLI 批次）都會自動套用，不必再手動修。規則清單就在對話框下方，可隨時刪除或重存更新。

**Q：背景音樂較大聲的素材，精彩片段是不是標得怪怪的？**
A：v1.8.0 起音量分析預設聚焦人聲頻帶（150～4000 Hz），配樂鼓點不再干擾精彩判定，直接重新分析即可。若素材本身以音樂為主體（樂器演奏、DJ），到「偵測設定」關閉「音量聚焦人聲頻帶」。

**Q：勾了「剪除口頭禪字」，粗剪聽起來會不會很跳？**
A：有三層保護：太短的口頭禪（<0.12 秒）不剪、剪點向內縮小緩衝不切到相鄰字、剪除後過短的殘片自動捨棄，多數口播素材效果自然。若素材語速很快、逐字跳剪頓挫感明顯，取消勾選改回整段取捨即可；也可改用 EDL 進剪輯軟體，剪點相同但可逐一微調。

**Q：發佈包的建議標題／標籤是怎麼來的？可靠嗎？**
A：標題取自「精彩分數最高的段落文字」——觀眾反應最大的內容通常就是影片賣點；標籤取自素材中實際講到的高頻詞（你的自訂情緒詞優先、中文高頻詞組、英文高頻詞）。它們是「初稿與靈感」而非成品：標題建議挑一個再潤飾、標籤上傳前自行增刪。想要更多候選，調大 `config.json` 裡 `publish` 的數量設定。

**Q：配樂助手輸出後，音樂閃避的效果聽起來還是不太對？**
A：先確認調的是哪個方向的問題——講話時**音樂還是蓋過人聲**：調高「閃避強度」；閃避**忽大忽小很突兀**（例如講話中間有短暫停頓就跳回原音量）：調低「閃避強度」或調高「閃避靈敏度」數值讓觸發沒那麼敏感；整體**音樂太大聲或太小聲**（跟閃避無關）：直接調「音樂音量」。三個旋鈕互相獨立，一次只調一個比較容易聽出差異。

**Q：審片助手輸出的 EDL 怎麼用？**
A：在 Premiere Pro 選「檔案 → 讀入」、DaVinci Resolve 選「File → Import → Timeline」載入 `.edl`，再連結原始素材，時間軸就是保留段落的順剪，可直接開始精剪。

**Q：粗剪影片／精彩合輯輸出後聲音或畫面不同步？**
A：粗剪採重新編碼（libx264＋AAC）確保剪點精準，一般不會不同步；若來源影片編碼特殊，建議改用 EDL 進剪輯軟體處理。
